# マスタ管理機能 基本設計書

## 1. 概要

本機能は、システム内で利用する汎用的なマスタデータを、マスタ分類ごとに検索・参照・登録・更新・削除する機能である。

画面の起点は `/master` とし、以下の機能を提供する。

- マスタの検索および一覧表示
- マスタの新規登録
- 登録済みマスタの詳細表示
- マスタの更新（マスタ分類・マスタコード・マスタ内容）
- 登録・更新内容の実行前確認
- マスタの削除
- マスタ分類の一覧表示および詳細表示
- マスタ分類の新規登録
- マスタ分類名の更新
- マスタ分類の削除
- マスタおよびマスタ分類のCSVダウンロード

マスタ分類と個々のマスタデータは別のテーブルで管理する。**マスタ分類は専用の画面で登録・更新・削除する。** マスタの新規登録画面から新しいマスタ分類を作ることはできず、登録済みのマスタ分類を選択できるだけとする。分類を増やす操作とマスタを増やす操作を分けることで、マスタを登録するつもりで分類が増えてしまう事故を防ぐ。

登録・更新の入力画面ではデータベースを更新せず、確認画面で「実行」ボタンが押された時点で初めて反映する。

削除は**物理削除**とする。論理削除は採用しない。削除したマスタおよびマスタ分類はデータベースから行ごと消えるため、画面からの復元手段は設けない。この方式を採る理由と制約は §8.3 に記す。

## 2. 用語

| 画面名称     | 説明                       | 例                     |
| -------- | ------------------------ | --------------------- |
| マスタ分類コード | マスタ分類のコード。0001から自動採番     | 0001、0002             |
| マスタ分類    | マスタデータを用途ごとにまとめる分類       | 契約種別、都道府県、支払方法        |
| マスタコード   | 同じマスタ分類内でマスタデータを識別するコード  | `CON00001`、`PREF0001` |
| マスタ内容    | マスタコードに対応する表示内容（マスタデコード） | 月額契約、東京都              |

## 3. 権限

既存のロールに対する操作権限は以下とする。

| 操作          | ADMIN | OPERATOR | VIEWER |
| ----------- |:-----:|:--------:|:------:|
| マスタの検索・一覧表示 | 可     | 可        | 可      |
| マスタの詳細表示    | 可     | 可        | 可      |
| マスタの新規登録    | 可     | 可        | 不可     |
| マスタの更新      | 可     | 可        | 不可     |
| マスタの削除      | 可     | 可        | 不可     |
| マスタ分類の一覧    | 可     | 可        | 可      |
| マスタ分類の詳細    | 可     | 可        | 可      |
| マスタ分類の新規登録  | 可     | 可        | 不可     |
| マスタ分類の更新    | 可     | 可        | 不可     |
| マスタ分類の削除    | 可     | 可        | 不可     |
| CSVダウンロード   | 可     | 可        | 可      |

VIEWERには「新規登録」ボタン、「更新する」ボタンおよび「削除」ボタンを表示しない。画面上の非表示だけでなく、Server Actionでも書き込み権限を検証し、不正な直接リクエストを拒否する。判定には既存の `canWrite`（`@/shared/constants/roles`）を使用する。

CSVダウンロードは参照操作であり、一覧画面で閲覧できる情報しか含まないため、参照権限と同じく全ロールに許可する。ただし絞り込みの有無にかかわらず対象を一度に取得できる操作であるため、実行者をログへ記録する（§13.11）。また、生成されたCSVを受け取れるのは**依頼した本人だけ**とする（§13.5.3）。

マスタコードの変更は業務上の識別子を書き換える操作だが、マスタ内容の更新と権限を分けずADMIN・OPERATORとする。ADMIN限定にすると `canWrite` とは別の判定が必要になり、権限設計が複雑になるためである。誤操作は権限ではなく、確認画面での変更前後の並記（§6.3.1）で防ぐ。

## 4. 画面一覧

| 画面ID   | 画面名         | URL                                                                 | 概要                    |
| ------ | ----------- | ------------------------------------------------------------------- | --------------------- |
| MST-01 | マスタ検索一覧画面   | `/master`                                                           | 検索条件の指定とマスタ一覧の表示      |
| MST-02 | マスタ新規登録画面   | `/master/new`                                                       | 新しいマスタの入力             |
| MST-03 | マスタ確認画面     | `/master/new` または `/master/[masterId]/edit`                         | 新規登録または更新する内容の確認      |
| MST-04 | マスタ詳細画面     | `/master/[masterId]`                                                | 登録済みマスタの詳細表示と削除       |
| MST-05 | マスタ更新画面     | `/master/[masterId]/edit`                                           | マスタ分類・マスタコード・マスタ内容の変更 |
| MST-06 | マスタ分類一覧画面   | `/master/categories`                                                | マスタ分類の一覧表示            |
| MST-07 | マスタ分類詳細画面   | `/master/categories/[categoryId]`                                   | マスタ分類の詳細表示と削除         |
| MST-08 | マスタ分類新規登録画面 | `/master/categories/new`                                            | 新しいマスタ分類の入力           |
| MST-09 | マスタ分類確認画面   | `/master/categories/new` または `/master/categories/[categoryId]/edit` | マスタ分類を登録または更新する内容の確認  |
| MST-10 | マスタ分類更新画面   | `/master/categories/[categoryId]/edit`                              | マスタ分類名の変更             |

MST-03は、新規登録と更新で共通利用する論理画面とする。独立した画面ルートは作成せず、新規登録の場合はMST-02、更新の場合はMST-05のコンポーネントを確認状態へ切り替えて表示する。入力値をURLへ含めないことで、入力値がブラウザー履歴やアクセスログへ残ることを防ぐ。

MST-09も同様に、マスタ分類の新規登録と更新で共通利用する論理画面とし、独立した画面ルートは作成しない。

**マスタコードと所属マスタ分類の変更に専用の画面は設けず、マスタ更新画面（MST-05）で行う。** 当初はマスタ内容の更新と分けることを検討したが、確認画面（MST-03）が変更前後を並べて表示し、変わらない項目に「変更なし」を併記する仕様であるため、内容を直すつもりでコードを書き換える誤操作はその時点で気づける。画面を割いてまで二重に防ぐ必要はないと判断した。

マスタ更新画面（MST-05）とマスタ分類更新画面（MST-10）は対象が異なる。前者は個々のマスタの所属分類とコードを変更し、後者はマスタ分類そのものの名称を変更する。**あるマスタを別の分類へ移す操作は、分類側ではなくマスタ側（MST-05）で行う。**

削除の確認は独立した画面を設けず、MST-04およびMST-07の上に表示する確認ダイアログで行う。ダイアログの仕様はそれぞれ §6.6 と §6.8 に記す。

削除ボタンは一覧画面（MST-01・MST-06）には配置せず、**詳細画面（MST-04・MST-07）だけに配置する**。削除の前に必ず対象の詳細を開く導線となり、一覧上の誤操作を防ぐ。「更新する」ボタンも同じ理由で詳細画面だけに配置する。

```text

  │         │                   ├─「実行」→ マスタ詳細画面
  │         │                   └─「入力内容を修正」→ マスタ新規登録画面
  │         └─「キャンセル」→ マスタ検索一覧画面
  │
  ├─ 一覧の「詳細」
  │    └─ マスタ詳細画面
  │         ├─「更新する」→ マスタ更新画面
  │         │                 ├─「確認する」→ マスタ確認画面（更新モード）
  │         │                 │                   ├─「実行」→ マスタ詳細画面
  │         │                 │                   └─「入力内容を修正」→ マスタ更新画面
  │         │                 └─「キャンセル」→ マスタ詳細画面
  │         └─「削除」→ マスタ削除確認ダイアログ
  │                        ├─「削除する」→ マスタ検索一覧画面（削除完了メッセージ）
  │                        └─「キャンセル」→ マスタ詳細画面（ダイアログを閉じる）
  │
  └─「マスタ分類の管理」
       └─ マスタ分類一覧画面
            ├─「新規登録」
            │    └─ マスタ分類新規登録画面
            │         ├─「確認する」→ マスタ分類確認画面（新規登録モード）
            │         │                   ├─「実行」→ マスタ分類詳細画面
            │         │                   └─「入力内容を修正」→ マスタ分類新規登録画面
            │         └─「キャンセル」→ マスタ分類一覧画面
            ├─ 一覧の「詳細」
            │    └─ マスタ分類詳細画面
            │         ├─「更新する」→ マスタ分類更新画面
            │         │                 ├─「確認する」→ マスタ分類確認画面（更新モード）
            │         │                 │                   ├─「実行」→ マスタ分類詳細画面
            │         │                 │                   └─「入力内容を修正」→ マスタ分類更新画面
            │         │                 └─「キャンセル」→ マスタ分類詳細画面
```

一覧画面から遷移する際は、検索条件とページ番号を戻り先情報として引き継ぐ。詳細画面の「一覧へ戻る」および新規登録画面の「キャンセル」では、元の検索条件を復元した一覧画面へ戻る。削除実行後も同様に、元の検索条件を復元した一覧画面へ戻る。

マスタ分類一覧画面（MST-06）には検索条件が無いため、引き継ぐのはページ番号だけとする。

## 6. 画面設計

### 6.1 マスタ検索一覧画面（MST-01）

#### 6.1.1 画面イメージ

- 初期表示・検索条件展開時: [master_search_list_open.png](../04_screens/master_search_list_open.png)
- 検索条件折りたたみ時: [master_search_list_close.png](../04_screens/master_search_list_close.png)

検索条件は初期表示時に展開する。利用者は検索条件の見出し右端にある開閉ボタンを押すことで、検索条件を展開または折りたたむことができる。

#### 6.1.2 検索条件の開閉

| 状態      | 表示内容                                            | 開閉ボタン         |
| ------- | ----------------------------------------------- | ------------- |
| 展開状態    | 見出し「検索条件」、マスタ分類、マスタ文字列、「検索」ボタン、「条件をクリア」ボタン      | 上向きシェブロンを表示する |
| 折りたたみ状態 | 見出し「検索条件」だけを表示し、検索項目、入力中の検索条件概要および検索操作ボタンは表示しない | 下向きシェブロンを表示する |

開閉仕様は以下とする。

- 画面を最初に表示した時点では展開状態とする。
- 開閉操作は表示領域を切り替えるだけとし、入力済みのマスタ分類とマスタ文字列は消去しない。
- 折りたたみ状態から再び展開した場合は、折りたたむ前の入力値を復元して表示する。
- 開閉状態は検索条件およびURLクエリには含めない。
- ブラウザーで画面を再読み込みした場合は、初期状態である展開状態へ戻す。
- 「検索条件」の文字は、展開状態と折りたたみ状態で同じフォントサイズ、太さ、色および左位置を使用する。
- 「検索条件」の左側にはアイコンを表示しない。
- 開閉ボタンはアイコンだけのボタンとし、展開状態では `aria-label="検索条件を閉じる"`、折りたたみ状態では `aria-label="検索条件を開く"` を設定する。
- 開閉ボタンに `aria-expanded` と `aria-controls` を設定し、制御対象となる検索条件領域との関係を支援技術へ伝える。
- 開閉ボタンはTabキーでフォーカスでき、EnterキーまたはSpaceキーで操作できるようにする。

#### 6.1.3 検索条件

| 項目     | UI部品     | 必須  | 説明                                   |
| ------ | -------- |:---:| ------------------------------------ |
| マスタ分類  | プルダウン    | 任意  | 登録済みのマスタ分類から1件を選択する。未選択の場合は全分類を対象とする |
| マスタ文字列 | テキストボックス | 任意  | マスタコードまたはマスタ内容を検索する                  |

検索条件はURLクエリとして保持する。

```text
/master?categoryId={マスタ分類ID}&keyword={検索文字列}&page={ページ番号}
```

#### 6.1.4 検索仕様

- マスタ分類が指定された場合は、指定された分類に属するマスタだけを対象とする。
- マスタ文字列の前後にある空白は検索前に除去する。
- マスタ文字列は、マスタコードまたはマスタ内容のいずれかに一致した場合に検索結果へ含める。
- マスタコードとマスタ内容のどちらに対しても、大文字・小文字を区別しない部分一致検索を行う。
- 部分一致は、検索対象文字列の先頭、途中、末尾のいずれに検索文字列が存在する場合も一致とする。
- マスタ分類とマスタ文字列の両方が指定された場合はAND条件とする。
- 検索条件がすべて未指定の場合は、すべてのマスタを対象とする。
- 検索条件を変更して検索した場合、ページ番号を1へ戻す。

PostgreSQLでは、マスタコードとマスタ内容に対して大文字・小文字を区別しない `contains` 条件を使用する。

#### 6.1.5 ボタン

| ボタン      | 動作                                   |
| -------- | ------------------------------------ |
| 検索       | 入力された検索条件で検索し、ページ番号を1へ戻す             |
| 条件をクリア   | 検索条件とページ番号を削除し、全件検索へ戻す               |
| 検索条件の開閉  | 検索条件領域の展開状態と折りたたみ状態を切り替える            |
| 新規登録     | マスタ新規登録画面へ遷移する。ADMINとOPERATORだけに表示する |
| マスタ分類の管理 | マスタ分類一覧画面（MST-06）へ遷移する。全ロールに表示する     |
| CSVダウンロード | 現在の検索条件に一致する全件をCSVでダウンロードする。全ロールに表示する → §13 |

「新規登録」ボタンは一覧領域の右上に配置する。「マスタ分類の管理」ボタンと「CSVダウンロード」ボタンはその左隣に並べ、補助的な操作であることが分かるよう `variant="outline"` とする。

マスタ分類一覧画面への導線はこのボタンだけとし、サイドバーのナビゲーション（`@/shared/layout/nav-config`）には追加しない。マスタ分類はマスタ機能に付随する管理対象であり、独立した業務メニューとして扱わない。

#### 6.1.6 一覧

| 列      | 表示内容                |
| ------ | ------------------- |
| マスタ分類  | マスタ分類名              |
| マスタコード | マスタコード              |
| マスタ内容  | マスタ内容               |
| 操作     | マスタ詳細画面へ遷移する「詳細」リンク |

一覧仕様は以下とする。

- サーバー側で検索、並び替えおよびページングを行う。
- 1ページの表示件数は既存の `env.PAGE_SIZE` を使用する。
- 並び順は、マスタ分類名の昇順、マスタコードの昇順とする。**この並び順は固定とし、利用者が変更する手段は設けない**（§14.1）。
- 一覧の上部に検索結果の総件数と現在のページを表示する。
- 検索結果が0件の場合は「該当するマスタがありません」と表示する。
- 一覧は `@/shared/ui/table` のTableコンポーネントを使用する。

### 6.2 マスタ新規登録画面（MST-02）

#### 6.2.1 入力項目

| 項目     | UI部品     | 必須  | 入力仕様                                   |
| ------ | -------- |:---:| -------------------------------------- |
| マスタ分類  | プルダウン    | 必須  | 登録済みのマスタ分類から1件を選択する                    |
| マスタコード | テキストボックス | 必須  | 1文字以上8文字以内。英大文字、数字、ハイフン、アンダースコアだけを許可する |
| マスタ内容  | テキストボックス | 必須  | 1文字以上30文字以内                            |

**この画面から新しいマスタ分類を登録することはできない。** プルダウンには登録済みのマスタ分類だけを表示し、マスタ分類コードの昇順で並べる。初期状態は未選択とし、利用者に明示的な選択を求める。

登録済みのマスタ分類が0件の場合は、プルダウンの代わりに「マスタ分類が登録されていません。先にマスタ分類を登録してください。」と表示し、マスタ分類新規登録画面（MST-08）へのリンクを置く。この状態では「確認する」ボタンを無効化する。

マスタコードの許可形式は以下の正規表現で表す。

```text
^[A-Z0-9_-]{1,8}$
```

英小文字が入力された場合に自動で英大文字へ変換せず、入力エラーとして表示する。これにより、利用者が入力した値と実際に登録される値が意図せず変わることを防ぐ。

#### 6.2.2 ボタン

| ボタン   | 動作                                                 |
| ----- | -------------------------------------------------- |
| 確認する  | 入力内容を検証し、問題がなければマスタ確認画面へ新規登録モードで進む。データベースへの登録は行わない |
| キャンセル | 入力内容を破棄し、元の検索条件を復元したマスタ検索一覧画面へ戻る                   |

「確認する」時点で、選択されたマスタ分類内に同じマスタコードが登録されていないか確認する。

### 6.3 マスタ確認画面（MST-03）

マスタ確認画面は、新規登録と更新で同じレイアウトを使用する。画面内部に「新規登録」と「更新」の処理モードを持ち、処理モードに応じて表示項目、実行するServer Actionおよび戻り先を切り替える。

#### 6.3.1 表示項目

| 項目         | 新規登録モード    | 更新モード      |
| ---------- | ---------- | ---------- |
| 処理内容       | 新規登録       | 更新         |
| 現在のマスタ分類   | 表示しない      | 変更前のマスタ分類名 |
| 登録・更新後の分類  | 選択したマスタ分類名 | 変更後のマスタ分類名 |
| 現在のマスタコード  | 表示しない      | 変更前のマスタコード |
| 登録・更新後のコード | 入力したマスタコード | 変更後のマスタコード |
| 現在のマスタ内容   | 表示しない      | 変更前のマスタ内容  |
| 登録・更新後の内容  | 入力したマスタ内容  | 変更後のマスタ内容  |

処理内容を見出しおよび表示項目として明示し、利用者が新規登録と更新のどちらを実行しようとしているかを判別できるようにする。

**更新モードでは3項目すべてについて現在値と変更後の値を並べ、変更前と変更後で値が同じ項目には「変更なし」と併記する。** マスタ更新画面（MST-05）ではマスタ分類・マスタコード・マスタ内容のいずれも変更できるため、実際に変わる項目をここで目視できることが、誤操作を防ぐ唯一の砦となる。

#### 6.3.2 ボタン

| ボタン     | 新規登録モード                             | 更新モード                                          |
| ------- | ----------------------------------- | ---------------------------------------------- |
| 実行      | 入力内容を再検証し、登録用Server Actionでマスタを登録する | 入力内容・重複・同時更新の有無を再検証し、更新用Server Actionでマスタを更新する |
| 入力内容を修正 | 入力値を保持したままマスタ新規登録画面へ戻る              | 入力値を保持したままマスタ更新画面へ戻る                           |
| キャンセル   | 入力内容を破棄し、元の検索条件を復元したマスタ検索一覧画面へ戻る    | 入力内容を破棄し、対象マスタの詳細画面へ戻る                         |

画面レイアウトとボタンコンポーネントは共通化するが、新規登録と更新では入力検証、権限確認およびデータベース処理が異なるため、実行するServer Actionは分離する。

#### 6.3.3 新規登録モードの実行処理

1. 入力値をサーバー側で再検証する。
2. 選択されたマスタ分類が現在も存在することを確認する。
3. 同じマスタ分類内に同じマスタコードが存在しないことを確認する。
4. マスタを登録する。`createdBy` と `updatedBy` に実行した利用者のユーザーIDを設定する。
5. 登録したマスタの詳細画面へ遷移し、登録完了メッセージを表示する。

マスタ分類はこの画面では登録しないため、登録処理はマスタ1行の挿入だけとなる。複数テーブルにまたがる更新が無いため、明示的なトランザクションは不要である。

確認画面の表示後に別の利用者が同じマスタコードを登録する可能性があるため、確認画面への遷移時だけでなく、「実行」時にも重複を検査する。最終的な重複防止はデータベースの複合一意制約で保証する。

同じく、確認画面の表示後に別の利用者が選択中のマスタ分類を削除する可能性があるため、「実行」時にも分類の存在を確認する。最終的には `Master.categoryId` の外部キー制約が保証し、制約違反は `MASTER_CATEGORY_NOT_FOUND` へ変換する。

#### 6.3.4 更新モードの実行処理

1. 対象マスタが現在も存在することを確認する。
2. 変更後のマスタ分類ID・マスタコード・マスタ内容をサーバー側で再検証する。
3. 入力画面を表示した時点の `updatedAt` と、データベースに保存されている現在の `updatedAt` を比較する。
4. 変更後のマスタ分類が現在も存在することを確認する。
5. 変更後のマスタ分類内に、変更後のマスタコードを持つ**別の**マスタが存在しないことを確認する。対象マスタ自身は重複判定から除外する。
6. `categoryId`・マスタコード・マスタ内容を更新し、`updatedBy` に実行した利用者のユーザーIDを設定する。`createdBy` は変更しない。
7. 対象マスタの詳細画面へ遷移し、更新完了メッセージを表示する。

`updatedAt` が一致しない場合は更新せず、同時更新エラーを表示する。重複した場合は `MASTER_CODE_CONFLICT` を表示する。

3項目は同じ実行でまとめて更新する。一部だけを変更した場合も、残りは変更前の値のまま同じ処理を通る。項目ごとにServer Actionを分けることはしない。

変更前と変更後の値が完全に同じ場合も実行を許可し、`updatedAt` と `updatedBy` だけが更新される。「変更が無い場合は実行させない」という規則を設けると、確認画面が実行可否の判定を持つことになり、仕様が複雑になるためである。

### 6.5 マスタ更新画面（MST-05）

#### 6.5.1 表示・入力項目

| 項目     | UI部品     | 編集可否 | 入力仕様                                  |
| ------ | -------- |:----:| ------------------------------------- |
| マスタ分類  | プルダウン    | 可    | 必須。登録済みのマスタ分類から1件を選択する。初期値は現在の所属マスタ分類 |
| マスタコード | テキストボックス | 可    | 必須。§7.2 と同じ。初期値は現在のマスタコード             |
| マスタ内容  | テキストボックス | 可    | 必須。1文字以上30文字以内。初期値は現在のマスタ内容           |

**この画面では3項目すべてを変更できる。** マスタ分類を変更すればマスタは別の分類へ移り、マスタコードを変更すれば業務コードが付け替わる。`updatedAt` と `updatedBy` はシステムが設定する。

- マスタ分類のプルダウンは、マスタ新規登録画面（MST-02）と同じく登録済みの分類だけをマスタ分類コードの昇順で表示する。**この画面からも新しいマスタ分類は登録できない。**
- 3項目は同時に変更できる。変更しない項目は現在値が初期表示されているため、触らずに済む。
- マスタ分類名そのものを変更したい場合は、この画面ではなくマスタ分類更新画面（§6.11）を使用する。

#### 6.5.2 変更の影響についての表示

入力欄の上に、以下の固定文言を表示する。

```text
マスタコードと所属マスタ分類を変更しても、このマスタを参照している画面の表示先は変わりません。
変更後のマスタコードは、変更後のマスタ分類の中で重複しない値である必要があります。
```

参照側はマスタIDを保持し、マスタコードでは参照しない（§8.4）。したがってコードを変更しても参照は追随して有効なままである。利用者がこれを不安に感じて変更をためらわないよう、画面上で明示する。

#### 6.5.3 ボタン

| ボタン   | 動作                                              |
| ----- | ----------------------------------------------- |
| 確認する  | 入力内容を検証し、問題がなければマスタ確認画面へ更新モードで進む。データベースの更新は行わない |
| キャンセル | 入力内容を破棄し、対象マスタの詳細画面へ戻る                          |

「確認する」時点で、変更後のマスタ分類内に変更後のマスタコードを持つ**別の**マスタが存在しないか確認する。対象マスタ自身は重複判定から除外する。これにより、マスタ分類だけを変更してマスタコードは据え置く、という操作が自分自身との重複で弾かれることを防ぐ。

#### 6.5.4 所属マスタ分類を変更した後の旧分類

マスタを別の分類へ移した結果、移動元のマスタ分類に属するマスタが0件になっても、**そのマスタ分類を自動的に削除しない**。空になった分類が不要であれば、マスタ分類詳細画面（MST-07）から明示的に削除する。

削除は利用者が明示的に指示したときだけ行うという方針（§6.6）を、ここでも崩さない。

### 6.6 マスタ削除確認ダイアログ

マスタ詳細画面（MST-04）の「削除」ボタンを押したときに表示する確認ダイアログ。独立した画面ルートは作成せず、詳細画面の上に重ねて表示する。

#### 6.6.1 表示項目

| 項目     | 表示内容             |
| ------ | ---------------- |
| 見出し    | 「マスタを削除しますか？」    |
| マスタ分類  | 削除対象のマスタ分類名      |
| マスタコード | 削除対象のマスタコード      |
| マスタ内容  | 削除対象のマスタ内容       |
| 警告     | 後述の固定文言          |
| ボタン    | 「キャンセル」および「削除する」 |

警告として、以下の固定文言を表示する。マスタが利用されているかどうかの判定は行わないため、条件による出し分けはしない。

```text
削除したマスタは元に戻せません。
このマスタを参照している画面では「未設定」として表示されます。
```

#### 6.6.2 ダイアログの仕様

- shadcn/ui の `AlertDialog` を使用する（`DESIGN.md` §3「破壊的確認」）。本テンプレートには未導入のため、実装時に `pnpm dlx shadcn@latest add alert-dialog` で追加する。
- 「削除する」ボタンは `variant="destructive"` とする。
- 警告は色だけで伝えず、アイコンと文言を併用する（`DESIGN.md` §5）。
- ダイアログを開く際にサーバーへ問い合わせない。表示に必要な値はすべて詳細画面が保持しているものを使用する。
- 削除処理の実行中は「削除する」ボタンを無効化し、二重送信を防止する。処理中はダイアログを閉じられないようにする。
- 初期フォーカスは「キャンセル」ボタンに置き、Escapeキーで閉じられるようにする。

#### 6.6.3 削除の実行処理

1. Server Actionで書き込み権限を検証する。
2. 対象マスタが現在も存在することを確認する。
3. 詳細画面を表示した時点の `updatedAt` と、データベースに保存されている現在の `updatedAt` を比較する。
4. 一致する場合、対象マスタを物理削除する。
5. 元の検索条件を復元したマスタ検索一覧画面へ遷移し、削除完了メッセージを表示する。

検証の順序は上記のとおりとし、権限 → 存在 → 同時更新の順に判定する。

#### 6.6.4 削除完了メッセージ

削除後は対象の詳細画面が存在しなくなるため、マスタ検索一覧画面へリダイレクトしたうえで完了メッセージを表示する。リダイレクト先のURLへ一時的なクエリを付与し、一覧画面側がそれを検出してトースト（`@/shared/ui/toaster`）を表示する。

```text
/master?categoryId={マスタ分類ID}&keyword={検索文字列}&page={ページ番号}&deleted=1
```

- メッセージは「削除しました」とする（`MESSAGES.common.deleted`）。
- `deleted` は表示制御専用のクエリであり、検索条件には含めない。検索や「条件をクリア」の操作では引き継がない。

#### 6.8.2 ボタン

#### 6.8.3 削除条件

マスタ分類は、**そのマスタ分類に属するマスタが1件も存在しない場合にだけ**削除できる。

- 配下のマスタを一括削除する方式は採用しない。
- 配下にマスタが存在する場合は、先に個々のマスタを削除する必要がある。

配下にマスタが存在する場合、「削除」ボタンは表示するが、押下時に削除できない旨のエラーメッセージ（`MASTER_CATEGORY_HAS_MASTERS`）を表示する。件数は §6.8.1 に表示されているため、利用者は事前に削除可否を把握できる。

#### 6.8.4 マスタ分類削除確認ダイアログ

| 項目       | 表示内容                 |
| -------- | -------------------- |
| 見出し      | 「マスタ分類を削除しますか？」      |
| マスタ分類コード | 削除対象のマスタ分類コード        |
| マスタ分類名   | 削除対象のマスタ分類名          |
| 警告       | 「削除したマスタ分類は元に戻せません。」 |
| ボタン      | 「キャンセル」および「削除する」     |

ダイアログの実装仕様（`AlertDialog` の使用、二重送信防止、フォーカス制御）は §6.6.2 と同一とする。

#### 6.8.5 削除の実行処理

1. Server Actionで書き込み権限を検証する。
2. 対象マスタ分類が現在も存在することを確認する。
3. 詳細画面を表示した時点の `updatedAt` と、データベースに保存されている現在の `updatedAt` を比較する。
4. 対象マスタ分類に属するマスタが0件であることを確認する。
5. 対象マスタ分類を物理削除する。
6. マスタ分類一覧画面へ遷移し、削除完了メッセージを表示する。

配下マスタの件数確認と削除は、同じデータベーストランザクション内で行う。ただしPostgreSQLの既定の分離レベル（READ COMMITTED）では、件数確認から削除までの間に別の利用者が同じマスタ分類へマスタを登録する可能性を排除できない。

配下にマスタが残ったまま分類が削除されないことは、最終的には `Master.categoryId` の外部キー制約が保証する。マスタ分類の削除で外部キー制約違反が発生した場合は業務エラーへ変換し、`MASTER_CATEGORY_HAS_MASTERS` として扱う。アプリケーションによる件数確認は、利用者へ件数を伝えるための事前確認と位置づける（§9.1 の登録時の重複と同じ考え方）。

削除完了メッセージの表示方法は §6.6.4 と同じとし、リダイレクト先を `/master/categories?deleted=1` とする。

#### 6.10.1 表示項目

| 項目         | 新規登録モード | 更新モード          |

| 処理内容       | 新規登録    | 更新             |
| マスタ分類コード   | 表示しない   | 対象のマスタ分類コード    |
| 現在のマスタ分類名  | 表示しない   | 更新前のマスタ分類名     |
| 登録・更新後の分類名 | 入力した分類名 | 更新後のマスタ分類名     |
| 登録マスタ件数    | 表示しない   | その分類に属するマスタの件数 |

新規登録モードではマスタ分類コードがまだ採番されていないため表示しない。更新モードでは登録マスタ件数を表示し、影響範囲の大きさを実行前に把握できるようにする。

#### 6.10.2 ボタン

| ボタン     | 新規登録モード                               | 更新モード                                          |
| ------- | ------------------------------------- | ---------------------------------------------- |
| 実行      | 入力内容を再検証し、登録用Server Actionでマスタ分類を登録する | 入力内容と同時更新の有無を再検証し、更新用Server Actionでマスタ分類名を更新する |
| 入力内容を修正 | 入力値を保持したままマスタ分類新規登録画面へ戻る              | 入力値を保持したままマスタ分類更新画面へ戻る                         |
| キャンセル   | 入力内容を破棄し、マスタ分類一覧画面へ戻る                 | 入力内容を破棄し、対象マスタ分類の詳細画面へ戻る                       |

#### 6.10.3 新規登録モードの実行処理

1. 入力値をサーバー側で再検証する。
2. 同じ名称のマスタ分類が存在しないことを確認する。
3. マスタ分類を登録する。`createdBy` と `updatedBy` に実行した利用者のユーザーIDを設定する。
4. 登録したマスタ分類の詳細画面へ遷移し、登録完了メッセージを表示する。

確認画面の表示後に別の利用者が同じ名称を登録する可能性があるため、「実行」時にも重複を検査する。最終的な重複防止は `MasterCategory.name` の一意制約で保証し、制約違反は `MASTER_CATEGORY_CONFLICT` へ変換する。

#### 6.10.4 更新モードの実行処理

1. 対象マスタ分類が現在も存在することを確認する。
2. 更新後のマスタ分類名をサーバー側で再検証する。
3. 入力画面を表示した時点の `updatedAt` と、データベースに保存されている現在の `updatedAt` を比較する。
4. 更新後の名称を持つ**別の**マスタ分類が存在しないことを確認する。対象マスタ分類自身は重複判定から除外する。
5. マスタ分類名を更新し、`updatedBy` に実行した利用者のユーザーIDを設定する。`createdBy` は変更しない。
6. 対象マスタ分類の詳細画面へ遷移し、更新完了メッセージを表示する。

`updatedAt` が一致しない場合は更新せず、同時更新エラーを表示する。

マスタ分類名は表示専用の値であり、マスタとの関連は `Master.categoryId` が保持している。したがって分類名を変更しても、その分類に属するマスタとの関連は影響を受けない。ただしマスタ検索一覧画面（MST-01）の並び順はマスタ分類名の昇順であるため（§6.1.6）、名称の変更によって一覧の並び順が変わる。

### 6.11 マスタ分類更新画面（MST-10）

マスタ分類詳細画面（MST-07）の「更新する」ボタンから遷移する。この画面が変更するのは**マスタ分類そのものの名称**であり、個々のマスタの所属分類ではない。所属分類の変更はマスタ更新画面（§6.5）で行う。

#### 6.11.1 表示・入力項目

| 項目       | UI部品     | 編集可否 | 入力仕様                      |
| -------- | -------- |:----:| ------------------------- |
| マスタ分類コード | テキスト表示   | 不可   | 対象のマスタ分類コードを表示する          |
| マスタ分類名   | テキストボックス | 可    | 必須。1文字以上30文字以内。初期値は現在の分類名 |
| 登録マスタ件数  | テキスト表示   | 不可   | その分類に属するマスタの件数を表示する       |

マスタ分類コードは `MasterCategory.id` に由来するため変更できない。この画面で更新できる項目はマスタ分類名だけとする。

#### 6.11.2 ボタン

| ボタン   | 動作                                                |
| ----- | ------------------------------------------------- |
| 確認する  | 入力内容を検証し、問題がなければマスタ分類確認画面へ更新モードで進む。データベースの更新は行わない |
| キャンセル | 入力内容を破棄し、対象マスタ分類の詳細画面へ戻る                          |

## 7. 入力検証

### 7.1 マスタ分類の選択（MST-02・MST-05）

- マスタ分類IDを必須とする。
- 指定されたマスタ分類IDが登録済みのマスタ分類に存在することを検証する。
- 新しいマスタ分類名の入力欄はこれらの画面に存在しないため、リクエストに含まれていても無視する。

### 7.2 マスタコード

- 必須とする。
- 前後にある空白は検証前に除去する。
- 1文字以上8文字以内とする。
- 使用可能文字は英大文字 `A-Z`、数字 `0-9`、ハイフン `-`、アンダースコア `_` とする。
- 英小文字、空白、日本語および上記以外の記号は許可しない。
- 同じマスタ分類内で重複を許可しない。
- 異なるマスタ分類では同じマスタコードを登録できる。
- 確認画面への遷移時と「実行」時の両方で重複を確認する。
- 更新（MST-05）の場合、重複判定から対象マスタ自身を除外する。

### 7.3 マスタ内容

- 必須とする。
- 前後にある空白は検証前に除去する。
- 1文字以上30文字以内とする。
- 文字数はUnicodeコードポイント単位で数える。

### 7.4 マスタ分類名（MST-08・MST-10）

- 必須とする。
- 前後にある空白は検証前に除去する。
- 1文字以上30文字以内とする。
- 文字数はUnicodeコードポイント単位で数える。
- 使用可能文字は制限しない。日本語を含む任意の文字を許可する。
- システム全体で重複を許可しない。
- 確認画面への遷移時と「実行」時の両方で重複を確認する。
- 更新（MST-10）の場合、重複判定から対象マスタ分類自身を除外する。

## 8. データベース設計

### 8.1 ER概要

```text
MasterCategory 1 ───── N Master

MasterExport（関連を持たない独立したテーブル。§13.6）
```

マスタ分類とマスタを別テーブルで管理する。マスタ分類自体を通常のマスタデータとして扱わないため、分類がどの分類に属するかという自己参照上の曖昧さを持たない。

### 8.2 Prismaモデル案

```prisma
model MasterCategory {
  id        Int      @id @default(autoincrement())
  name      String   @unique @db.VarChar(30)
  createdAt DateTime @default(now())
  createdBy String? // 登録した利用者の User.id（FK は張らない）
  updatedAt DateTime @updatedAt
  updatedBy String? // 最後に更新した利用者の User.id（FK は張らない）

  masters Master[]
}

model Master {
  id         Int            @id @default(autoincrement())
  categoryId Int
  category   MasterCategory @relation(fields: [categoryId], references: [id])
  code       String         @db.VarChar(8)
  content    String         @db.VarChar(30)
  createdAt  DateTime       @default(now())
  createdBy  String?
  updatedAt  DateTime       @updatedAt
  updatedBy  String?

  @@unique([categoryId, code])
  @@index([categoryId])
}
```

`MasterCategory.id` と `Master.id` は、PostgreSQLのシーケンスを利用して1から昇順に自動採番する。アプリケーション側では主キーの値を指定せず、データベースに採番を任せる。

`createdBy` と `updatedBy` には、登録・更新を実行した利用者の `User.id` を保持する。外部キー制約は設定しない。これらは操作の記録であり、利用者が削除された後も記録として残す必要があるためである。Server Actionが現在の利用者を取得してサービス層へ渡し、リポジトリが書き込む。値を特定できない場合は `null` とする。

削除を表すカラム（`deleted` / `deletedAt` / `deletedBy`）は持たない。削除は物理削除であり、行そのものが消えるためである。

利用者の操作で更新できるカラムは以下のとおりである。モデル定義は変更せず、どの画面がどのカラムを書き換えるかだけが増える。

| カラム                              | 更新できる画面         | 備考               |
| -------------------------------- | --------------- | ---------------- |
| `Master.categoryId`              | MST-05（マスタ更新）   | 所属分類の付け替え        |
| `Master.code`                    | MST-05（マスタ更新）   | 業務コードの付け替え       |
| `Master.content`                 | MST-05（マスタ更新）   | マスタ内容の修正         |
| `MasterCategory.name`            | MST-10（マスタ分類更新） | 表示名の変更           |
| `id` / `createdAt` / `createdBy` | なし              | 登録後は変更しない        |
| `updatedAt` / `updatedBy`        | 上記の各更新に伴い自動設定   | 利用者が直接入力する項目ではない |

`MasterCategory.id` はマスタ分類コードの採番元としても使用する。データベースには `1`、`2` のような整数で保持し、画面では4桁になるようにゼロ埋めして `0001`、`0002` と表示する。`Master.id` は内部識別子とし、利用者がマスタを識別する業務コードには `Master.code` を使用する。

自動採番は一意性と増加順を保証するが、トランザクションのロールバックなどによって欠番が発生する可能性があるため、欠番のない連続番号であることは保証しない。マスタ分類コードについても同様に欠番を許容する。

### 8.3 制約

| 対象           | 制約                |
| ------------ | ----------------- |
| マスタ分類名       | システム全体で一意、最大30文字  |
| マスタコード       | 同じマスタ分類内で一意、最大8文字 |
| マスタ内容        | 最大30文字            |
| マスタとマスタ分類の関係 | 存在するマスタ分類だけを参照可能  |

マスタコードの使用可能文字はZodによるアプリケーション検証で保証する。データベースでも同じ形式を強制する場合は、Prismaスキーマだけでは表現できないため、CHECK制約をマイグレーションへ追加する。

削除は**物理削除**とする。論理削除は採用しない。

論理削除を採用しない理由は、削除したマスタコードおよびマスタ分類名を再び使用できなくなるためである。論理削除では削除済みの行が残り続けるため、一意制約 `@@unique([categoryId, code])` および `MasterCategory.name` の一意制約が削除済みの行に対しても働く。誤って登録したマスタを削除して同じコードで登録し直す、という日常的な操作ができなくなる。未削除の行だけを一意制約の対象とする部分一意インデックスを使えば回避できるが、同じコードを二度削除した場合に削除済みの行同士が衝突するため、一意キーに削除日時を含める設計が必要となり複雑になる。

物理削除の制約は以下のとおりである。

- 削除したマスタおよびマスタ分類は復元できない。復旧手段はデータベースのバックアップからのリストアだけである。
- 「誰が何を削除したか」はデータベースに残らない。アプリケーションログでのみ追跡する（§10）。

### 8.4 マスタを参照するテーブルの扱い

本設計の時点では、マスタを参照するテーブルは存在しない。将来、契約などがマスタを参照するようになった場合の規約を以下に定める。

- 参照側はマスタIDを保持するが、**外部キー制約は設定しない**。
- 参照側は**マスタコードを保持しない**。マスタコードは変更され得る値であり、複製して持つと変更時に食い違うためである。
- マスタの削除時に、参照側のマスタIDを `NULL` へ変更しない。参照IDはそのまま保持する。
- 画面上は、参照先のマスタを取得できた場合はマスタ内容を表示し、取得できなかった場合は「未設定」と表示する。
- マスタの削除時に、参照されているかどうかの判定は行わない。利用中であっても削除できる。
- **マスタコードおよび所属マスタ分類の変更時も、参照されているかどうかの判定は行わない。** 参照はマスタIDで行われ、変更後も同じ行を指し続けるため、参照が壊れることはない。

外部キー制約を設定しないため、参照側には存在しないマスタIDが残る。マスタIDはシーケンスによる単調増加であり、通常の運用で同じIDが再採番されることはない。ただし、データ移行やバックアップからのリストアの手順を誤ってシーケンスを巻き戻した場合、過去に削除したマスタと同じIDを別のマスタが取得し、参照側が意図しない値を指す可能性がある。データ移行時はシーケンスの現在値を必ず引き継ぐこと。

現在の `Contract.status` は文字列であり、マスタを参照していない。マスタ参照へ移行するかどうかは契約機能の設計時に判断する。

## 9. 同時実行制御

### 9.1 登録・変更時の重複

同じマスタ分類内のマスタコードに複合一意制約 `@@unique([categoryId, code])` を、マスタ分類名に一意制約 `@unique` を設定する。

アプリケーションで事前に重複を確認していても、複数の利用者が同時に実行する可能性がある。データベースの一意制約違反が発生した場合は業務エラーへ変換する。

| 操作                | 違反する制約                         | 変換後のエラー                    |
| ----------------- | ------------------------------ | -------------------------- |
| マスタの登録（MST-02）    | `@@unique([categoryId, code])` | `MASTER_CODE_CONFLICT`     |
| マスタの更新（MST-05）    | `@@unique([categoryId, code])` | `MASTER_CODE_CONFLICT`     |
| マスタ分類の登録（MST-08）  | `MasterCategory.name` の一意制約    | `MASTER_CATEGORY_CONFLICT` |
| マスタ分類名の更新（MST-10） | `MasterCategory.name` の一意制約    | `MASTER_CATEGORY_CONFLICT` |

更新（MST-05・MST-10）では、事前の重複確認から対象自身を除外する。除外しないと、値を変えずに実行しただけで自分自身との重複として拒否されてしまう。一意制約は同じ行に対しては働かないため、データベース側での除外は不要である。

### 9.2 更新・変更時の競合

入力画面を表示した時点の `updatedAt` を、実行時に送信する。データベースに保存されている現在の `updatedAt` と一致しない場合は更新せず、以下のメッセージを表示する。

```text
ほかの利用者によって更新されています。最新の内容を確認してから、もう一度操作してください。
```

この楽観的排他制御は、マスタ更新（MST-05）とマスタ分類更新（MST-10）の双方に同じ方式で適用する。

`updatedAt` は行単位で持つため、2人の利用者が同じマスタの別々の項目を変更した場合も検出できる。先に実行した側が成功し、後から実行した側が同時更新エラーとなる。項目単位での併合は行わない。

### 9.3 削除時の競合

削除にも更新と同じ楽観的排他制御を適用する。詳細画面（MST-04・MST-07）を表示した時点の `updatedAt` を、削除実行時に送信する。データベースに保存されている現在の `updatedAt` と一致しない場合は削除せず、§9.2 と同じメッセージを表示する。

削除に楽観的排他制御を適用するのは、詳細画面を開いた後に別の利用者がマスタ内容を変更していた場合、利用者が確認した内容と実際に削除される内容が異なるためである。

検証の順序は次のとおりとする。

| 順序  | 検証内容               | 一致しない場合                                          |
| --- | ------------------ | ------------------------------------------------ |
| 1   | 書き込み権限があるか         | `FORBIDDEN`                                      |
| 2   | 対象が存在するか           | `MASTER_NOT_FOUND` / `MASTER_CATEGORY_NOT_FOUND` |
| 3   | `updatedAt` が一致するか | `MASTER_CONCURRENT_UPDATE`                       |
| 4   | （マスタ分類のみ）配下マスタが0件か | `MASTER_CATEGORY_HAS_MASTERS`                    |

確認ダイアログを表示した後に別の利用者が同じ対象を削除していた場合、対象は既に存在しないため `MASTER_NOT_FOUND` となる。物理削除では「存在しない」と「既に削除された」を区別できないため、両者を同一のエラーとして扱う。

## 10. エラー設計

| エラーコード                        | HTTPステータス | 発生条件                                | 利用者向けメッセージ例                                         |
| ----------------------------- | ---------:| ----------------------------------- | --------------------------------------------------- |
| `VALIDATION_ERROR`            | 422       | 必須、文字数、文字種に違反した                     | 入力内容を確認してください                                       |
| `MASTER_NOT_FOUND`            | 404       | 対象マスタが存在しない（既に削除された場合を含む）           | 対象のマスタが見つかりません                                      |

`MASTER_CATEGORY_HAS_MASTERS` の `context` には配下マスタの件数を含め、利用者向けメッセージに反映する。

### 10.1 削除・変更操作の記録

物理削除では削除された行が残らず、コードや分類名の変更では上書き前の値が残らない。どちらもデータベースには「変更後の姿」しか存在しないため、記録はアプリケーションログでのみ行う。誤って操作した場合に、何を元の値へ戻せばよいかをログから特定できるようにする。

`src/AGENTS.md` の規約により、業務コード（`service.ts` / `repository.ts`）にログを書いてはならない。ログは境界ラッパー `withOp` が処理ごとに一度だけ出力する。`withOp` は操作名・`requestId`・実行者の `userId` に加えて**Server Actionの引数**を出力するため、Server Actionの入力に対象の表示内容と変更前の値を含めることで、仕組みを追加せずに記録を残す。

| 操作                | Server Actionの入力に含める値                                              |
| ----------------- | ------------------------------------------------------------------ |
| マスタの削除            | マスタID、`updatedAt`、マスタ分類名、マスタコード、マスタ内容                              |
| マスタ分類の削除          | マスタ分類ID、`updatedAt`、マスタ分類名                                         |
| マスタの更新（MST-05）    | マスタID、`updatedAt`、変更前のマスタ分類名・マスタコード・マスタ内容、変更後のマスタ分類ID・マスタコード・マスタ内容 |
| マスタ分類名の更新（MST-10） | マスタ分類ID、`updatedAt`、変更前のマスタ分類名、変更後のマスタ分類名                          |

- 変更前の値は確認画面が保持しているものをそのまま送信する。
- **可否判定にこれらの値を使用しない。** 判定に使うのは対象IDと `updatedAt`、および変更後の入力値だけとする（§9.2・§9.3）。
- クライアントから送信される値であるため改ざんされ得るが、対象IDが同じログレコードに記録されるため、突き合わせは可能である。

マスタの更新では、変更されなかった項目についても変更前後の値を送信する。項目ごとに送る・送らないを切り替えると、ログを読む側が「記録が無いのは変更しなかったからか、送り漏れたからか」を判別できなくなるためである。

ログの保持期間を超えると追跡できなくなる点は許容する。**データベース上での変更履歴の保持は採用しない**（§14.1.3）。

CSVダウンロードの記録については §13.11 に記す。

既存のfeature-modular規約に従い、マスタ機能を `src/modules/master` 内で完結させる。

```text
src/modules/master/
├─ actions.ts
├─ service.ts
├─ repository.ts
├─ validation.ts
├─ csv.ts
├─ types.ts
├─ index.ts
└─ ui/
   ├─ master-search-form.tsx
   ├─ master-table.tsx
   ├─ master-create-form.tsx
   ├─ master-confirmation.tsx
   ├─ master-detail.tsx
   ├─ master-update-form.tsx
   ├─ master-delete-dialog.tsx
   ├─ master-export-button.tsx
   ├─ master-category-table.tsx
   ├─ master-category-detail.tsx
   ├─ master-category-create-form.tsx
   ├─ master-category-update-form.tsx
   ├─ master-category-confirmation.tsx
   └─ master-category-delete-dialog.tsx
```

画面ルートは以下とする。

```text
src/app/(main)/master/
├─ page.tsx
├─ new/
│  └─ page.tsx
├─ categories/
│  ├─ page.tsx
│  ├─ new/
│  │  └─ page.tsx
│  └─ [categoryId]/
│     ├─ page.tsx
│     └─ edit/
│        └─ page.tsx
└─ [masterId]/
   ├─ page.tsx
   └─ edit/
      └─ page.tsx
```

CSVダウンロードのRoute Handlerは、画面ルートとは別に以下へ置く（役割は §13.5.3）。

```text
src/app/api/master/exports/
└─ [exportId]/
   ├─ route.ts          # 受け取り（CSV を返す）
   └─ status/
      └─ route.ts       # 状態の問い合わせ
```

CSVの生成はworkerが行うため、キューの購読を [`src/worker/index.ts`](../../../src/worker/index.ts) へ追加する。業務処理はworkerへ書かず、`src/modules/master/service.ts` を呼ぶ（§13.5.2）。

マスタ分類はマスタと同じ境界づけられたコンテキストに属するため、独立したモジュールを作らず `src/modules/master` 内で扱う。

各ファイルの責務は以下とする。

| ファイル              | 責務                                   |
| ----------------- | ------------------------------------ |
| `app/**/page.tsx` | 認証確認、URLパラメーターの取得、サービス呼び出し、UIの組み立て   |
| `actions.ts`      | 書き込み権限確認、入力値の受け取り、Server Actionの処理境界 |
| `service.ts`      | 検索、重複確認、登録・更新ユースケース、トランザクション制御       |
| `repository.ts`   | Prismaを使用したデータベース操作                  |
| `validation.ts`   | Zodを使用した入力値検証                        |
| `csv.ts`          | CSV文字列の組み立て（純粋関数。DBにもリクエストにも依存しない）   |
| `types.ts`        | 一覧、詳細、フォームおよび検索条件の型定義                |
| `index.ts`        | マスタモジュールが外部へ公開するAPI                  |
| `ui/*.tsx`        | 画面表示、フォーム入力、入力状態と確認状態の切り替え           |

`master-confirmation.tsx` は新規登録と更新で共通利用し、処理モードに応じて表示項目、実行するServer Actionおよび戻り先を切り替える。`master-category-confirmation.tsx` はマスタ分類の新規登録と更新で共通利用する。マスタとマスタ分類では表示項目が重ならないため、確認画面のコンポーネントは分ける。

`master-create-form.tsx` と `master-update-form.tsx` は、マスタ分類のプルダウン・マスタコード・マスタ内容という同じ3項目を扱う。**入力欄はひとつの共通コンポーネントとして切り出し、両フォームから使用する。** 違いは初期値の有無、送信先のServer Action、および更新側が `updatedAt` と変更前の値を保持する点だけである。

`master-delete-dialog.tsx` と `master-category-delete-dialog.tsx` は、確認ダイアログの表示と削除用Server Actionの呼び出しを担う。対象の項目が異なるため別ファイルとするが、`AlertDialog` の構造、二重送信の防止および実行中の表示は共通の実装方針（§6.6.2）に従う。

`master-export-button.tsx` は、現在の検索条件を引き継いだダウンロードURLへのリンクを描画する。Server Actionを呼ばないため、状態を持たない表示専用のコンポーネントとする。

`actions.ts` が公開するServer Actionは**8つ**とする。マスタの登録・更新・削除、マスタ分類の登録・更新・削除の6つに加え、CSVダウンロードの依頼が2つ（マスタ・マスタ分類）である。処理ごとに入力・検証・権限確認が異なるため、1つのServer Actionへまとめない。逆に、マスタの更新を項目ごとに分割することもしない（§6.3.4）。

**CSVダウンロードは、依頼だけがServer Actionである。** 生成はworker、受け取りはRoute Handlerが担う（§13.5）。Server Actionはファイルのダウンロードを返せないため、受け取りをServer Actionにはできない。

依存方向は `app → modules/master → shared` とし、Prismaは `repository.ts` 以外から直接使用しない。データベースへアクセスするファイルには `server-only` を適用する。

## 12. テスト方針

テストは対象ファイルの隣へコロケーションし、以下を確認する。

### 12.1 検索

- マスタ分類だけで検索できる。
- マスタコードに対して、大文字・小文字を区別しない部分一致検索ができる。
- マスタ内容に対して、大文字・小文字を区別しない部分一致検索ができる。
- マスタコードまたはマスタ内容のOR条件で検索される。
- マスタ分類とマスタ文字列のAND条件で検索される。
- 検索条件を指定しない場合に全件が対象になる。
- 検索結果が規定件数でページングされる。
- マスタ分類名、マスタコードの順に並ぶ。
- 初期表示では検索条件領域が展開されている。
- 展開状態の開閉ボタンを操作すると、検索項目と検索操作ボタンが非表示になり、下向きシェブロンへ切り替わる。
- 折りたたみ状態では、入力中の検索条件概要が表示されない。
- 折りたたみ状態の開閉ボタンを操作すると、検索項目と検索操作ボタンが再表示され、上向きシェブロンへ切り替わる。
- 検索条件を折りたたんでから再展開しても、入力済みのマスタ分類とマスタ文字列が保持される。
- 展開状態と折りたたみ状態で「検索条件」の文字サイズ、太さ、色および左位置が変わらず、左側にアイコンが表示されない。
- 開閉ボタンをTabキーで選択し、EnterキーまたはSpaceキーで開閉できる。
- 開閉状態に応じて、開閉ボタンの `aria-label` と `aria-expanded` が正しく切り替わる。

### 12.2 登録

- 登録済みマスタ分類を選択して登録できる。
- マスタ分類が未選択の場合は拒否する。
- 存在しないマスタ分類IDを指定した場合は `MASTER_CATEGORY_NOT_FOUND` となる。
- 登録済みのマスタ分類が0件の場合、「確認する」ボタンが無効化され、マスタ分類の登録を促す案内が表示される。
- マスタコードが8文字の場合は登録でき、9文字の場合は拒否する。
- マスタコードに英小文字、日本語、空白または許可されていない記号が含まれる場合は拒否する。
- 同じマスタ分類内のマスタコード重複を拒否する。
- 異なるマスタ分類では同じマスタコードを登録できる。
- マスタ内容が30文字の場合は登録でき、31文字の場合は拒否する。
- 確認画面を表示しただけではデータベースへ登録されない。

### 12.3 更新

- マスタ内容だけを更新できる。
- マスタコードだけを更新できる。
- 所属マスタ分類だけを更新できる。
- 3項目を同時に更新できる。
- 変更後のマスタコードが §7.2 の形式に違反する場合は拒否する。
- 変更後のマスタ分類が存在しない場合は `MASTER_CATEGORY_NOT_FOUND` となる。
- 変更後のマスタ分類に同じマスタコードの別のマスタが存在する場合は `MASTER_CODE_CONFLICT` となる。
- **値を変えずに実行した場合、自分自身との重複で拒否されない。**
- 所属分類だけを変更し、マスタコードは変更前と同じ値のままでも、移動先に同じコードが無ければ成功する。
- 変更前のマスタコードは、更新後ただちに同じマスタ分類で再利用できる。
- 存在しないマスタの更新を拒否する。
- `updatedAt` が異なる場合に同時更新エラーとなる。
- 更新で `updatedBy` だけが更新され、`createdBy` は変わらない。
- 更新処理で、変更前のマスタ分類名・マスタコード・マスタ内容がログへ渡される。
- 所属分類を移した結果、移動元の分類に属するマスタが0件になっても、その分類は削除されない。
- 確認画面を表示しただけではデータベースが更新されない。

### 12.4 確認画面

- 新規登録と更新で同じ確認画面IDおよび共通コンポーネントが使用される。
- 新規登録モードでは、処理内容、選択したマスタ分類、入力したマスタコードおよびマスタ内容が表示される。
- 更新モードでは、処理内容と、マスタ分類・マスタコード・マスタ内容それぞれの変更前と変更後が表示される。
- 変更前と変更後が同じ項目には「変更なし」が併記される。
- 各モードの「実行」で、そのモードに対応するServer Actionが呼び出される。
- 「入力内容を修正」と「キャンセル」の戻り先が処理モードに応じて切り替わる。

### 12.5 権限

- VIEWERは一覧と詳細を参照できる。
- VIEWERには新規登録、更新および削除ボタンが表示されない。
- VIEWERによるServer Actionの直接実行を、**書き込み系6つ**のServer Actionすべてで拒否する。
- ADMINとOPERATORは登録、更新および削除を実行できる。
- CSVダウンロードの依頼（2つ）は、VIEWERでも拒否されない（§12.8）。

### 12.6 削除

マスタの削除について確認する。

- 存在するマスタを削除できる。
- 削除したマスタは一覧の検索結果に含まれない。
- 削除したマスタの詳細取得が `MASTER_NOT_FOUND` になる。
- 存在しないマスタの削除を拒否する。
- `updatedAt` が異なる場合に同時更新エラーとなる。
- 権限、存在、同時更新の順に検証される。
- 削除したマスタと同じマスタ分類・同じマスタコードで再登録できる。
- 削除処理で削除対象の分類名・コード・内容がログへ渡される。

マスタ分類の削除について確認する。

- 配下にマスタが存在しないマスタ分類を削除できる。
- 配下にマスタが存在する場合は `MASTER_CATEGORY_HAS_MASTERS` となり、件数が `context` に含まれる。
- 存在しないマスタ分類の削除を拒否する。
- `updatedAt` が異なる場合に同時更新エラーとなる。
- 削除したマスタ分類と同じ名称で再登録できる。

登録者・更新者について確認する。

- 登録時に `createdBy` と `updatedBy` へ実行者のユーザーIDが設定される。
- 更新時に `updatedBy` だけが更新され、`createdBy` は変わらない。

### 12.7 マスタ分類の登録と更新

- マスタ分類を登録できる。
- マスタ分類名が30文字の場合は登録でき、31文字の場合は拒否する。
- 前後の空白が除去されてから検証・登録される。
- 同じ名称のマスタ分類の登録を拒否する（`MASTER_CATEGORY_CONFLICT`）。
- マスタ分類名を更新できる。
- 更新後の名称が別のマスタ分類と重複する場合は `MASTER_CATEGORY_CONFLICT` となる。
- **名称を変えずに更新を実行した場合、自分自身との重複で拒否されない。**
- 存在しないマスタ分類の更新を拒否する。
- `updatedAt` が異なる場合に同時更新エラーとなる。
- 分類名を更新しても、その分類に属するマスタの `categoryId` は変わらない。
- 更新で `updatedBy` だけが更新され、`createdBy` は変わらない。
- 更新処理で、変更前のマスタ分類名がログへ渡される。
- マスタ新規登録画面（MST-02）およびマスタ更新画面（MST-05）から、新しいマスタ分類を登録できない。
- マスタ分類名を変更しても、マスタ更新画面（MST-05）で行う所属分類の付け替えとは別の操作として扱われる。

### 12.8 CSVダウンロード

CSV文字列の組み立て（`csv.ts`）は純粋関数であり、テストの費用対効果が高い。次を確認する。

- 先頭にBOM（U+FEFF）が付く。
- ヘッダー行が §13.4.3 および §13.4.4 の列順どおりに出力される。
- 改行コードがCRLFである。
- 値にカンマ・引用符・改行が含まれる場合に引用符で囲まれ、値中の引用符が2つ重ねられる。
- マスタ分類コードが4桁ゼロ埋めで出力される。
- 日時が `YYYY/MM/DD HH:mm:ss` 形式・Asia/Tokyo で出力される。
- `createdBy` / `updatedBy` が `null` の場合は空欄になる（「—」を出さない）。
- 0件の場合もヘッダー行だけのCSVが生成される。

依頼（`service.ts`）について確認する。

- 対象件数が上限と等しい場合は依頼できる。
- 対象件数が上限を1件超えた場合は `MASTER_EXPORT_LIMIT_EXCEEDED` となり、`context` に対象件数と上限が含まれる。ジョブは登録されない。
- 依頼で `MasterExport` が `QUEUED` として作成され、`requestedBy` に実行者のユーザーIDが入る。
- 依頼で検索条件が `MasterExport` へ保存され、ジョブのペイロードには `exportId` だけが積まれる。
- VIEWERが依頼できる（書き込み権限を要求しない）。
- 保持期限を過ぎた過去の `MasterExport` が、依頼時に削除される（§13.9.2）。

生成（worker のハンドラー）について確認する。

- `QUEUED` の依頼を処理すると `READY` になり、`filePath` と `rowCount` が入る。
- `QUEUED` でない依頼を渡された場合は何もしない（多重実行への保険）。
- 存在しない `exportId` を渡された場合は何もしない。
- 生成中に例外が発生した場合は `FAILED` と `errorCode` が記録される。
- 検索条件がCSVの内容へ反映される（マスタ分類・マスタ文字列のAND条件）。
- ページ番号に相当する絞り込みが行われず、条件に一致する全件が出力される。

受け取り（Route Handler）について確認する。

- 未ログインのリクエストが `UNAUTHORIZED` になる。
- 依頼した本人が受け取れる。
- **依頼した本人以外は `MASTER_EXPORT_NOT_FOUND` になる**（403 ではない）。
- 存在しない `exportId` が `MASTER_EXPORT_NOT_FOUND` になる。
- `READY` でない依頼の受け取りが `MASTER_EXPORT_NOT_READY` になる。
- 受け取りに成功すると、ファイルと `MasterExport` の行が削除される。
- ファイルの削除に失敗しても、応答は成功として返る。

## 13. CSVダウンロード

### 13.1 概要

マスタ検索一覧画面（MST-01）とマスタ分類一覧画面（MST-06）から、一覧の内容をCSVファイルとしてダウンロードできる。**出力専用の機能であり、CSVを取り込む手段は設けない**（一括登録・一括更新は §14.2 のとおり対象外）。

新しい画面は追加しない。既存の2画面へボタンが1つずつ増えるだけである。

**CSVの生成はworker（pg-boss）で行う。** 時間がかかる可能性のある処理をworkerへ寄せるという本テンプレートの方針に従い、リクエストの中では生成しない。生成したファイルは既存のファイルストレージ（`@/shared/storage`）へ置き、利用者はアプリケーション経由で受け取る。**本機能が、本テンプレートでworkerを実際に使う最初の機能となる。**

利用者から見た動きは「ボタンを押して待つと、ダウンロードが始まる」だけである。ジョブの一覧やダウンロード履歴の画面は設けない。

### 13.2 ダウンロードの対象

| 起点画面   | 対象                    | 並び順        |
| ------ | --------------------- | ---------- |
| MST-01 | 現在の検索条件に一致するマスタ**全件** | §6.1.6 と同じ |
| MST-06 | マスタ分類の**全件**          | §6.7.1 と同じ |

- 検索条件（`categoryId` / `keyword`）は画面の指定をそのまま適用する。検索仕様は §6.1.4 と同一とする。
- **ページ番号は無視する。** 画面が2ページ目を表示していても、出力されるのは条件に一致する全件である。
- 画面と同じ並び順にすることで、一覧で見えているものとCSVの内容が対応する。

### 13.3 導線とボタン

- 配置は一覧領域の右上とし、MST-01 では「マスタ分類の管理」ボタンの隣、MST-06 では「新規登録」ボタンの隣に置く。
- ラベルは「CSVダウンロード」、`variant="outline"` とする。全ロールに表示する（§3）。
- 次の場合はボタンを無効化する。
  - 対象が0件のとき。無効化に併せて理由を示す。
  - 対象件数が上限を超えるとき（§13.8）。
- ボタンを押してからダウンロードが始まるまでの間、ボタンを処理中の表示へ切り替え、二重に依頼できないようにする。

#### 13.3.1 待機中の表示

| 状態          | ボタンの表示   | 補助表示                                  |
| ----------- | -------- | ------------------------------------- |
| 待機          | CSVダウンロード | 無し                                    |
| 依頼中・生成中     | 作成中...（無効） | 「CSVを作成しています。しばらくお待ちください」            |
| 完了          | CSVダウンロード | ダウンロードが自動的に始まる                        |
| 時間切れ（§13.10） | CSVダウンロード | 「時間がかかっています。しばらくしてからもう一度お試しください」      |
| 失敗          | CSVダウンロード | エラーメッセージ（§10）                          |

進捗率は表示しない。生成の進み具合をworkerから取得する仕組みを持たないためであり、件数の上限（§13.8）がある以上、待ち時間は限定的である。

### 13.4 出力仕様

#### 13.4.1 ファイル形式

| 項目    | 仕様                                                    |
| ----- | ----------------------------------------------------- |
| 文字コード | UTF-8。先頭にBOM（U+FEFF）を付与する                             |
| 区切り文字 | カンマ                                                   |
| 改行コード | CRLF                                                  |
| 引用    | 値にカンマ・引用符・改行のいずれかを含む場合だけ `"` で囲む。値中の `"` は `""` へ置き換える |
| 先頭行   | ヘッダー行（日本語の列名）                                         |
| 生成    | 既存の依存である `papaparse` の `unparse` を使用する                |

BOMを付けるのは、付けない場合にMicrosoft ExcelがUTF-8と判定できず日本語が文字化けするためである。**`iconv-lite` は使用しない。** Shift_JISへ変換する方式では、変換できない文字（一部の漢字・絵文字）の扱いを別途決める必要があり、マスタ内容に任意の文字を許可している本設計（§7.3 は文字種を制限しない）と相性が悪い。

#### 13.4.2 ファイル名

| 起点画面   | ファイル名                                  |
| ------ | -------------------------------------- |
| MST-01 | `master_YYYYMMDDHHmmss.csv`            |
| MST-06 | `master_categories_YYYYMMDDHHmmss.csv` |

- 日時はCSVを生成した時刻（Asia/Tokyo）とする。
- ファイル名はASCII文字だけで構成する。日本語を含めると `Content-Disposition` でのエンコードが必要になり、ブラウザーごとの差異を抱えるためである。
- `Content-Type` は `text/csv; charset=utf-8`、`Content-Disposition` は `attachment; filename="<上記>"` とする。
- **ストレージ上の保存名は利用者へ見せるファイル名と別にする**（§13.9）。

#### 13.4.3 マスタの出力列

| 順 | 列名       | 値                              |
| - | -------- | ------------------------------ |
| 1 | マスタ分類コード | `MasterCategory.id` を4桁ゼロ埋めした値 |
| 2 | マスタ分類名   | `MasterCategory.name`          |
| 3 | マスタID    | `Master.id`                    |
| 4 | マスタコード   | `Master.code`                  |
| 5 | マスタ内容    | `Master.content`               |
| 6 | 登録日時     | `Master.createdAt`             |
| 7 | 登録者      | `Master.createdBy`。値が無い場合は空欄    |
| 8 | 最終更新日時   | `Master.updatedAt`             |
| 9 | 最終更新者    | `Master.updatedBy`。値が無い場合は空欄    |

マスタ詳細画面（MST-04）の表示項目7つに、マスタ分類コードと内部IDを加えた9列とする。

**内部ID（`Master.id`）を出力する。** §8.2 では内部識別子と位置づけているが、CSVを他システムやスプレッドシートへ取り込む際に行を一意に識別できる必要があり、参照側がマスタIDを保持するという規約（§8.4）とも整合する。マスタコードは変更され得る値であるため（§6.5）、突合のキーには使えない。

#### 13.4.4 マスタ分類の出力列

| 順 | 列名       | 値                                    |
| - | -------- | ------------------------------------ |
| 1 | マスタ分類コード | `MasterCategory.id` を4桁ゼロ埋めした値       |
| 2 | マスタ分類名   | `MasterCategory.name`                |
| 3 | 登録マスタ件数  | その分類に属するマスタの件数                       |
| 4 | 登録日時     | `MasterCategory.createdAt`           |
| 5 | 登録者      | `MasterCategory.createdBy`。値が無い場合は空欄 |
| 6 | 最終更新日時   | `MasterCategory.updatedAt`           |
| 7 | 最終更新者    | `MasterCategory.updatedBy`。値が無い場合は空欄 |

マスタ分類詳細画面（MST-07）の表示項目と同じ7列とする。マスタ分類コードが `MasterCategory.id` そのものであるため、内部IDの列は設けない。

#### 13.4.5 値の書式

- 日時は `YYYY/MM/DD HH:mm:ss` 形式とし、タイムゾーンは Asia/Tokyo に固定する。Excelが日時として解釈できる形式であり、画面の表示とも一致させる。
- `null` は**空欄**とする。画面では「—」を表示するが（§6.4.1）、CSVでは記号を出さない。取り込み側が値の有無を判定できるようにするためである。

### 13.5 処理の流れ

3つの処理が関わる。**依頼**（Server Action）、**生成**（worker）、**受け取り**（Route Handler）である。

```text
利用者                app                          DB / ストレージ            worker
  │                    │                                │                     │
  ├─「CSVダウンロード」──▶│                                │                     │
  │                    ├─ 権限・件数上限を確認 ───────────▶│                     │
  │                    ├─ MasterExport を QUEUED で作成 ─▶│                     │
  │                    ├─ pg-boss へジョブ送信 ──────────▶│                     │
  │                    ├─ worker を起動（§13.7）─────────┼────────────────────▶│
  │◀── exportId ───────┤                                │                     │
  │                    │                                │◀─ ジョブを取得 ───────┤
  │                    │                                │◀─ 検索・CSV生成 ──────┤
  │                    │                                │◀─ ファイルを保存 ─────┤
  │                    │                                │◀─ READY へ更新 ──────┤
  ├─ 状態を問い合わせ ──▶│                                │                     │
  │◀── READY ──────────┤                                │                     │
  ├─ ファイルを要求 ────▶│                                │                     │
  │                    ├─ 本人確認 → ストレージから取得 ──▶│                     │
  │◀── CSV ────────────┤                                │                     │
  │                    ├─ ファイルと行を削除（§13.9）─────▶│                     │
```

#### 13.5.1 依頼（Server Action）

`actions.ts` に `requestMasterExportAction` と `requestMasterCategoryExportAction` を追加する。`withOp` でラップする。

1. `getCurrentUser()` で利用者を取得する。未ログインなら `UNAUTHORIZED`。ロールによる制限は行わない（§3）。
2. 検索条件を検証する（一覧と同じ `validation.ts` のスキーマを再利用する）。
3. 対象件数を数え、上限を超える場合は `MASTER_EXPORT_LIMIT_EXCEEDED`（§13.8）。
4. 保持期限を過ぎた過去の生成物を掃除する（§13.9）。
5. `MasterExport` を `QUEUED` で作成する（§13.6）。
6. pg-boss のキュー `master.export` へ、`exportId` だけを積む。**検索条件はジョブのペイロードへ入れず `MasterExport` に持たせる**。ジョブの内容が変わっても pg-boss のペイロード構造に影響させないためである。
7. workerを起動する（§13.7）。
8. `exportId` を返す。

依頼をServer Actionにするのは、状態を変える操作（行の作成とジョブ投入）であり、既存の登録・更新と同じ境界（`withOp`）へ揃えるためである。

#### 13.5.2 生成（worker）

`src/worker/index.ts` へ、キュー `master.export` の購読を追加する。ハンドラーは `withJob` でラップする（`src/AGENTS.md`）。

1. `exportId` から `MasterExport` を読む。存在しない、または `QUEUED` でない場合は何もしない（多重実行への保険）。
2. `RUNNING` へ更新する。
3. 保存されている条件で検索する。並び順は §13.2 のとおり。
4. `csv.ts` でCSV文字列を組み立てる（§13.4）。
5. `storage.upload()` でファイルを保存する（§13.9）。
6. `READY` へ更新し、`filePath` と `rowCount` を記録する。
7. 例外が発生した場合は `FAILED` と `errorCode` を記録する。ログは `withJob` が処理境界で1回だけ出力する。

worker側の処理はマスタモジュールの `service.ts` を呼ぶ。ジョブの登録先ファイルは `src/worker/index.ts` だが、業務処理をそこへ書かない。

#### 13.5.3 状態の問い合わせと受け取り（Route Handler）

| 用途    | メソッド | URL                                     |
| ----- | ---- | --------------------------------------- |
| 状態の確認 | GET  | `/api/master/exports/[exportId]/status` |
| 受け取り  | GET  | `/api/master/exports/[exportId]`        |

いずれも `withRoute` でラップする。**`/api` は [`proxy.ts`](../../../src/proxy.ts) の `matcher` から除外されており、middlewareの認証ガードがかからない。** ハンドラーの先頭で `getCurrentUser()` を呼び、未ログインなら `UNAUTHORIZED` を投げる。

さらに、**`MasterExport.requestedBy` が現在の利用者と一致することを検証する。** 一致しない場合は `MASTER_EXPORT_NOT_FOUND` とする（他人の依頼が存在することを知らせないため、403ではなく404とする）。`exportId` は推測困難な値（cuid）だが、それだけを頼りにしない。

受け取りの処理は次のとおり。

1. 認証と本人確認を行う。
2. `status` が `READY` でない場合は `MASTER_EXPORT_NOT_READY`。
3. `storage.download()` でファイルを取得する。
4. `Content-Type` / `Content-Disposition` を付けて返す（§13.4.2）。
5. ファイルと `MasterExport` の行を削除する（§13.9）。

**署名URLへのリダイレクトは行わない。** アプリケーション経由で返すことにより、本人以外が受け取れないことをアプリケーションで保証でき、ローカル（ファイルシステム）とSupabase Storageで経路が同じになる。ローカルの `getSignedUrl` が返す `/uploads/{path}` は配信されないため、署名URL方式ではローカルで動作しない。

ダウンロードはブラウザーの遷移で行う（`window.location.href` へ受け取りURLを設定する）。ファイルの内容をJavaScriptで受け取ってから保存する方式は採らない。

### 13.6 データモデル

`MasterExport` を追加する。マスタ機能に属するテーブルであるため、`schema.prisma` の同じ場所へ置く。

```prisma
/// CSVダウンロードの依頼と生成物（§13）。
model MasterExport {
  id          String   @id @default(cuid())
  target      String // MASTER / MASTER_CATEGORY
  categoryId  Int? // 検索条件（target = MASTER のときのみ）
  keyword     String? // 検索条件（target = MASTER のときのみ）
  status      String   @default("QUEUED") // QUEUED / RUNNING / READY / FAILED
  filePath    String? // ストレージ上のパス（READY のときのみ）
  fileName    String? // 利用者へ見せるファイル名
  rowCount    Int?
  errorCode   String? // FAILED のときのエラーコード
  requestedBy String // 依頼した利用者の User.id（FK は張らない）
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([createdAt])
  @@index([requestedBy])
}
```

- `requestedBy` は必須とする。受け取り時の本人確認に使うため、値が無い状態を許さない（マスタの `createdBy` とは扱いが異なる）。外部キー制約は張らない点は §8.2 と同じ。
- `target` を文字列で持ち、マスタとマスタ分類で同じテーブルを共用する。出力列は異なるが、依頼・生成・受け取りの流れは同一であるため、テーブルを分けない。
- 状態は4つとする。`DOWNLOADED` は持たない。受け取った時点で行ごと削除するためである（§13.9）。

### 13.7 workerの実行方式と本番構成

**本テンプレートの本番環境には、現時点でworkerが存在しない。** Cloud Runのサービスは `contract-app` の1つだけで、[`docker/Dockerfile`](../../../docker/Dockerfile) の `runner` ステージの `CMD` は `next start` である。本機能の実装には、**worker を本番で実行できるようにする作業が前提として必要**になる。

#### 13.7.1 起動方式

**Cloud Run Jobs として実行し、appがジョブ実行APIで起動する。** 常時起動はさせない。

| 環境    | worker の動き                                                 | 起動の担当                        |
| ----- | ---------------------------------------------------------- | ---------------------------- |
| ローカル  | `docker compose` の `worker` サービスが常駐し、pg-boss をポーリングし続ける     | 起動不要（常駐しているため）               |
| 本番    | Cloud Run Jobs として単発実行される。溜まっているジョブを処理し終えたら終了する             | app が Cloud Run Admin API で起動 |

環境による分岐は環境変数で切り替える。

| 環境変数                   | 値                            | 説明                                |
| ---------------------- | ---------------------------- | --------------------------------- |
| `WORKER_INVOKE_MODE`   | `none` / `cloud-run-job`     | `none`（既定・ローカル）では起動処理を行わない        |
| `CLOUD_RUN_JOB_NAME`   | Cloud Run Jobs のジョブ名         | `cloud-run-job` のときのみ必須           |
| `CLOUD_RUN_JOB_REGION` | リージョン（本番は `us-central1`）     | 同上                                |
| `GOOGLE_CLOUD_PROJECT` | プロジェクトID                     | 同上。Cloud Run上では既定で設定される           |

`.env.example` へ上記を追記する。

#### 13.7.2 worker の2つの実行モード

現在の [`src/worker/index.ts`](../../../src/worker/index.ts) は起動して待受し続ける常駐型である。Cloud Run Jobs では**処理し終えたら終了する**必要があるため、実行モードを2つ持たせる。

| モード | 起動方法                                     | 終了条件                             |
| --- | ---------------------------------------- | -------------------------------- |
| 常駐  | `pnpm worker`（ローカル・docker compose）        | SIGINT / SIGTERM（既存の実装のまま）        |
| 単発  | Cloud Run Jobs のコンテナ起動（`--once` 等の引数で区別） | キューが空になったら `boss.stop()` して終了する   |

単発モードは、起動直後に処理すべきジョブが無い場合も一定時間（数秒）待ってから終了する。依頼とジョブ登録のコミットが、起動要求より後になる可能性があるためである。

#### 13.7.3 サービスアカウントへの影響

app がCloud Run Jobsを起動するには、**app の実行サービスアカウントに Cloud Run Jobs の実行権限（`roles/run.invoker` 相当）が必要**になる。

これは [`TODO.md`](../../todo/TODO.md) の宿題「Cloud Run の実行サービス アカウントを、権限を持たない専用 SA に差し替える」と直接ぶつかる。**本機能の採用により、「権限ゼロのSA」は成立しなくなる。** 宿題の目標を「権限ゼロ」から**「必要な権限だけを持つ専用SA」**へ読み替える必要がある。

- 差し替え後の専用SAに付与するのは、対象のCloud Run Jobsに対する実行権限**だけ**とする。既定のサービスアカウントが持つプロジェクトの編集者権限とは比較にならないほど狭いため、最小権限という宿題の趣旨は保てる。
- worker（Cloud Run Jobs）側の実行サービスアカウントには、Google CloudのAPIを呼ぶ権限は不要である（DBもストレージもSupabaseを直接叩くため）。
- ローカルでは `WORKER_INVOKE_MODE=none` のため、Google Cloudの資格情報を一切必要としない。

#### 13.7.4 本番構成として必要になる作業

設計上の前提として列挙する。実施は [`TODO.md`](../../todo/TODO.md) で管理する。

1. worker用のコンテナイメージを用意する（`docker/Dockerfile` に worker 用のステージを足すか、`runner` を共用して起動コマンドで分ける）。
2. Cloud Run Jobs を作成し、DB接続とストレージの環境変数を設定する。
3. app 側に `WORKER_INVOKE_MODE=cloud-run-job` とジョブ名・リージョンを設定する。
4. app の実行サービスアカウントへジョブ実行権限を付与する（§13.7.3）。
5. Cloud Build のトリガーが worker 用イメージも更新するようにする。

### 13.8 件数上限

一度にダウンロードできる行数の上限を **10,000行** とする。モジュール定数 `MASTER_EXPORT_MAX_ROWS` として `types.ts` に置き、環境変数にはしない。案件ごとに変える値ではなく、変えるなら生成方式そのものを見直すべき値だからである。

worker で生成するためリクエストのタイムアウトからは解放されるが、上限は残す。CSV全体をメモリ上で組み立てて1つのファイルとして保存する方式であり、Cloud Run Jobs のメモリを超えれば失敗するためである。行数を増やす場合は、上限の引き上げではなく分割出力やストリーミングの導入を検討する。

超過は2段階で防ぐ。

1. **画面側**: 一覧は既に総件数を表示している（§6.1.6・§6.7.1）。総件数が上限を超える場合はボタンを無効化し、「対象が *N* 件あります。10,000件以下になるよう検索条件で絞り込んでください」と表示する。
2. **サーバー側**: 依頼のServer Actionで件数を数え、上限を超える場合はジョブを登録せず `MASTER_EXPORT_LIMIT_EXCEEDED` を返す。`context` には対象件数と上限を含める。

件数の確認から生成までの間にマスタが増え、生成時点で上限を超える可能性はある。**worker側では件数を再確認しない**。上限は保護のための目安であり、数件の超過で失敗させる価値は無い。

マスタ分類（MST-06）にも同じ上限を適用する。分類が10,000件を超えることは想定しにくいが、経路ごとに仕様を変えない。

### 13.9 ファイルの保持と削除

#### 13.9.1 保存先

既存の `@/shared/storage` を使用する。`STORAGE_TYPE` により、ローカルはファイルシステム（`STORAGE_LOCAL_DIR`）、本番はSupabase Storage（非公開バケット `uploads`）へ保存される。**CSVのために新しい保存先を追加しない。**

保存パスは `master-export/{exportId}.csv` とする。`exportId` を使うことで、同じ条件で同時に依頼されても衝突しない。利用者へ見せるファイル名（§13.4.2）は `MasterExport.fileName` に持ち、保存パスとは分ける。

#### 13.9.2 削除

**受け取った時点で削除する。**

1. 受け取りのRoute Handlerが `storage.download()` した後、`storage.remove()` でファイルを消し、`MasterExport` の行も削除する。
2. ファイルの削除に失敗しても、利用者への応答は成功として返す。取り残しは 3 の掃除で回収される。

**取り残しは次回の依頼時にまとめて掃除する。** 依頼のServer Action（§13.5.1 の手順4）で、作成から24時間以上経過した `MasterExport` を対象に、ファイルと行を削除する。

- 利用者がダウンロードを完了しなかった場合や、生成が `FAILED` で終わった場合の取り残しはここで回収する。
- **掃除専用の定期ジョブは設けない。** Cloud Schedulerなどの定期起動の仕組みを持ち込まずに済ませるためである。依頼が長期間発生しなければ取り残しも増えないため、実害が無い。
- 保持期間（24時間）は定数 `MASTER_EXPORT_RETENTION_HOURS` として `types.ts` に置く。

### 13.10 待ち時間とエラー

#### 13.10.1 状態の問い合わせ

画面は `exportId` を受け取った後、状態を問い合わせて完了を待つ。

| 項目    | 値                       |
| ----- | ----------------------- |
| 間隔    | 2秒                      |
| 打ち切り  | 60秒（30回）                |
| 打ち切り後 | §13.3.1 の「時間切れ」を表示する    |

打ち切った場合でも、workerは処理を続け生成物は残る。ただし**受け取る導線はその画面にしか無いため、利用者は同じ操作をやり直すことになる**。取り残しは §13.9.2 の掃除で回収される。ダウンロード履歴の画面を設けないことで受け入れる制約である。

#### 13.10.2 エラー

| 状況                | エラーコード                         | 画面の扱い                  |
| ----------------- | ------------------------------ | ---------------------- |
| 件数が上限を超える         | `MASTER_EXPORT_LIMIT_EXCEEDED` | 依頼せずメッセージを表示する         |
| 依頼が存在しない・他人の依頼    | `MASTER_EXPORT_NOT_FOUND`      | メッセージを表示する             |
| まだ生成が終わっていない      | `MASTER_EXPORT_NOT_READY`      | 問い合わせを続ける（利用者へは見せない）   |
| 生成に失敗した           | `MASTER_EXPORT_FAILED`         | メッセージを表示し、再実行を促す       |
| 未ログインでURLを直接開いた   | `UNAUTHORIZED`                 | ログイン画面へ誘導する            |

生成の失敗はworkerの中で起きるため、その場で利用者へ伝えられない。`MasterExport.status` を `FAILED` にし、`errorCode` を残すことで、状態の問い合わせを通じて画面へ伝える。

### 13.11 ダウンロードの記録

CSVダウンロードは、絞り込みの有無にかかわらずマスタを一度に取得できる操作であるため、**誰がいつ実行したかを記録する**。記録は §10 と同じくアプリケーションログで行う。

- **依頼**は `withOp` が記録する。`withOp` は実行者の `userId` と Server Action の引数（検索条件）を出力するため、追加の仕組みは要らない。
- **生成**は `withJob` が記録する。
- **受け取り**は `withRoute` が記録する。ただし現在の [`withRoute`](../../../src/shared/observability/with-route.ts) は `op` / `requestId` / `method` / `url` を出力するのみで、**実行者を含まない**（`userId` を解決しているのは [`withOp`](../../../src/shared/observability/with-op.ts) だけである）。そこで本機能の実装に併せて、**`withRoute` にも `withOp` と同じ利用者解決を組み込み、`userId` と `role` を出力するよう変更する**。

  - 対象は `src/shared/observability/with-route.ts` であり、マスタモジュール外への変更となる。実装時はこの変更を独立したコミットとする。
  - 既存の `/api/health` は未ログインでも呼ばれるが、その場合は利用者が解決できず値が付かないだけで、動作へは影響しない（`resolveUserCtx` は失敗時に空を返す）。

依頼と受け取りは同じ `exportId` を持つため、ログ上で突き合わせられる。**出力件数は `MasterExport.rowCount` に一時的に残るが、受け取り後は行ごと消える。** 業務コードにログを書かない規約（`src/AGENTS.md`）を曲げてまで恒久的に記録する価値は無いと判断する。

### 13.12 同期方式を採らなかった理由

リクエストの中でCSVを生成して返す同期方式と比較し、worker方式を採用した。

| 観点        | worker方式（採用）                              | 同期方式                            |
| --------- | ---------------------------------------- | ------------------------------- |
| 追加の部品     | `MasterExport` テーブル、ジョブ定義、状態の問い合わせ、worker の本番構成 | 無し                              |
| 利用者の操作    | ボタンを押して待つ（自動でダウンロードが始まる）                 | ボタンを押すとすぐ始まる                    |
| リクエストの制限  | 受けない                                     | Cloud Run のリクエストタイムアウト内に収める必要がある |
| 件数が増えたとき  | 上限の引き上げで対応できる                            | タイムアウトが先に来る                     |
| テンプレートの価値 | **workerを使う実装例が揃う**                      | worker の雛形は使われないまま残る            |

決め手は、**時間のかかる可能性がある処理はworkerへ寄せるという本テンプレートの方針**である。マスタのCSVは現状の件数なら同期でも間に合うが、本テンプレートをコピーして作る案件では対象が大きくなり得る。ここでworkerの経路を通しておけば、後続の機能は同じ型をなぞれる。

## 14. 対象外

### 14.1 採用しないと決めたもの

検討したうえで、機能として設けないと決めたものを記す。今後の設計で蒸し返さないための記録である。

#### 14.1.1 マスタの表示順を任意に変更する機能

**マスタおよびマスタ分類に、利用者が任意に並べ替えられる表示順（`sortOrder` に相当するカラム）は持たない。** 並び順は次のとおり固定とする。

| 対象     | 並び順                                       | 決定箇所     |
| ------ | ----------------------------------------- | -------- |
| マスタ    | マスタ分類名の昇順 → マスタコードの昇順                     | §6.1.6   |
| マスタ分類  | マスタ分類コードの昇順（`MasterCategory.id` の採番順）      | §6.7.1   |
| 分類プルダウン | マスタ分類コードの昇順                               | §6.2.1・§6.5.1 |

採用しない理由は以下のとおりである。

- **マスタコードが並び順の役割を果たす。** マスタコードは利用者が付ける値であり自動採番ではない（§8.2）。並べたい順序があるなら、`CON00001`・`CON00002` のようにコードの採番規則で表現できる。並び順のためだけに別のカラムを増やす必要がない。
- **並び順を変更する導線が、既存の「入力 → 確認 → 実行」の型に馴染まない。** 複数行を一度に書き換える操作となるため、専用画面か一覧上での即時反映が要る。前者は画面が増え、後者は「更新は必ず確認画面を経る」という本設計の前提（§1）を崩す。
- **現時点で並び順が効く場所が検索一覧しかない。** マスタを参照するテーブルは存在せず（§8.4）、本来の狙いである参照側プルダウンの並びは、参照が生まれるまで価値を持たない。

将来、参照側でマスタを選択するプルダウンが登場し、そこでコード順とは異なる並びが業務上必要になった時点で、あらためて検討する。その場合も、まずマスタコードの採番規則で表現できないかを先に確認する。

#### 14.1.2 マスタの有効期間および有効・無効状態の管理

**マスタおよびマスタ分類に、有効期間（`validFrom` / `validTo` に相当するカラム）も有効フラグ（`enabled` に相当するカラム）も持たない。** 登録されているマスタはすべて有効として扱い、状態という概念を設けない。

したがって以下はいずれも行わない。

- マスタ検索一覧（MST-01）への「状態」列および状態による絞り込みの追加
- 登録・更新画面（MST-02・MST-05）への有効期間の入力欄の追加
- 基準日による有効・無効の判定

採用しない理由は以下のとおりである。

- **使わなくなったマスタは削除で対応する。** 本設計は物理削除を採用しており（§8.3）、誤登録の抹消と運用終了のどちらも削除で扱える。無効化を足すと「消す」と「止める」の 2 つの手段が並び、どちらを使うべきかの判断が利用者に委ねられる。
- **現時点で状態が効く場所が無い。** マスタを参照するテーブルは存在せず（§8.4）、本来の狙いである「基準日に有効なマスタだけを選択肢に出す」という効き先が存在しない。
- **状態はすべての画面へ波及する。** 一覧の表示、検索条件、登録・更新の入力、確認画面の表示項目、将来の参照側プルダウンのすべてに判定が加わり、画面ごとの仕様が増える。効き先が生まれていない段階で払うコストとしては大きい。

将来、参照側でマスタを選択するようになり、過去の参照を保ったまま新規の選択肢からは外したい、という要求が出た時点であらためて検討する。その時点では削除では要求を満たせない（削除すると過去の参照が「未設定」になる。§8.4）ため、有効期間の導入が正当化される。

#### 14.1.3 変更履歴の参照画面

**登録・更新・削除の履歴をデータベースへ保持する専用テーブルは設けず、履歴を参照する画面も作らない。** 追跡は §10.1 のとおりアプリケーションログのみで行う。

採用しない理由は以下のとおりである。

- **§10.1 の仕組みで、誤操作からの復旧に必要な情報は残っている。** 削除・更新の Server Action は変更前の値を引数に含め、`withOp` が操作名・`requestId`・実行者の `userId` とともに一度だけ記録する。「何を元の値へ戻せばよいか」はログから特定できる。
- **履歴テーブルは全 Server Action へ波及する。** 登録・更新・削除の 6 つすべてに履歴行の挿入が加わり、業務処理と同じトランザクションに含めるかどうかの判断も要る。マスタは変更頻度が低く、この重さに見合わない。
- **参照画面まで作ると画面が増える。** 一覧・詳細に加えて履歴の一覧と差分表示が必要になり、10 画面がさらに増える。

制約として、**ログの保持期間を超えると追跡できなくなる**点は許容する（§10.1）。監査要件として一定期間の変更履歴の保持が求められる案件では、本テンプレートをコピーした先で履歴テーブルを追加する。
