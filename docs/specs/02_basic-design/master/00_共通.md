## 00.1 概要

本機能は、システム内で利用する汎用的なマスタデータを、マスタ分類ごとに検索・参照・登録・更新・削除する機能である。

画面の起点は `/master` とし、以下の機能を提供する。

- マスタの検索および一覧表示
- マスタの新規登録
- 登録済みマスタの詳細表示
- マスタの更新（マスタ分類・マスタコード・マスタ内容）
- 登録・更新内容の実行前確認
- マスタの削除
- マスタ分類の一覧表示および詳細表示
- マスタ分類の新規登録
- マスタ分類名の更新
- マスタ分類の削除
- マスタおよびマスタ分類のCSVダウンロード
- マスタ分類とマスタをまとめたExcelファイルの取得（→ [`40_マスタ情報Excel取得.md`](40_マスタ情報Excel取得.md)）

マスタ分類と個々のマスタデータは別のテーブルで管理する。**マスタ分類は専用の画面で登録・更新・削除する。** マスタの新規登録画面から新しいマスタ分類を作ることはできず、登録済みのマスタ分類を選択できるだけとする。分類を増やす操作とマスタを増やす操作を分けることで、マスタを登録するつもりで分類が増えてしまう事故を防ぐ。

登録・更新の入力画面ではデータベースを更新せず、確認画面で「実行」ボタンが押された時点で初めて反映する。

削除は**物理削除**とする。論理削除は採用しない。削除したマスタおよびマスタ分類はデータベースから行ごと消えるため、画面からの復元手段は設けない。この方式を採る理由と制約は §01.1.3 に記す。

## 00.3 権限

既存のロールに対する操作権限は以下とする。

| 操作          | ADMIN | OPERATOR | VIEWER |
| ----------- |:-----:|:--------:|:------:|
| マスタの検索・一覧表示 | 可     | 可        | 可      |
| マスタの詳細表示    | 可     | 可        | 可      |
| マスタの新規登録    | 可     | 可        | 不可     |
| マスタの更新      | 可     | 可        | 不可     |
| マスタの削除      | 可     | 可        | 不可     |
| マスタ分類の一覧    | 可     | 可        | 可      |
| マスタ分類の詳細    | 可     | 可        | 可      |
| マスタ分類の新規登録  | 可     | 可        | 不可     |
| マスタ分類の更新    | 可     | 可        | 不可     |
| マスタ分類の削除    | 可     | 可        | 不可     |
| CSVダウンロード   | 可     | 可        | 可      |
| マスタ情報Excel取得の実行・履歴閲覧・ダウンロード | 可 | 可 | 可 |

VIEWERには「新規登録」ボタン、「更新する」ボタンおよび「削除」ボタンを表示しない。画面上の非表示だけでなく、Server Actionでも書き込み権限を検証し、不正な直接リクエストを拒否する。判定には既存の `canWrite`（`@/shared/constants/roles`）を使用する。

CSVダウンロードは参照操作であり、一覧画面で閲覧できる情報しか含まないため、参照権限と同じく全ロールに許可する。ただし絞り込みの有無にかかわらず対象を一度に取得できる操作であるため、実行者をログへ記録する（§30.1.8）。

マスタ情報Excel取得は、CSVダウンロードと異なり実行履歴が画面に残る仕様のため、実行・履歴閲覧・他人が作ったファイルのダウンロードのいずれも全ロールへ許可する（→ §40.4）。

マスタコードの変更は業務上の識別子を書き換える操作だが、マスタ内容の更新と権限を分けずADMIN・OPERATORとする。ADMIN限定にすると `canWrite` とは別の判定が必要になり、権限設計が複雑になるためである。誤操作は権限ではなく、確認画面での変更前後の並記（§11.2.1）で防ぐ。

| MST-11 | マスタ情報Excel取得画面 | `/master/exports`                                                | Excelファイルの作成依頼と実行履歴の表示・ダウンロード（→ §40.3） |

MST-03は、新規登録と更新で共通利用する論理画面とする。独立した画面ルートは作成せず、新規登録の場合はMST-02、更新の場合はMST-05のコンポーネントを確認状態へ切り替えて表示する。入力値をURLへ含めないことで、入力値がブラウザー履歴やアクセスログへ残ることを防ぐ。

MST-09も同様に、マスタ分類の新規登録と更新で共通利用する論理画面とし、独立した画面ルートは作成しない。

**マスタコードと所属マスタ分類の変更に専用の画面は設けず、マスタ更新画面（MST-05）で行う。** 当初はマスタ内容の更新と分けることを検討したが、確認画面（MST-03）が変更前後を並べて表示し、変わらない項目に「変更なし」を併記する仕様であるため、内容を直すつもりでコードを書き換える誤操作はその時点で気づける。画面を割いてまで二重に防ぐ必要はないと判断した。

マスタ更新画面（MST-05）とマスタ分類更新画面（MST-10）は対象が異なる。前者は個々のマスタの所属分類とコードを変更し、後者はマスタ分類そのものの名称を変更する。**あるマスタを別の分類へ移す操作は、分類側ではなくマスタ側（MST-05）で行う。**

削除の確認は独立した画面を設けず、MST-04およびMST-07の上に表示する確認ダイアログで行う。ダイアログの仕様はそれぞれ §14.1 と §21.1 に記す。

削除ボタンは一覧画面（MST-01・MST-06）には配置せず、**詳細画面（MST-04・MST-07）だけに配置する**。削除の前に必ず対象の詳細を開く導線となり、一覧上の誤操作を防ぐ。「更新する」ボタンも同じ理由で詳細画面だけに配置する。

## 00.6 エラー設計

| エラーコード                        | HTTPステータス | 発生条件                                | 利用者向けメッセージ例                                         |
| ----------------------------- | ---------:| ----------------------------------- | --------------------------------------------------- |
| `VALIDATION_ERROR`            | 422       | 必須、文字数、文字種に違反した                     | 入力内容を確認してください                                       |
| `MASTER_NOT_FOUND`            | 404       | 対象マスタが存在しない（既に削除された場合を含む）           | 対象のマスタが見つかりません                                      |
| `MASTER_CATEGORY_NOT_FOUND`   | 404       | 対象・選択・変更先のマスタ分類が存在しない（既に削除された場合を含む） | 対象のマスタ分類が見つかりません                                    |
| `MASTER_CATEGORY_CONFLICT`    | 409       | 同じ分類名が登録または更新で重複した                  | 同じ名前のマスタ分類が登録されています                                 |
| `MASTER_CODE_CONFLICT`        | 409       | 同じ分類内でコードが登録または変更で重複した              | 同じマスタ分類に同じマスタコードが登録されています                           |
| `MASTER_CONCURRENT_UPDATE`    | 409       | ほかの利用者が先に更新した                       | ほかの利用者によって更新されています。最新の内容を確認してください                   |
| `MASTER_CATEGORY_HAS_MASTERS` | 409       | 削除対象のマスタ分類に属するマスタが存在する              | このマスタ分類には *N* 件のマスタが登録されているため削除できません。先にマスタを削除してください |
| `FORBIDDEN`                   | 403       | 書き込み権限がない利用者が登録・更新・変更・削除した          | この操作を行う権限がありません                                     |
| `UNAUTHORIZED`                | 401       | 未ログインでCSVダウンロードのURLを直接開いた           | ログインが必要です                                           |
| `MASTER_EXPORT_LIMIT_EXCEEDED` | 422      | CSVダウンロードの対象件数が上限を超えた（§30.1.6）        | 対象が *N* 件あり、一度にダウンロードできる上限（*M* 件）を超えています。検索条件で絞り込んでください |
| `MASTER_EXCEL_EXPORT_LIMIT_EXCEEDED` | 422 | Excel取得の対象件数が上限を超えた（§40.8）        | 対象の件数が多く、Excelを作成できません。管理者に相談してください |
| `MASTER_EXCEL_EXPORT_FAILED`  | 500       | Excel生成中に例外が発生した（§40.10）           | Excelの作成に失敗しました。もう一度お試しください |
| `MASTER_EXCEL_EXPORT_EXPIRED` | 410       | 保持期限を過ぎたファイルをダウンロードしようとした（§40.9）      | ファイルの有効期限が切れています |
| `MASTER_EXCEL_EXPORT_NOT_FOUND` | 404     | 対象の実行履歴が存在しない（§40.10）              | 対象の実行履歴が見つかりません |

業務処理では `Errors` ファクトリまたはマスタ機能固有の `AppError` を送出する。業務コードに個別のログ出力や包括的な `try/catch` は記述せず、Server Actionを `withOp` でラップして処理境界で一度だけ記録する。データベースの更新に失敗した場合は `AppError` へ変換せず、`withOp` が記録したうえで画面には汎用のエラーメッセージ（`MESSAGES.common.unexpected`）を表示する。

`MASTER_CATEGORY_HAS_MASTERS` の `context` には配下マスタの件数を含め、利用者向けメッセージに反映する。

### 00.6.1 削除・変更操作の記録

物理削除では削除された行が残らず、コードや分類名の変更では上書き前の値が残らない。どちらもデータベースには「変更後の姿」しか存在しないため、記録はアプリケーションログでのみ行う。誤って操作した場合に、何を元の値へ戻せばよいかをログから特定できるようにする。

`src/AGENTS.md` の規約により、業務コード（`service.ts` / `repository.ts`）にログを書いてはならない。ログは境界ラッパー `withOp` が処理ごとに一度だけ出力する。`withOp` は操作名・`requestId`・実行者の `userId` に加えて**Server Actionの引数**を出力するため、Server Actionの入力に対象の表示内容と変更前の値を含めることで、仕組みを追加せずに記録を残す。

| 操作                | Server Actionの入力に含める値                                              |
| ----------------- | ------------------------------------------------------------------ |
| マスタの削除            | マスタID、`updatedAt`、マスタ分類名、マスタコード、マスタ内容                              |
| マスタ分類の削除          | マスタ分類ID、`updatedAt`、マスタ分類名                                         |
| マスタの更新（MST-05）    | マスタID、`updatedAt`、変更前のマスタ分類名・マスタコード・マスタ内容、変更後のマスタ分類ID・マスタコード・マスタ内容 |
| マスタ分類名の更新（MST-10） | マスタ分類ID、`updatedAt`、変更前のマスタ分類名、変更後のマスタ分類名                          |

- 変更前の値は確認画面が保持しているものをそのまま送信する。
- **可否判定にこれらの値を使用しない。** 判定に使うのは対象IDと `updatedAt`、および変更後の入力値だけとする（§13.2・§14.2）。
- クライアントから送信される値であるため改ざんされ得るが、対象IDが同じログレコードに記録されるため、突き合わせは可能である。

マスタの更新では、変更されなかった項目についても変更前後の値を送信する。項目ごとに送る・送らないを切り替えると、ログを読む側が「記録が無いのは変更しなかったからか、送り漏れたからか」を判別できなくなるためである。

ログの保持期間を超えると追跡できなくなる点は許容する。**データベース上での変更履歴の保持は採用しない**（§00.9.1.3）。

CSVダウンロードの記録については §30.1.8 に記す。

```text
│        └─ page.tsx
└─ [masterId]/
   ├─ page.tsx
   └─ edit/
      └─ page.tsx
```

CSVダウンロードとマスタ情報Excel取得のRoute Handlerは、画面ルートとは別に以下へ置く（役割はそれぞれ §30.1.5・§40.5.4）。

```text
src/app/api/master/
├─ exports/
│  ├─ csv/
│  │  └─ route.ts          # マスタのCSVを返す
│  └─ excel/
│     └─ [id]/
│        └─ route.ts       # 完了したExcelファイルを返す（→ §40.5.4）
└─ categories/
   └─ exports/
      └─ csv/
         └─ route.ts       # マスタ分類のCSVを返す
```

CSVの生成はappのリクエストの中で行うため、workerのキュー購読は不要である（§30.1.9）。**一方、マスタ情報Excel取得（§40.5）はworkerでキューを購読して処理するため、`src/worker/index.ts` に `src/modules/master/excel-job.ts` が公開するジョブハンドラーの登録を追加する。** 業務処理は `src/modules/master/service.ts` を呼ぶ。

マスタ分類はマスタと同じ境界づけられたコンテキストに属するため、独立したモジュールを作らず `src/modules/master` 内で扱う。

各ファイルの責務は以下とする。

| ファイル              | 責務                                   |
| ----------------- | ------------------------------------ |
| `app/**/page.tsx` | 認証確認、URLパラメーターの取得、サービス呼び出し、UIの組み立て   |
| `actions.ts`      | 書き込み権限確認、入力値の受け取り、Server Actionの処理境界 |
| `service.ts`      | 検索、重複確認、登録・更新ユースケース、トランザクション制御       |
| `repository.ts`   | Prismaを使用したデータベース操作                  |
| `validation.ts`   | Zodを使用した入力値検証                        |
| `export.ts`       | CSV文字列の組み立て（純粋関数。DBにもリクエストにも依存しない）   |
| `excel-export.ts` | Excelファイルの組み立て（純粋関数。→ §40.2）              |
| `excel-job.ts`    | Excel取得のジョブハンドラー（worker側の処理境界。→ §40.5.3）   |
| `types.ts`        | 一覧、詳細、フォームおよび検索条件の型定義                |
| `index.ts`        | マスタモジュールが外部へ公開するAPI                  |
| `ui/*.tsx`        | 画面表示、フォーム入力、入力状態と確認状態の切り替え           |

`master-confirmation.tsx` は新規登録と更新で共通利用し、処理モードに応じて表示項目、実行するServer Actionおよび戻り先を切り替える。`master-category-confirmation.tsx` はマスタ分類の新規登録と更新で共通利用する。マスタとマスタ分類では表示項目が重ならないため、確認画面のコンポーネントは分ける。

`master-create-form.tsx` と `master-update-form.tsx` は、マスタ分類のプルダウン・マスタコード・マスタ内容という同じ3項目を扱う。**入力欄はひとつの共通コンポーネントとして切り出し、両フォームから使用する。** 違いは初期値の有無、送信先のServer Action、および更新側が `updatedAt` と変更前の値を保持する点だけである。

`master-delete-dialog.tsx` と `master-category-delete-dialog.tsx` は、確認ダイアログの表示と削除用Server Actionの呼び出しを担う。対象の項目が異なるため別ファイルとするが、`AlertDialog` の構造、二重送信の防止および実行中の表示は共通の実装方針（§14.1.2）に従う。

`master-export-button.tsx` は、現在の検索条件を引き継いだダウンロードURLへのリンクを描画する。Server Actionを呼ばないため、状態を持たない表示専用のコンポーネントとする。

`master-excel-export-button.tsx` は、マスタ情報Excel取得画面（MST-11）への遷移リンクを描画する。`master-export-button.tsx` と同じく状態を持たない表示専用のコンポーネントとする。

`actions.ts` が公開するServer Actionは**7つ**とする。マスタの登録・更新・削除、マスタ分類の登録・更新・削除、マスタ情報Excel取得の依頼（§40.5.2）である。処理ごとに入力・検証・権限確認が異なるため、1つのServer Actionへまとめない。逆に、マスタの更新を項目ごとに分割することもしない（§11.2.4）。

**CSVダウンロードはServer Actionを持たない。** 検索条件をクエリパラメータとして渡すだけで済み、状態を変える操作でもないため、依頼から応答まで1つのRoute Handlerで完結させる（§30.1.5）。マスタ情報Excel取得は、依頼（Server Action）と受け取り（Route Handler）で役割が分かれる（§40.5）。

依存方向は `app → modules/master → shared` とし、Prismaは `repository.ts` 以外から直接使用しない。データベースへアクセスするファイルには `server-only` を適用する。

## 00.8 テスト方針

テストは対象ファイルの隣へコロケーションする。

機能ごとの確認項目は各機能のファイルの「テスト方針」に相当する節にある。ここには全機能に共通する権限の確認だけを置く。

### 00.8.1 権限

- VIEWERは一覧と詳細を参照できる。
- VIEWERには新規登録、更新および削除ボタンが表示されない。
- VIEWERによるServer Actionの直接実行を、**書き込み系6つ**のServer Actionすべてで拒否する。
- ADMINとOPERATORは登録、更新および削除を実行できる。
- CSVダウンロードの依頼（2つ）は、VIEWERでも拒否されない（§30.2）。
- マスタ情報Excel取得の依頼・履歴閲覧・ダウンロードは、VIEWERでも拒否されない（§40.14）。

## 00.9 対象外

### 00.9.1 採用しないと決めたもの

検討したうえで、機能として設けないと決めたものを記す。今後の設計で蒸し返さないための記録である。

#### 00.9.1.1 マスタの表示順を保存する機能

**マスタおよびマスタ分類に、利用者が保存できる任意の表示順（`sortOrder` に相当するカラム）は持たない。** 一覧を表示している間の一時的な並べ替えと、データとして表示順を登録・更新する機能は別のものとして扱う。

| 対象     | 初期の並び順                                  | 一覧上で選択できるソート列                         | 決定箇所     |
| ------ | ---------------------------------------- | -------------------------------------- | -------- |
| マスタ    | マスタ分類名の昇順 → マスタコードの昇順                | マスタ分類、マスタコード、マスタ内容                    | §10.1.6   |
| マスタ分類  | マスタ分類コードの昇順（`MasterCategory.id` の採番順） | マスタ分類コード、マスタ分類名、登録マスタ件数              | §20.1.1   |
| 分類プルダウン | マスタ分類コードの昇順                          | 利用者による並べ替えは行わない                       | §11.1.1・§13.1.1 |

一覧上のソート条件はURLクエリにだけ保持し、データベースへ保存しない。したがって、見出しによる並べ替えは登録・更新操作ではなく、確認画面やServer Actionも必要としない。

`sortOrder`カラムを採用しない理由は以下のとおりである。

- **マスタコードが既定の並び順の役割を果たす。** 業務上恒常的に並べたい順序がある場合は、まずコードの採番規則で表現する。
- **保存順の変更は複数行を更新する業務操作になる。** 専用画面、確認、同時更新制御が必要になり、一覧の閲覧中だけに使うソートより影響が大きい。
- **参照側プルダウンで独自の保存順を使う要求がまだ無い。** 将来その要求が生まれた時点で、`sortOrder`の追加をあらためて検討する。

#### 00.9.1.2 マスタの有効期間および有効・無効状態の管理

**マスタおよびマスタ分類に、有効期間（`validFrom` / `validTo` に相当するカラム）も有効フラグ（`enabled` に相当するカラム）も持たない。** 登録されているマスタはすべて有効として扱い、状態という概念を設けない。

したがって以下はいずれも行わない。

- マスタ検索一覧（MST-01）への「状態」列および状態による絞り込みの追加
- 登録・更新画面（MST-02・MST-05）への有効期間の入力欄の追加
- 基準日による有効・無効の判定

採用しない理由は以下のとおりである。

- **使わなくなったマスタは削除で対応する。** 本設計は物理削除を採用しており（§01.1.3）、誤登録の抹消と運用終了のどちらも削除で扱える。無効化を足すと「消す」と「止める」の 2 つの手段が並び、どちらを使うべきかの判断が利用者に委ねられる。
- **現時点で状態が効く場所が無い。** マスタを参照するテーブルは存在せず（§01.1.4）、本来の狙いである「基準日に有効なマスタだけを選択肢に出す」という効き先が存在しない。
- **状態はすべての画面へ波及する。** 一覧の表示、検索条件、登録・更新の入力、確認画面の表示項目、将来の参照側プルダウンのすべてに判定が加わり、画面ごとの仕様が増える。効き先が生まれていない段階で払うコストとしては大きい。

将来、参照側でマスタを選択するようになり、過去の参照を保ったまま新規の選択肢からは外したい、という要求が出た時点であらためて検討する。その時点では削除では要求を満たせない（削除すると過去の参照が「未設定」になる。§01.1.4）ため、有効期間の導入が正当化される。

#### 00.9.1.3 変更履歴の参照画面

**登録・更新・削除の履歴をデータベースへ保持する専用テーブルは設けず、履歴を参照する画面も作らない。** 追跡は §00.6.1 のとおりアプリケーションログのみで行う。

採用しない理由は以下のとおりである。

- **§00.6.1 の仕組みで、誤操作からの復旧に必要な情報は残っている。** 削除・更新の Server Action は変更前の値を引数に含め、`withOp` が操作名・`requestId`・実行者の `userId` とともに一度だけ記録する。「何を元の値へ戻せばよいか」はログから特定できる。
- **履歴テーブルは全 Server Action へ波及する。** 登録・更新・削除の 6 つすべてに履歴行の挿入が加わり、業務処理と同じトランザクションに含めるかどうかの判断も要る。マスタは変更頻度が低く、この重さに見合わない。
- **参照画面まで作ると画面が増える。** 一覧・詳細に加えて履歴の一覧と差分表示が必要になり、10 画面がさらに増える。

制約として、**ログの保持期間を超えると追跡できなくなる**点は許容する（§00.6.1）。監査要件として一定期間の変更履歴の保持が求められる案件では、本テンプレートをコピーした先で履歴テーブルを追加する。

### 00.9.2 本設計では扱わないもの

以下は必要性を否定していないが、本設計の対象外とする。

- CSVによる一括登録・一括更新（ダウンロードは §30.1 で設計する）
