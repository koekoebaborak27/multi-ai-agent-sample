## 40.1 概要

本機能は、マスタ分類のデータとマスタのデータを、1つのExcelファイルとしてダウンロードできる機能です。画面の「Excelを作成する」ボタンを押すと、裏側で少し時間をかけてファイルが作られ、できあがると履歴の一覧からダウンロードできるようになります。

この機能は、[`foundation_plan.md`](../../../foundation_plan.md) §5に定めた「`worker` は定期バッチ処理などを実装する場合や、一時的に重い処理を動かす場合のみ本番で起動する」という方針にもとづき、**worker を使った「依頼 → 裏側で生成 → あとで受け取る」という進め方を、実際に動くかたちで示す実装サンプル**でもあります。マスタCSVダウンロード（[`30_CSVダウンロード.md`](30_CSVダウンロード.md)）は当初 worker（Cloud Run Jobs）を使う作りでしたが、実際の処理が1〜2秒と軽く、Cloud Run Jobs の起動待ち（1〜3分）だけが目立ってしまったため、アプリの中で完結する方式に作り直した経緯があります（§40.12）。**本機能のExcel組み立てそのものも、実際には数秒で終わる軽い処理です。**それでも worker を通しているのは、この進め方の「型」を見本として1つ残しておくためです。詳しくは §40.12 に書いています。

### 40.1.1 用語のミニ辞書

| 用語 | 説明 |
|---|---|
| バッチ処理 | データをまとめて処理すること。画面を1回操作するたびに少しずつ処理するのではなく、一度に大量のデータをまとめて処理する |
| worker（ワーカー） | 時間のかかる処理を裏側で行うプログラム。画面を表示するプログラム（app）とは別に動く |
| Cloud Run Jobs | workerを本番環境で動かす仕組み。呼び出されるたびに1回だけ起動して処理を行い、終わったら停止する |
| キュー | 処理待ちの依頼を順番に並べておく列。依頼された順に処理される |
| ストレージ | 作成したファイルを保管しておく場所。本番ではSupabase Storageを使う |

## 40.2 出力するもの（Excelファイルの中身）

### 40.2.1 ファイル全体

| 項目 | 内容 |
|---|---|
| 形式 | `.xlsx`（Excel 2007以降の形式） |
| シート構成 | 1つのファイルに「マスタ分類」「マスタ」の2シート（この順） |
| ファイル名（保存用） | `master_info_YYYYMMDDHHmmss.xlsx`。日時は作成した時刻（Asia/Tokyo） |
| ファイル名（利用者に見せる名前） | 履歴一覧の表示は日本語（「マスタ情報_2026-08-17_10-30.xlsx」のような形）でよいが、ダウンロード時に実際に使われるファイル名はASCII文字だけで構成する |
| 生成に使う道具 | `exceljs`（新規に追加する依存）を使う |

ファイル名をASCII文字だけにする理由は、CSVダウンロード（§30.1.4.2）と同じです。日本語を含めると、ブラウザーごとに表示が変わってしまうことがあるためです。

**`exceljs` を採用する理由**: 1つのファイルに複数シートを持たせられること、見出し行の色・太さやセルの背景色（縞模様）、列の絞り込み（オートフィルター）、見出し行の固定といった見た目の指定に標準で対応していること、Node.js上で完結し追加のソフトをインストールする必要がないことによります。生成処理はworkerだけで行うため、appが配布する画面のプログラム（バンドル）には含めません。

### 40.2.2 「マスタ分類」シートの列

CSVダウンロード（§30.1.4.4）と同じ7列とします。同じマスタ情報を2つの形式（CSV・Excel）で出力するため、列をそろえておくことで、突き合わせたときに迷いません。

| 順 | 列名 | 値 |
|---|---|---|
| 1 | マスタ分類コード | `MasterCategory.id` を4桁ゼロ埋めした値 |
| 2 | マスタ分類名 | `MasterCategory.name` |
| 3 | 登録マスタ件数 | その分類に属するマスタの件数 |
| 4 | 登録日時 | `MasterCategory.createdAt` |
| 5 | 登録者 | `MasterCategory.createdBy`。値が無い場合は空欄 |
| 6 | 最終更新日時 | `MasterCategory.updatedAt` |
| 7 | 最終更新者 | `MasterCategory.updatedBy`。値が無い場合は空欄 |

### 40.2.3 「マスタ」シートの列

CSVダウンロード（§30.1.4.3）と同じ9列とします。

| 順 | 列名 | 値 |
|---|---|---|
| 1 | マスタ分類コード | `MasterCategory.id` を4桁ゼロ埋めした値 |
| 2 | マスタ分類名 | `MasterCategory.name` |
| 3 | マスタID | `Master.id` |
| 4 | マスタコード | `Master.code` |
| 5 | マスタ内容 | `Master.content` |
| 6 | 登録日時 | `Master.createdAt` |
| 7 | 登録者 | `Master.createdBy`。値が無い場合は空欄 |
| 8 | 最終更新日時 | `Master.updatedAt` |
| 9 | 最終更新者 | `Master.updatedBy`。値が無い場合は空欄 |

### 40.2.4 見た目・デザイン

単なるデータの書き出しではなく、見た目を整えたファイルとして出力します。実装する内容は次の4点です。

| 工夫 | 内容 |
|---|---|
| 見出し行の装飾 | 1行目（列名の行）を太字にし、背景色を付けて、通常のデータ行と見分けやすくする |
| 見出し行の固定＋オートフィルター | 下へスクロールしても列名の行が常に見えるようにする。あわせて列ごとに絞り込み・並べ替えができるようにする |
| タイトル行 | 各シートの最上部（列名の行より上）に、「マスタ分類一覧」「マスタ一覧」といったタイトル、出力日時、件数を表示する行を設ける |
| 縞模様 | データ行を1行おきに薄い背景色にして、行が多くても目で追いやすくする |

配色は既存の画面デザイン（[`DESIGN.md`](../../../../DESIGN.md)）で使っている基調色に合わせた、青系の見出し・薄灰色の縞模様とします。具体的な色コードは実装時に確定します。

### 40.2.5 値の書き方

- 日時はExcelの日付・時刻として認識される値で出力し、表示形式を `yyyy/mm/dd hh:mm:ss`（Asia/Tokyo固定）にします。文字列ではなく日付の値にすることで、Excel上で並べ替えやフィルターが正しく機能します。
- `null` の項目は**空欄**とします（CSVと同じ扱い。§30.1.4.5）。

## 40.3 マスタ情報Excel取得画面（MST-11）

### 40.3.1 画面の構成

画面は次の3つの要素で構成します。

1. 説明文: 「マスタ分類とマスタの情報をExcelファイルにまとめて出力します。作成には1〜3分ほどかかります。できあがったら、下の一覧の『ダウンロード』から取得してください」
2. 実行ボタン（§40.3.2）
3. 実行履歴一覧（§40.3.3）

### 40.3.2 実行ボタン

- ラベル: 「Excelを作成する」（「バッチ実行」のような専門用語は使わない）
- 押すと、依頼の登録（§40.5.2）が行われ、実行履歴一覧の先頭に「受付済み」の行がすぐに追加される
- 二重押下防止: ボタンは押した直後に短時間disabledにする（他の登録系ボタンと同じ方式）
- 実行中の依頼があっても、新しい依頼をブロックしない（複数の依頼を並べて出せる）。理由: 「前の実行が終わるまで待つ」という制約を作ると、失敗時に画面が固まった状態に見えてしまうため

### 40.3.3 実行履歴一覧

決定: 全ロールの実行履歴を表示し、ページングします（`env.PAGE_SIZE`。他の一覧と同じ仕組み）。新しい実行が上に来る順（依頼日時の降順）で並べます。

| 列     | 内容                                    |
| ----- | ------------------------------------- |
| 実行日時  | 依頼した日時                                |
| 状態    | 受付済み／作成中／完了／失敗（内部の状態値ではなく日本語ラベルを表示する） |
| 実行者   | 依頼した利用者名                              |
| 件数    | マスタ分類・マスタそれぞれの出力件数（完了後のみ表示）           |
| ファイル  | 完了時のみ「ダウンロード」リンクを表示する                 |
| エラー内容 | 失敗時のみ、利用者向けのメッセージを表示する                |

0件のとき（初回利用時）は「まだ実行履歴がありません」と表示します。

### 40.3.4 状態の見せ方と自動更新

CSVダウンロードでの失敗（§40.12。画面が結果を待つ作りにしたことが原因だった）を繰り返さないため、この画面は**結果を待ちません**。

- ボタンを押すと即座に「受付済み」の行が増え、利用者はそのまま画面を離れてよい
- 履歴一覧は10秒ごとに自動的に最新の状態を取得し直す。あわせて手動の「最新の状態にする」ボタンも置く
- 自動更新は、進行中（受付済み・作成中）の行が無くなったら停止する（無駄なアクセスを続けない）
- CSVダウンロードのような「一定時間で打ち切る」仕組みは設けない。結果は履歴として残るため、後から見に来れば必ず受け取れる

### 40.3.5 ダウンロードのリンク

完了した行の「ダウンロード」を押すと、その場でファイルのダウンロードが始まります。完了と同時に自動でダウンロードが始まる作りにはしません（数分後に利用者の意図しないタイミングでダウンロードが始まると驚かせてしまうため）。

### 40.3.6 画面へたどり着く道すじ

- マスタ管理画面（`/master`）の画面見出し「マスタ管理」の右側、**「マスタ分類の管理」ボタンの一つ左**に「マスタ管理情報Excel作成」ボタンを配置します。並び順は左から「マスタ管理情報Excel作成」「マスタ分類の管理」です
- 一覧領域（検索結果カード）の並び（「CSVダウンロード」「新規登録」）は変更しません
- サイドバーのナビゲーション（`@/shared/layout/nav-config`）には追加しません（§10.1.5と同じ理由。マスタ機能に付随する操作として扱う）
- URL: `/master/exports`。CSVのダウンロード窓口 `/api/master/exports/csv` と対応する名前にしています

## 40.5 処理の流れ

### 40.5.1 全体の流れ

```text
あなた                      画面                     裏方（worker）           ファイル置き場
  │                          │                          │                      │
  ├─「Excelを作成する」───────▶│                          │                      │
  │◀── 受付済みの行を表示 ─────┤                          │                      │
  │                          ├─ 順番待ちの列に依頼を追加 ──▶│                      │
  │                          │                          ├─ 少し時間をかけて ────┤
  │                          │                          │   Excelを組み立てる   │
  │                          │                          ├─ 完成したファイルを ──▶│
  │                          │                          │   保存               │
  │                          │◀── 「完了」に更新 ─────────┤                      │
  │◀── 一覧を自動更新 ─────────┤                          │                      │
  ├─「ダウンロード」──────────▶│                          │                      │
  │                          ├─ ファイルを取得 ───────────┼──────────────────────▶│
  │◀── ファイルを受け取る ─────┤                          │                      │
```

### 40.5.2 依頼

利用者が「Excelを作成する」を押すと、Server Actionが以下を行います。

1. 権限を確認する（§40.4。実質すべてのロールで許可）
2. 実行履歴（§40.6）に「受付済み」の行を作る
3. 順番待ちの列（キュー）へ依頼を積む
4. 即座に画面へ応答する（生成が終わるのを待たない。CSVでの失敗の教訓）

### 40.5.3 生成

workerが順番待ちの列から依頼を受け取り、次を行います。

1. 履歴の状態を「作成中」に更新する
2. 保持期限切れファイルの掃除を行う（§40.9。この依頼の生成そのものとは別の付随処理で、失敗しても依頼を止めない）
3. マスタ分類・マスタをデータベースから取得する
4. Excelファイルを組み立てる（§40.2）
5. ファイルをストレージへ保存する
6. 履歴の状態を「完了」に更新し、件数・保存先を記録する
7. 途中で失敗した場合は状態を「失敗」に更新し、エラー内容を記録する

### 40.5.4 受け取り

利用者が履歴一覧の「ダウンロード」を押すと、Route Handlerがストレージからファイルを取得し、その場でダウンロード応答を返します（§40.9のとおり、署名URLではなくアプリ経由で統一します）。

## 40.6 実行履歴の記録（データモデル）

新しいテーブル `MasterExcelExport` を追加します。旧`MasterExport`（CSV用。同期方式への変更に伴い削除済み）とは別のモデルとし、同じ名前は使いません。

```prisma
model MasterExcelExport {
  id           String    @id @default(cuid())
  status       String    @default("QUEUED") // QUEUED / RUNNING / READY / FAILED
  filePath     String?
  fileName     String?
  categoryRowCount Int?
  masterRowCount   Int?
  errorCode    String?
  requestedBy  String
  startedAt    DateTime?
  finishedAt   DateTime?
  expiresAt    DateTime?
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt

  @@index([createdAt])
}
```

旧`MasterExport`からの主な差分:

| 項目 | 扱い | 理由 |
|---|---|---|
| `target`（マスタ／マスタ分類の選択） | 持たない | 1回の実行で両方を1ファイルに出力するため |
| `categoryId` / `keyword`（絞り込み条件） | 持たない | 全件固定出力のため（画面から検索条件を渡さない） |
| `status` | 残す。受け取り後も行を削除しない | 履歴として残す仕様のため（CSVは受け取り時に行ごと削除していた） |
| `rowCount` | `categoryRowCount` / `masterRowCount` の2列に分割 | 履歴一覧に分類・マスタそれぞれの件数を表示するため |
| `requestedBy` | 残す（必須） | `User` へのFKは張らない規約（§01.1.4と同じ考え方）のため、一覧の「実行者」表示は都度 `User` テーブルを引いて名前を解決する |
| `startedAt` / `finishedAt` | 新規追加 | 実際にどれくらい時間がかかったかを記録できるようにする。workerサンプルとしての実測値を残す意味もある |
| `expiresAt` | 新規追加 | 保持期限の判定に使う（§40.9） |

## 40.7 workerの実行方式と本番構成

### 40.7.1 ローカルと本番の違い

| 環境 | 実行方法 |
|---|---|
| ローカル開発 | `pnpm worker` を手動で実行するか、常駐モードで起動しておく |
| 本番 | Cloud Run Jobs（`contract-worker`）を、依頼のたびにappから起動する |

### 40.7.2 単発モードの終了条件

**現状の `src/worker/index.ts` の `--once` は、キューを購読せず即座に終了する雛形です。** この機能の実装では、次のように作り替えます。

- 起動したら、順番待ちの列（キュー）に溜まっている依頼をすべて処理する
- 依頼を処理するたびに、次の依頼が無いか確認する
- 処理すべき依頼が無くなったら終了する（`process.exit(0)`）

Cloud Run Jobs は1回の起動で1回だけ処理して終わる仕組みで、起動そのものに1〜3分かかります。依頼1件ごとに起動し直すと待ち時間が積み上がるため、起動したついでに溜まっている依頼をまとめて片付けます。

### 40.7.3 タイムアウトと再試行の設定値

[`infra_design_07_CloudRunJobs構築.md`](../../99_infra/infra_design_07_CloudRunJobs構築.md) §07.1.3の設定値を、この機能の想定処理時間に合わせて見直します。

| 項目 | 既定値 | この機能での設定値 | 理由 |
|---|---|---|---|
| タスクのタイムアウト | 600秒 | **900秒（15分）** | Cloud Run Jobs の起動待ち（1〜3分）＋実際のExcel組み立て処理に余裕を持たせる。起動待ちが上振れした場合や、将来もっと時間のかかる処理を worker へ載せた場合の余裕として、900秒のまま据え置く（本番も設定済み） |
| メモリ | 512MiB | 512MiB（既定のまま） | §40.8の件数上限の範囲では不足しない想定。実装時に確認する |
| 最大再試行回数 | 3回 | 3回（既定のまま） | 再試行しても安全なように、処理を冪等にする（後述） |

**再試行があるため、処理を冪等にします。** workerは依頼を処理する前に履歴の `status` を確認し、`QUEUED` 以外（既に処理中・完了・失敗）であれば何もせず終了します。これにより、同じ依頼が2回実行されてもファイルが二重に作られません。

### 40.7.4 本番構成として必要になる作業

本番でこの機能を動かすには、次の作業が必要です。

- app→worker起動処理の作り直し: 依頼が登録されたら、appからCloud Run Jobsを起動するコードが必要
- `WORKER_INVOKE_MODE` 等の環境変数の再設定
- worker専用サービスアカウントへの差し替え
- Cloud Buildでworker用イメージも自動的に作り直す仕組み

## 40.8 件数上限とメモリ

件数が増えるほど、メモリ使用量も組み立てにかかる時間も増えるため、CSVダウンロードと同じ**10,000行**を上限とします（マスタ・マスタ分類の合計ではなく、それぞれの上限）。上限を超える場合は依頼自体を受け付けず、エラーを返します（§40.10）。

## 40.9 ファイルの保存先・保持期間・削除

- 保存先: Supabase Storage（既存の `@/shared/storage` をそのまま使う。新しい保存先は作らない）
- ダウンロード方式: **アプリ経由に統一します。** 署名URLは採りません。CSVダウンロードの設計（§30.1.5.3相当）で「ローカル開発では配信されず動かないため署名URLを採らない」と判断した経緯を踏襲します
- 保持期間: 作成から**7日間**とします。期限を過ぎたファイルは、次回いずれかの依頼が処理されたタイミングでworkerがまとめて削除します（Cloud Schedulerのような定期実行の仕組みは持ち込みません。§30.1.9.2と同じ方針）。定期実行を持ち込まない理由は、本プロジェクトが無料枠で動かせることを前提にしたテンプレートであり、掃除のためだけに専用の定期実行の仕組み（設定・管理の手間）を増やしたくないためです。またworkerは「依頼が来たときだけ動く」設計であり、期限が切れた瞬間ぴったりに削除されている必要もありません（数日遅れて片付いても実害はほぼ無い）
- 期限切れの行は履歴一覧に残しますが、「ダウンロード」リンクは無効化し、状態欄に「期限切れ」と表示します
- 削除するのはストレージ上のファイルの実体だけです。実行履歴の行そのものは削除せず、保存先の情報（ファイルパス・ファイル名）だけを空にします。1回の依頼処理でまとめて削除する件数には上限（50件）を設け、長期間依頼が無かった場合でも一度に大量のファイルを削除しに行かないようにします。上限を超えた分は、次回以降の依頼が処理されたタイミングで片付きます
- 削除の一部が失敗しても（ストレージ側の一時的な不調など）、依頼そのもの（Excelの生成）は失敗させません。掃除は本来の生成処理に付随するおまけの処理と位置づけており、失敗した対象は次回以降の依頼処理で改めて削除を試みます

## 40.10 エラー

| 状況 | エラーコード | 画面の扱い |
|---|---|---|
| 件数が上限を超える | `MASTER_EXCEL_EXPORT_LIMIT_EXCEEDED` | 依頼を受け付けず、エラーメッセージを表示する |
| 生成中に例外が発生した | `MASTER_EXCEL_EXPORT_FAILED` | 履歴の状態を「失敗」にし、一覧にエラー内容を表示する |
| 期限切れのファイルをダウンロードしようとした | `MASTER_EXCEL_EXPORT_EXPIRED` | 「ファイルの有効期限が切れています」と表示する |
| 対象の履歴が存在しない | `MASTER_EXCEL_EXPORT_NOT_FOUND` | 404として扱う |
| 作成が終わっていない、または失敗した履歴のURLを直接開いた | `MASTER_EXCEL_EXPORT_NOT_FOUND` | 404として扱う（一覧画面はリンク自体を出さないため、直接URLを開いた場合のみ発生する） |
| 未ログインでURLを直接開いた | `UNAUTHORIZED` | ログイン画面へ誘導する |

worker側の起動に失敗した場合（Cloud Run Jobsの起動API呼び出しが失敗した場合）は、依頼自体は失敗させず、警告としてログに記録するだけとします（CSVダウンロードの旧設計と同じ判断）。この場合、依頼は順番待ちの列に残ったままになるため、次にいずれかの依頼が処理されるタイミングで一緒に処理されます。

`00_共通.md` §00.6のエラー設計表には、本文確定後にこれらの行を追記します。

## 40.11 実行の記録（ログ）

依頼・生成・受け取りのそれぞれで、既存の境界ラッパーがログを残します。

- 依頼: `withOp`（Server Action）
- 生成: `withJob`（worker側の処理境界）
- 受け取り: `withRoute`（ダウンロードのRoute Handler）

保持期限切れファイルの掃除（§40.9）も、生成処理とは別に `withJob` で包んだ独立の処理境界とし、記録を1回残します。削除に失敗した対象があった場合は `MASTER_EXCEL_EXPORT_CLEANUP_FAILED` としてログにだけ記録し、依頼の処理結果（画面上の状態）には影響しません。

追加の仕組みは持たず、他機能と同じ記録方針に揃えます。

## 40.12 CSVダウンロードとの違い（なぜここでは非同期方式を採るか）

[`30_CSVダウンロード.md`](30_CSVダウンロード.md) §30.1.9（同期方式へ作り直した理由）と対になる節です。CSVは実際の処理が1〜2秒と軽く、Cloud Run Jobs の起動待ち（1〜3分）だけが目立ったため、アプリの中で完結する同期方式へ作り直しました。

**本機能のExcel組み立ても、実際には数秒で終わる軽い処理です。この点はCSVと同じで、「起動待ちだけが目立つ」という指摘は本機能にもそのまま当てはまります。** それでも非同期方式（worker）を採っているのは、worker を使った「依頼 → 生成 → 受け取り」という進め方そのものを、動く見本として1つ残しておくためです。

当初は、生成処理の中に意図的な待ち時間（約2分）を入れ、実際のデータ件数に関わらず数分かかるようにしていました。「時間のかかる処理を worker に任せる例」に見せるためでしたが、**わざと待たせる仕組みがあること自体が、Cloud Run Jobs の起動待ちと区別できず混乱の元になった**ため、2026-08-18に削除しました。削除しても起動待ち（1〜3分、こちらでは短くできない）は残るため、体感が速くなるわけではありません。

| 観点 | CSVダウンロード（同期方式） | マスタ情報Excel取得（非同期方式） |
|---|---|---|
| 実処理時間 | 1〜2秒（実測） | 数秒程度（Excelの組み立てのみ。実測は未確認） |
| 利用者から見た待ち時間 | ほぼ無し | 1〜3分（ほぼ Cloud Run Jobs の起動待ち） |
| 待ち時間の受け入れやすさ | 待たせると失敗と感じられる | 数分かかることを画面上で明示し、履歴から後で受け取れる |
| 履歴画面 | 無し（その場で受け取るだけ） | 有り（過去の実行を一覧できる） |
| 位置づけ | Cloud Run Jobs に向かない処理の実例（同期方式へ作り直した経緯付き） | 実処理は軽いが、worker を使った進め方の「型」を示す実装サンプル |

利用者の快適さだけを考えるなら、本機能もCSVと同じくアプリの中で完結させる方が優れています。それを承知のうえで、テンプレートとしての見本を残すことを優先しています。

## 40.13 この設計で扱わないもの

- Excelファイルの取り込み（インポート）機能は設けない
- 生成したExcelの書式を利用者がカスタマイズする機能は設けない
- 定期的な自動実行（毎日決まった時刻に作る、など）は設けない。あくまで利用者がボタンを押した時だけ作る
- 完成時のメール通知は設けない。履歴一覧を見に来る運用とする

## 40.14 テスト方針

`00_共通.md` §00.8、[`30_CSVダウンロード.md`](30_CSVダウンロード.md) §30.2の粒度に合わせ、次の区分で確認する。

- Excelの組み立て（純粋関数）: シート構成、列の順序・内容、見出し行の装飾、日時の形式、`null` の空欄化
- 依頼（Server Action）: 履歴行が作られる、キューに積まれる、応答が即座に返る
- worker側の生成: 状態が正しく遷移する（受付済み→作成中→完了／失敗）、冪等性（同じ依頼を2回処理しても二重に生成されない）、件数上限を超える依頼を拒否する
- ダウンロード: 完了済みファイルを取得できる、期限切れファイルを拒否する、存在しない履歴を404として扱う
- 権限: 全ロールが実行・閲覧・ダウンロードできる
