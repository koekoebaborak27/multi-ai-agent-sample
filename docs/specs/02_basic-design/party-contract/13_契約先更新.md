## 13.1 契約先更新画面（PTY-05）

### 13.1.1 表示・入力項目

| 項目  | UI部品     | 編集可否 | 入力仕様                    |
| --- | -------- |:----:| ----------------------- |
| 名称  | テキストボックス | 可    | §11.3と同じ。初期値は現在の名称      |
| 分類  | プルダウン    | 可    | §11.3と同じ。初期値は現在の分類（未設定可） |
| 連絡先 | テキストボックス | 可    | §11.3と同じ。初期値は現在の連絡先     |

**この画面では3項目すべてを変更できる。** `updatedAt` と `updatedBy` はシステムが設定する。入力欄は §11.1 の新規登録画面と共通のコンポーネント（`party-form-fields.tsx`）を使う。

### 13.1.2 ボタン

| ボタン   | 動作                                            |
| ----- | ----------------------------------------------- |
| 確認する  | 入力内容を検証し、問題があれば画面上にエラーを表示する。問題がなければ契約先確認画面へ更新モードで進む。データベースの更新は行わない |
| キャンセル | 入力内容を破棄し、対象契約先の詳細画面へ戻る                        |

## 13.2 更新時の競合

入力画面を表示した時点の `updatedAt` を、実行時に送信する。データベースに保存されている現在の `updatedAt` と一致しない場合は更新せず、以下のメッセージを表示する。

```text
ほかの利用者によって更新されています。最新の内容を確認してから、もう一度操作してください。
```

この楽観的排他制御は、契約先更新（PTY-05）と削除（§14.3）の双方に同じ方式で適用する（マスタ機能の `updatedAt` 比較と同じ方式。[`master/13_マスタ更新.md` §13.2](../master/13_マスタ更新.md#132-更新変更時の競合)）。

### 13.2.1 更新モードの実行処理

1. 対象契約先が現在も存在することを確認する。存在しない場合は `PARTY_NOT_FOUND`。
2. 変更後の名称・分類ID・連絡先をサーバー側で再検証する。
3. 入力画面を表示した時点の `updatedAt` と、データベースに保存されている現在の `updatedAt` を比較する。一致しない場合は `PARTY_CONCURRENT_UPDATE`。
4. 変更後の契約先分類マスタが現在も存在することを確認する（未選択の場合は確認不要）。存在しない場合は `MASTER_REFERENCE_INVALID`。
5. 名称・分類ID・連絡先を更新し、`updatedBy` に実行した利用者のユーザーIDを設定する。`createdBy` は変更しない。
6. 対象契約先の詳細画面へ遷移し、更新完了メッセージを表示する。

変更前と変更後の値が完全に同じ場合も実行を許可し、`updatedAt` と `updatedBy` だけが更新される（マスタ機能と同じ考え方。§11.2.4相当）。

### 13.2.2 テスト方針

- 名称・分類・連絡先をそれぞれ単独で更新できる。
- 3項目を同時に更新できる。
- 分類を未設定へ変更できる（既に設定されている分類を外せる）。
- 存在しない契約先の更新を拒否する（`PARTY_NOT_FOUND`）。
- 存在しない契約先分類マスタIDへの変更を拒否する（`MASTER_REFERENCE_INVALID`）。
- `updatedAt` が異なる場合に同時更新エラーとなる（`PARTY_CONCURRENT_UPDATE`）。
- 更新で `updatedBy` だけが更新され、`createdBy` は変わらない。
- 確認画面を表示しただけではデータベースが更新されない。
- 値を変えずに実行しても拒否されない。
