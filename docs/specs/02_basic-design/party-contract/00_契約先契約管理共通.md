## 00.1 概要

本機能は、契約先（取引先）と契約を検索・参照・登録・更新・削除する機能である。現在は一覧画面に新規登録フォームが埋め込まれているだけで、詳細・編集・削除の画面が無い。これを**マスタ管理機能（[`docs/specs/02_basic-design/master/`](../master/README.md)）と同じ画面構成**（検索一覧→詳細→編集/新規登録は別ページ→削除）に揃える。

画面の起点は `/parties`（契約先）と `/contracts`（契約）とし、それぞれ以下の機能を提供する。

- 契約先／契約の検索および一覧表示（検索・絞り込み・並び替え・ページング）
- 契約先／契約の新規登録（一覧とは別ページ）
- 登録済み契約先／契約の詳細表示
- 契約先／契約の更新
- 登録・更新内容の実行前確認
- 契約先／契約の削除

契約先と契約は別々の画面群として提供する。契約は登録時に契約先を1件選択して紐づける（マスタ分類とマスタのような親子関係ではなく、契約が契約先を参照する関係）。**契約先の詳細画面には、紐づく契約の一覧を表示しない**（要件定義で対象外と確定済み）。

登録・更新の入力画面ではデータベースを更新せず、確認画面で「実行」ボタンが押された時点で初めて反映する（マスタ管理機能と同じ方式。§11.2・§21.2）。

削除は**物理削除**とする。論理削除は採用しない（マスタ管理機能と同じ理由。[`master/01_データベース.md`](../master/01_データベース.md#0113-制約) 参照）。**契約先は、紐づく契約が1件でも存在する場合は削除できない**（§14.1）。契約自体には、同様の削除制限を設けない。契約に紐づく契約条項（`ContractItem`）は本設計・現行の画面のどちらでも登録・参照する手段が無いため（§00.9.2）。

Excel出力・CSVダウンロードは対象外とする（§00.9.2）。

## 00.2 用語

| 名称   | 説明                                        | 例                         |
| ---- | ----------------------------------------- | -------------------------- |
| 契約先  | 契約の相手方となる取引先。名称・分類・連絡先を持つ                 | 株式会社サンプル                   |
| 契約先分類 | 契約先を分類するマスタ分類コード `CONTRACT_COMPANY_TYPE` 配下のマスタ | 法人、個人 |
| 契約   | 契約先と結ぶ個々の契約。契約名・期間・状態・分類を持つ               | 業務委託契約2026年度               |
| 契約分類 | 契約を分類するマスタ分類コード `CONTRACT_TYPE` 配下のマスタ    | 業務委託、保守契約                  |
| 契約の状態 | 契約の進行状況を表す固定の3値（`DRAFT` / `ACTIVE` / `TERMINATED`） | 下書き／有効／終了 |

## 00.3 権限

既存のロールに対する操作権限は、マスタ管理機能と同じ考え方（[`master/00_マスタ管理共通.md` §00.3](../master/00_マスタ管理共通.md#003-権限)）で揃える。

| 操作            | ADMIN | OPERATOR | VIEWER |
| ------------- |:-----:|:--------:|:------:|
| 契約先の検索・一覧表示   | 可     | 可        | 可      |
| 契約先の詳細表示      | 可     | 可        | 可      |
| 契約先の新規登録      | 可     | 可        | 不可     |
| 契約先の更新        | 可     | 可        | 不可     |
| 契約先の削除        | 可     | 可        | 不可     |
| 契約の検索・一覧表示    | 可     | 可        | 可      |
| 契約の詳細表示       | 可     | 可        | 可      |
| 契約の新規登録       | 可     | 可        | 不可     |
| 契約の更新         | 可     | 可        | 不可     |
| 契約の削除         | 可     | 可        | 不可     |

VIEWERには「新規登録」ボタン、「編集する」ボタンおよび「削除」ボタンを表示しない。画面上の非表示だけでなく、Server Actionでも書き込み権限を検証し、不正な直接リクエストを拒否する。判定には既存の `canWrite`（`@/shared/constants/roles`）を使用する（現行の `party`/`contract` の登録・更新・削除Server Actionで既に実施済みの仕組みをそのまま使う）。

| ------ | --------- | ----------------------------- | ---------------------- |

| PTY-02 | 契約先新規登録画面 | `/parties/new`                | 新しい契約先の入力              |
| PTY-03 | 契約先確認画面   | `/parties/new` または `/parties/[partyId]/edit` | 新規登録または更新する内容の確認 |

| PTY-05 | 契約先更新画面   | `/parties/[partyId]/edit`     | 名称・分類・連絡先の変更           |
| CTR-01 | 契約検索一覧画面  | `/contracts`                  | 検索条件の指定と契約一覧の表示        |
| CTR-02 | 契約新規登録画面  | `/contracts/new`              | 新しい契約の入力               |
| CTR-03 | 契約確認画面    | `/contracts/new` または `/contracts/[contractId]/edit` | 新規登録または更新する内容の確認 |
| CTR-04 | 契約詳細画面    | `/contracts/[contractId]`     | 登録済み契約の詳細表示と削除         |
| CTR-05 | 契約更新画面    | `/contracts/[contractId]/edit` | 契約名・期間・状態・分類の変更        |

PTY-03／CTR-03は、それぞれ新規登録と更新で共通利用する論理画面とする。独立した画面ルートは作成せず、新規登録の場合はPTY-02／CTR-02、更新の場合はPTY-05／CTR-05のコンポーネントを確認状態へ切り替えて表示する（マスタ管理機能のMST-03と同じ方式。[`master/00_マスタ管理共通.md` §00.4](../master/00_マスタ管理共通.md#004-画面一覧)）。入力値をURLへ含めないことで、入力値がブラウザー履歴やアクセスログへ残ることを防ぐ。

削除の確認は独立した画面を設けず、PTY-04およびCTR-04の上に表示する確認ダイアログで行う（§14.2・§24.1）。

削除ボタンは一覧画面（PTY-01・CTR-01）には配置せず、**詳細画面（PTY-04・CTR-04）だけに配置する**。削除の前に必ず対象の詳細を開く導線となり、一覧上の誤操作を防ぐ。「編集する」ボタンも同じ理由で詳細画面だけに配置する（マスタ管理機能と同じ方針）。**現行の一覧テーブルに埋め込まれている削除ボタンは、この設計に合わせて削除する。**

契約詳細画面（CTR-04）には、表示している契約先名から契約先詳細画面（PTY-04）へのリンクを置く。契約先詳細画面（PTY-04）から契約への逆方向のリンクは置かない（紐づく契約一覧を表示しない、という要件定義の決定による）。

## 00.6 エラー設計

| エラーコード                  | HTTPステータス | 発生条件                             | 利用者向けメッセージ例                       |
| ----------------------- | ---------:| -------------------------------- | --------------------------------- |
| `VALIDATION_ERROR`      | 422       | 必須、文字数、形式に違反した                    | 入力内容を確認してください                     |
| `PARTY_NOT_FOUND`       | 404       | 対象契約先が存在しない（既に削除された場合を含む）        | 対象の契約先が見つかりません                    |
| `PARTY_CONCURRENT_UPDATE` | 409     | ほかの利用者が先に契約先を更新・削除した             | ほかの利用者によって更新されています。最新の内容を確認してください |
| `PARTY_HAS_CONTRACTS`   | 409       | 削除対象の契約先に紐づく契約が1件以上存在する          | この契約先には *N* 件の契約が登録されているため削除できません。先に契約を削除してください |
| `CONTRACT_NOT_FOUND`    | 404       | 対象契約が存在しない（既に削除された場合を含む）         | 対象の契約が見つかりません                     |
| `CONTRACT_CONCURRENT_UPDATE` | 409  | ほかの利用者が先に契約を更新・削除した              | ほかの利用者によって更新されています。最新の内容を確認してください |
| `MASTER_REFERENCE_INVALID` | 422    | 選択した契約先分類・契約分類が、対象の分類コード配下に存在しない（既存のマスタ機能のエラーを流用） | 選択した内容が見つかりません。画面を更新してから選び直してください |
| `FORBIDDEN`              | 403       | 書き込み権限がない利用者が登録・更新・削除した          | この操作を行う権限がありません                   |
| `UNAUTHORIZED`           | 401       | 未ログインで操作した                        | ログインが必要です                         |

`PARTY_NOT_FOUND`・`PARTY_CONCURRENT_UPDATE`・`PARTY_HAS_CONTRACTS`・`CONTRACT_NOT_FOUND`・`CONTRACT_CONCURRENT_UPDATE` は、マスタ機能の `MASTER_NOT_FOUND` 等と同じく `src/modules/party/service.ts`・`src/modules/contract/service.ts` 内で直接 `AppError` を組み立てる（共通の `Errors` ファクトリは使わない。汎用の `NOT_FOUND`/`CONFLICT` では発生源をエラーコードだけから特定できないため）。`MASTER_REFERENCE_INVALID` は既存の `masterService.assertMasterInCategoryCode` がそのまま送出するものを流用する。

業務処理では上記のエラーを送出する。業務コードに個別のログ出力や包括的な `try/catch` は記述せず、Server Actionを `withOp` でラップして処理境界で一度だけ記録する（マスタ機能と同じ方針。§00.6.1）。

### 00.6.1 削除・変更操作の記録

物理削除では削除された行が残らず、更新では上書き前の値が残らない。マスタ機能と同じく、記録はアプリケーションログ（`withOp` によるServer Action引数の出力）でのみ行う（[`master/00_マスタ管理共通.md` §00.6.1](../master/00_マスタ管理共通.md#0061-削除変更操作の記録)と同じ考え方）。

| 操作            | Server Actionの入力に含める値                                     |
| ------------- | ----------------------------------------------------------- |
| 契約先の削除        | 契約先ID、`updatedAt`、契約先名                                     |
| 契約の削除         | 契約ID、`updatedAt`、契約名                                       |
| 契約先の更新（PTY-05） | 契約先ID、`updatedAt`、変更前の名称・分類ID・連絡先、変更後の名称・分類ID・連絡先          |
| 契約の更新（CTR-05）  | 契約ID、`updatedAt`、変更前の契約名・期間・状態・分類ID、変更後の契約名・期間・状態・分類ID |

- 変更前の値は確認画面が保持しているものをそのまま送信する。
- 可否判定にこれらの値を使用しない。判定に使うのは対象IDと `updatedAt`、および変更後の入力値だけとする（§13.2・§14.3・§23.2・§24.2）。

## 00.7 モジュール構成

既存のfeature-modular規約に従い、`src/modules/party` と `src/modules/contract` 内で完結させる（新しいモジュールは作らない。既存モジュールへ画面・確認・楽観ロックの機能を追加する形になる）。

```text
src/modules/party/
├─ actions.ts               # 登録・更新・削除の3つのServer Action（既存に確認・楽観ロックを追加）
├─ service.ts                # 検索、登録・更新ユースケース、削除条件の判定
├─ repository.ts             # Prismaを使用したデータベース操作（検索条件・件数カウントを追加）
├─ validation.ts             # Zodを使用した入力値検証（updatedAtを追加）
├─ types.ts                  # 一覧・詳細・検索条件・選択肢の型定義
├─ index.ts
└─ ui/
   ├─ party-search-form.tsx      # PTY-01の検索条件フォーム
   ├─ party-table.tsx            # PTY-01の一覧テーブル（削除ボタンを撤去し「詳細」リンクのみにする）
   ├─ party-form-fields.tsx      # 名称・分類・連絡先の入力欄（新規登録・更新で共用）
   ├─ party-create-form.tsx      # PTY-02
   ├─ party-update-form.tsx      # PTY-05
   ├─ party-confirmation.tsx     # PTY-03（新規登録・更新で共用）
   ├─ party-detail.tsx           # PTY-04
   └─ party-delete-dialog.tsx    # PTY-04の削除確認ダイアログ

src/modules/contract/
├─ actions.ts
├─ service.ts
├─ repository.ts
├─ validation.ts
├─ types.ts
├─ index.ts
└─ ui/
   ├─ contract-search-form.tsx
   ├─ contract-table.tsx         # 削除ボタンを撤去し「詳細」リンクのみにする
   ├─ contract-form-fields.tsx
   ├─ contract-create-form.tsx
   ├─ contract-update-form.tsx
   ├─ contract-confirmation.tsx
   ├─ contract-detail.tsx
   ├─ contract-delete-dialog.tsx
   └─ party-combobox.tsx         # 契約先を検索して選ぶコンボボックス（検索条件・登録・更新フォームで共用）
```

画面ルートは以下とする。

```text
src/app/(main)/parties/
├─ page.tsx              # PTY-01
├─ new/
│  └─ page.tsx           # PTY-02（内部でPTY-03の確認状態も扱う）
└─ [partyId]/
   ├─ page.tsx            # PTY-04
   └─ edit/
      └─ page.tsx         # PTY-05（内部でPTY-03の確認状態も扱う）

src/app/(main)/contracts/
├─ page.tsx              # CTR-01
├─ new/
│  └─ page.tsx           # CTR-02
└─ [contractId]/
   ├─ page.tsx            # CTR-04
   └─ edit/
      └─ page.tsx         # CTR-05
```

`party-confirmation.tsx` は新規登録と更新で共通利用し、処理モードに応じて表示項目、実行するServer Actionおよび戻り先を切り替える（マスタ機能の `master-confirmation.tsx` と同じ方式。§11.2・§21.2）。`contract-confirmation.tsx` も同様。

`party-form-fields.tsx` は、名称・分類・連絡先という同じ3項目を扱う入力欄で、新規登録・更新の両フォームから使用する（マスタ機能の `master-create-form.tsx`/`master-update-form.tsx` の共通化と同じ考え方）。`contract-form-fields.tsx` も同様に契約名・期間・状態・分類を扱う（契約先の選択欄は新規登録時のみ表示し、更新時は現在の契約先を読み取り専用で表示する。§23.1）。

`party-delete-dialog.tsx`・`contract-delete-dialog.tsx` は、確認ダイアログの表示と削除用Server Actionの呼び出しを担う。`AlertDialog` の構造、二重送信の防止および実行中の表示は、マスタ機能の削除ダイアログと同じ実装方針に従う（[`master/14_マスタ削除.md` §14.1.2](../master/14_マスタ削除.md#1412-ダイアログの仕様)）。

`party-combobox.tsx` は、契約先が多数登録された場合でも入力して絞り込めるよう `Command`（combobox）を使う（`DESIGN.md` §3「選択肢が多い／検索したい」）。本テンプレートには未導入のため、実装時に `pnpm dlx shadcn@latest add command popover` で追加する。一覧取得は既存の `partyService` に選択肢専用の軽量な取得処理（id・名称のみ）を追加し、クライアント側で文字列の絞り込みを行う（新しいRoute Handlerは作らない）。

`actions.ts` が公開するServer Actionは、契約先・契約それぞれ**3つ**（登録・更新・削除）のままとする。処理ごとに入力・検証・権限確認が異なるため、1つのServer Actionへまとめない。

依存方向は `app → modules/party・modules/contract → shared`（および `modules/party・modules/contract → modules/master`、既存の分類解決と同じ）とし、Prismaは `repository.ts` 以外から直接使用しない。データベースへアクセスするファイルには `server-only` を適用する。

## 00.8 テスト方針

テストは対象ファイルの隣へコロケーションする。機能ごとの確認項目は各機能のファイルの「テスト方針」に相当する節にある。ここには全機能に共通する権限の確認だけを置く。

### 00.8.1 権限

- VIEWERは契約先・契約の一覧と詳細を参照できる。
- VIEWERには新規登録、更新および削除ボタンが表示されない。
- VIEWERによるServer Actionの直接実行を、契約先・契約それぞれの**書き込み系3つ**のServer Actionすべてで拒否する。
- ADMINとOPERATORは登録、更新および削除を実行できる。

## 00.9 対象外

### 00.9.1 採用しないと決めたもの

要件定義（[`docs/todo/history/2026-08-w3.md`](../../../todo/history/2026-08-w3.md#2026-08-19-契約先契約の管理画面整備の要件定義を実施)）およびこの設計で、検討したうえで設けないと決めたものを記す。

- **契約先詳細画面に紐づく契約一覧を表示しない。** 要件定義で対象外と確定済み。
- **Excel出力・CSVダウンロードは対象外。** マスタ機能にある同種の機能（[`master/30_CSVダウンロード.md`](../master/30_CSVダウンロード.md)・[`master/40_マスタ情報Excel取得.md`](../master/40_マスタ情報Excel取得.md)）は、この設計の対象に含めない。
- **契約の削除に、契約先削除のような依存関係チェックは設けない。** 契約に紐づく `ContractItem`（契約条項）は、登録・参照する画面がどちらのモジュールにも存在しないため（§00.9.2）、契約を削除しても外部キー制約に抵触しない。

### 00.9.2 本設計では扱わないもの

- **契約条項（`ContractItem`）の画面。** Prismaスキーマには存在するが、登録・参照する画面はまだ無く、本設計でも追加しない。将来 `ContractItem` の画面を作る際は、契約削除時の依存関係チェック（§00.9.1）をあらためて検討する。
- **契約先コンボボックスのサーバー側検索。** §00.7で述べたとおり、契約先の選択肢はクライアント側で絞り込む。契約先の登録件数が数千件規模になり性能上の問題が出た場合は、サーバー側で検索するAPIへの切り替えを検討する。
