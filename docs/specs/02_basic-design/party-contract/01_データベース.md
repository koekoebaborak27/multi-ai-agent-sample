# データベース設計

ER概要・Prismaモデルの変更点・制約。全機能が参照する。

契約先・契約管理機能 基本設計書の一部。全体の索引は [`README.md`](README.md)、共通の前提は [`00_契約先契約管理共通.md`](00_契約先契約管理共通.md) を見ること。

## 01.1 データベース設計

### 01.1.1 ER概要

```text
Party 1 ───── N Contract
MasterCategory(CONTRACT_COMPANY_TYPE) 1 ───N Master ← Party.companyTypeMasterId が参照（FK無し）
MasterCategory(CONTRACT_TYPE)         1 ───N Master ← Contract.categoryMasterId が参照（FK無し）
```

`Party`・`Contract` のテーブル自体は既存のまま変更しない。今回追加するのは、詳細画面（§12.1・§22.1）に表示する登録者・更新者の記録用カラムだけである。

### 01.1.2 Prismaモデルの変更点

既存モデル（`prisma/schema.prisma`）に `createdBy` / `updatedBy` を追加する。マスタ機能の `Master`／`MasterCategory` と同じ形（[`master/01_データベース.md` §01.1.2](../master/01_データベース.md#0112-prismaモデル案)）に揃える。

```prisma
model Party {
  id                  String   @id @default(cuid())
  name                String
  companyTypeMasterId Int?
  contactInfo         String?
  createdAt           DateTime @default(now())
  createdBy           String?  // 追加。登録した利用者の User.id（FK は張らない）
  updatedAt           DateTime @updatedAt
  updatedBy           String?  // 追加。最後に更新した利用者の User.id（FK は張らない）

  contracts Contract[]
}

model Contract {
  id               String    @id @default(cuid())
  partyId          String
  party            Party     @relation(fields: [partyId], references: [id])
  title            String
  startDate        DateTime?
  endDate          DateTime?
  status           String    @default("DRAFT")
  categoryMasterId Int?
  createdAt        DateTime  @default(now())
  createdBy        String?   // 追加
  updatedAt        DateTime  @updatedAt
  updatedBy        String?   // 追加

  items ContractItem[]

  @@index([partyId])
}
```

`ContractItem` は変更しない（§00.9.2）。

この変更は、既存の列を追加するだけの後方互換なマイグレーションである（`NULL` 許容のため、既存行の値は `NULL` のまま扱える）。マイグレーションの作成・適用は製造工程（TODO 3〜4番）で行う。運用は [`docs/prisma_operations.md`](../../../prisma_operations.md) の手順に従う。

`createdBy` と `updatedBy` の設定・利用方針は、マスタ機能とまったく同じである。

- 登録・更新を実行した利用者の `User.id` を保持する。外部キー制約は設定しない（利用者が削除された後も記録として残すため）。
- Server Actionが現在の利用者を取得してサービス層へ渡し、リポジトリが書き込む。値を特定できない場合は `null` とする。
- 画面には利用者IDをそのまま表示する（表示名の解決は行わない。値が無い場合は「—」）。

### 01.1.3 制約

| 対象         | 制約                                 |
| ---------- | ---------------------------------- |
| 契約先名称      | 1文字以上200文字以内（既存の `createPartySchema` のまま） |
| 契約先連絡先     | 任意、500文字以内（既存のまま）                   |
| 契約名        | 1文字以上200文字以内（既存のまま）                  |
| 契約と契約先の関係  | 存在する契約先だけを参照可能（既存のFK制約 `Contract.partyId` のまま） |
| 契約先の削除     | 紐づく契約が1件でも存在する場合は削除できない（**新規。§14.1**） |

削除は**物理削除**とする。論理削除を採用しない理由はマスタ機能と同じ（[`master/01_データベース.md` §01.1.3](../master/01_データベース.md#0113-制約)）。

契約先の削除制限は、`Contract.partyId` に既に張られている外部キー制約（`onDelete` 未指定 = 参照行が残っている限り削除を拒否する）を最終的な保証として使う。アプリケーション側では削除前に契約件数を確認し、外部キー制約違反（`P2003`）が発生した場合も `PARTY_HAS_CONTRACTS` へ変換する。マスタ分類の削除（[`master/24_マスタ分類削除.md` §24.3](../master/24_マスタ分類削除.md#243-削除の実行処理)）と同じ二重の考え方である。

### 01.1.4 マスタを参照する項目の扱い

`Party.companyTypeMasterId`・`Contract.categoryMasterId` は既存のマスタ参照カラムであり、扱いはマスタ機能の規約（[`master/01_データベース.md` §01.1.4](../master/01_データベース.md#0114-マスタを参照するテーブルの扱い)）のまま変更しない。参照先のマスタが削除された場合は画面上「未設定」と表示する（既存の `partyService`/`contractService` の `toSummary` で実装済み）。
