## 01.1 変更の概要

| 対象 | 変更 |
|---|---|
| `User.email` | 同じアドレスを2人以上が持てないようにする（`@unique`） |
| `PasswordResetToken` | 新規追加。再設定用URLの発行記録 |
| `EmailChangeToken` | 新規追加。本人によるメールアドレス変更の申し込み記録 |

## 01.2 User の変更

```prisma
model User {
  // ...既存の項目は変更しない
  email String? @unique
}
```

- **必須にはしない**（`String?` のまま）。すでにメールアドレスが空の利用者がいるため。PostgreSQL では空（NULL）は重複とみなされないので、空のまま複数人が残っていても支障はない
- **新規登録のときだけ、アプリの入力チェックで必須にする**（→ [`20_メールアドレス管理.md`](20_メールアドレス管理.md#201-管理者による登録と変更)）
- 大文字小文字の違いで別人にならないよう、**保存前に小文字へ揃える**。照合もすべて小文字で行う

## 01.3 PasswordResetToken

再設定用URLの発行記録。

```prisma
/// パスワード再設定用URLの発行記録。URLの合言葉はそのまま保存せず、要約値だけを持つ。
model PasswordResetToken {
  id        String    @id @default(cuid())
  userId    String // 対象の利用者（User.id。FK は張らない。既存方針に合わせる）
  tokenHash String    @unique // 合言葉の要約値（SHA-256の16進文字列）
  expiresAt DateTime // 有効期限（発行から30分後）
  usedAt    DateTime? // 使った日時。null なら未使用
  createdAt DateTime  @default(now())

  @@index([userId, createdAt]) // 24時間の発行回数を数えるために使う
}
```

- **1件も削除しない。** 使い終わった記録も残す。24時間の発行回数を数えるために必要
- 期限切れの古い記録の掃除は今回作らない（→ [`00_パスワードリセット共通.md`](00_パスワードリセット共通.md#009-対象外)）

## 01.4 EmailChangeToken

本人がメールアドレスを変更するときの申し込み記録。

```prisma
/// 本人によるメールアドレス変更の申し込み。確認用URLが開かれるまで User.email は変えない。
model EmailChangeToken {
  id        String    @id @default(cuid())
  userId    String // 申し込んだ利用者（User.id）
  newEmail  String // 変更先のメールアドレス（小文字へ揃えて保存する）
  tokenHash String    @unique
  expiresAt DateTime
  usedAt    DateTime?
  createdAt DateTime  @default(now())

  @@index([userId, createdAt])
}
```

- ここに入っているだけでは**まだ誰のものでもない**。確認用URLが開かれた時点で `User.email` を書き換える
- 書き換えの直前にもう一度、**そのアドレスが他の利用者に使われていないか**を確かめる（申し込みから確認までの間に他の人が登録した場合に備える）

## 01.5 合言葉の保存方法

- 合言葉は**32バイトの乱数**を、URLに使える文字だけで表した文字列にする（`crypto.randomBytes(32)` を base64url へ変換）
- データベースには**SHA-256の要約値**だけを保存する。元の文字列は保存しない
- 照合は「受け取った合言葉を同じ方法で要約し、その値で検索する」で行う

> **なぜパスワードと同じ方式（Argon2）にしないのか。** パスワードは人が決める短い文字列なので、総当たりを遅くする仕組みが要る。合言葉は機械が作る32バイトの乱数で総当たりが現実的でなく、逆に検索のたびに時間のかかる計算をすると、URLを開くたびに全件と突き合わせる必要が生じて実用に耐えない。要約値をそのまま検索できる SHA-256 を使う。

## 01.6 マイグレーションの手順

`prisma/AGENTS.md` と [`prisma_operations.md`](../../../prisma_operations.md) に従う。

1. `User.email` へ `@unique` を足す前に、**同じアドレスが2人以上に入っていないか**を確認する

   ```sql
   SELECT lower(email), count(*) FROM "User"
   WHERE email IS NOT NULL GROUP BY lower(email) HAVING count(*) > 1;
   ```

2. 重複があれば先に手作業で解消する（片方を空にする）
3. 小文字へ揃える

   ```sql
   UPDATE "User" SET email = lower(email) WHERE email IS NOT NULL AND email <> lower(email);
   ```

4. `prisma migrate dev --name add_password_reset` でマイグレーションを作る（`User.email` の一意制約と新しい2つのテーブルをまとめて1本にする）
5. 本番へは `prisma migrate deploy` で適用する（→ [`docs/specs/99_infra/` §09.1.2](../../99_infra/infra_design_10_構築後の運用.md#1012-データベースの構造を変更する)）
