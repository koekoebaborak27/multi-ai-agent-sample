## 00.1 概要

本機能は、ダッシュボード（トップ画面）に表示する「お知らせ」を、`ADMIN`・`OPERATOR`が画面から登録・更新・削除できるようにする機能である。

- 全ロールが、トップ画面で公開中のお知らせを閲覧できる（→ [`10_トップ画面お知らせ表示.md`](10_トップ画面お知らせ表示.md)）。
- `ADMIN`・`OPERATOR`だけが、独立した「お知らせ管理」画面（`/news`）で登録・更新・削除できる（→ [`20_お知らせ管理一覧.md`](20_お知らせ管理一覧.md) 以降）。
- **詳細画面は作らない。** 編集・削除は一覧の行から直接ポップアップを開いて行う。マスタ機能と異なり、削除ボタンも一覧の行に置く（マスタは詳細画面のみに置くが、お知らせには詳細画面自体が無いため）。
- 登録・更新の入力画面ではデータベースを更新せず、確認状態で「実行」ボタンが押された時点で初めて反映する（マスタ機能と同じ方針）。ただし確認状態への切り替えは別画面への遷移ではなく、**同じポップアップ（Dialog）の中で表示を切り替える**。独立した画面ルートは持たない。
- 削除は**物理削除**とする。論理削除は採用しない（要件定義 §01.9）。

既存の `Announcement` モデル・`src/modules/announcement` モジュールは、本機能の実装にあわせて `News` / `src/modules/news` へリネームする（要件定義 §01.9）。以降の設計書はすべてリネーム後の名前で記述する。

## 00.2 用語

| 用語 | 説明 |
|---|---|
| カテゴリ | お知らせの種類を表す区分。「障害情報」「メンテナンス」「お知らせ」の3種類の固定選択肢 |
| 公開期間 | お知らせを利用者に見せる期間。開始日時・終了日時をそれぞれ任意で指定できる |
| 公開／非公開トグル | 公開期間とは別に、手動で表示・非表示を切り替えられる印（`published`カラム） |
| 公開ステータス | お知らせ管理画面の一覧に表示する、公開期間とトグルを合わせた判定結果。「公開中」「公開前」「終了」「非公開中」の4種類（→ [§20.3](20_お知らせ管理一覧.md#203-公開ステータスの判定)） |
| さらに表示 | トップ画面で、表示済みの続きを画面遷移せずに追加取得するボタン（→ [`10_トップ画面お知らせ表示.md`](10_トップ画面お知らせ表示.md)） |

## 00.3 権限

| 操作 | ADMIN | OPERATOR | VIEWER |
| --- |:---:|:---:|:---:|
| トップ画面でのお知らせ閲覧 | 可 | 可 | 可 |
| お知らせ管理画面への入場 | 可 | 可 | 不可 |
| お知らせの登録・更新・削除 | 可 | 可 | 不可 |

`VIEWER`には「お知らせ管理」のナビゲーションメニュー項目を表示しない。画面上の非表示だけでなく、次の2箇所でもサーバー側の確認を行う。

- **遷移の入口（route guard）**：`src/modules/auth/route-guard.ts` の `decideRedirect` に、`path.startsWith("/news") && role === ROLES.VIEWER` の場合はトップ画面へリダイレクトする判定を追加する（既存の `/admin`限定判定と同じ形）。`/admin`とは別の判定にするのは、お知らせ管理は`OPERATOR`にも許可するためである（`/admin`配下は`ADMIN`限定の判定に使われている）。
- **Server Action**：登録・更新・削除の3つのServer Actionそれぞれで、既存の `canWrite`（`@/shared/constants/roles`）による書き込み権限確認を行う。

## 00.4 画面一覧

| 画面ID | 画面名 | URL | 概要 |
| --- | --- | --- | --- |
| NEWS-01 | トップ画面 | `/` | 公開中のお知らせの表示。既存のダッシュボードを拡張する |
| NEWS-02 | お知らせ管理画面 | `/news` | 検索条件の指定とお知らせ一覧の表示、登録・編集・削除の起点 |
| NEWS-03 | お知らせ確認 | NEWS-02上のポップアップ | 登録または更新する内容の確認。独立した画面ルートは持たない |

NEWS-03は、登録と更新で共通利用する論理的な状態とする。マスタ機能のMST-03（独立した画面ルートを持たない論理画面）と考え方は同じだが、お知らせ管理はポップアップ（Dialog）の中で完結するページ構成のため、NEWS-03は「ポップアップ内の表示状態の1つ」である点がマスタと異なる。

削除の確認は独立した画面を設けず、NEWS-02の一覧の行に表示する確認ダイアログで行う（→ [`23_お知らせ削除.md`](23_お知らせ削除.md)）。

## 00.5 画面遷移

```text
トップ画面（NEWS-01）
  └─「さらに表示」→ 同じ画面内で次の20件を追加取得（画面遷移なし。→ §10.2）

サイドバーメニュー「お知らせ管理」（ADMIN/OPERATORのみ表示）
  └─ お知らせ管理画面（NEWS-02）
       ├─「新規登録」
       │    └─ 登録ポップアップを開く（入力状態）
       │         ├─「確認する」→ ポップアップ内が確認状態（NEWS-03・新規登録モード）へ切り替わる
       │         │                   ├─「実行」→ ポップアップを閉じ、一覧を再読み込みして登録完了メッセージを表示
       │         │                   └─「入力内容を修正」→ 入力状態へ戻る（入力値を保持）
       │         └─「キャンセル」→ ポップアップを閉じる（入力を破棄）
       │
       ├─ 一覧の行の「編集」
       │    └─ 更新ポップアップを開く（入力状態。現在値を初期表示）
       │         ├─「確認する」→ ポップアップ内が確認状態（NEWS-03・更新モード）へ切り替わる
       │         │                   ├─「実行」→ ポップアップを閉じ、一覧を再読み込みして更新完了メッセージを表示
       │         │                   └─「入力内容を修正」→ 入力状態へ戻る（入力値を保持）
       │         └─「キャンセル」→ ポップアップを閉じる（入力を破棄）
       │
       └─ 一覧の行の「削除」→ 削除確認ダイアログ
                                ├─「削除する」→ 一覧を再読み込みして削除完了メッセージを表示
                                └─「キャンセル」→ ダイアログを閉じる
```

一覧画面から遷移する操作が無い（登録・更新・削除のすべてがNEWS-02上のポップアップ・ダイアログで完結する）ため、マスタ機能のような「検索条件・ページ番号を戻り先情報として引き継ぐ」処理は不要である。登録・更新・削除の後は、現在の検索条件・ページ番号・並び順を保持したままNEWS-02を再読み込みする。

## 00.6 エラー設計

| エラーコード | HTTPステータス | 発生条件 | 利用者向けメッセージ例 |
| --- | ---: | --- | --- |
| `VALIDATION_ERROR` | 422 | 必須、文字数、公開終了日時が公開開始日時より前、のいずれかに違反した | 入力内容を確認してください |
| `NEWS_NOT_FOUND` | 404 | 対象のお知らせが存在しない（既に削除された場合を含む） | 対象のお知らせが見つかりません |
| `NEWS_CONCURRENT_UPDATE` | 409 | ほかの利用者が先に更新または削除した | ほかの利用者によって更新されています。最新の内容を確認してから、もう一度操作してください |
| `FORBIDDEN` | 403 | 書き込み権限がない利用者（`VIEWER`）が登録・更新・削除を実行した | この操作を行う権限がありません |

業務処理では `AppError` を送出する。業務コード（`service.ts` / `repository.ts`）に個別のログ出力や包括的な `try/catch` は記述せず、Server Actionを `withOp` でラップして処理境界で一度だけ記録する（マスタ機能と同じ方針。§00.6.1）。

### 00.6.1 削除・変更操作の記録

物理削除では削除された行が残らず、更新では上書き前の値が残らない。マスタ機能（[`../master/00_マスタ管理共通.md`](../master/00_マスタ管理共通.md#0061-削除変更操作の記録)）と同じ理由・同じ方式で、記録はアプリケーションログ（`withOp`によるServer Action引数の出力）でのみ行う。

| 操作 | Server Actionの入力に含める値 |
| --- | --- |
| お知らせの削除 | お知らせID、`updatedAt`、削除対象のタイトル |
| お知らせの更新 | お知らせID、`updatedAt`、変更前のタイトル・カテゴリ・本文・公開期間・公開トグル、変更後の入力値 |

変更されなかった項目についても変更前後の値を送信する（マスタ機能と同じ理由。§00.6.1）。可否判定にはこれらの値を使用せず、対象IDと`updatedAt`、および変更後の入力値だけを使用する。

## 00.7 モジュール構成

既存のfeature-modular規約に従い、お知らせ機能を `src/modules/news` 内で完結させる（旧 `src/modules/announcement` からのリネーム）。

```text
src/modules/news/
├─ actions.ts
├─ service.ts
├─ repository.ts
├─ validation.ts
├─ types.ts
├─ index.ts
└─ ui/
   ├─ news-feed.tsx          # トップ画面の表示と「さらに表示」（クライアントコンポーネント。→ §10.2）
   ├─ news-item.tsx          # お知らせ1件分の表示（トップ画面で使用）
   ├─ news-search-form.tsx   # お知らせ管理画面の検索条件
   ├─ news-table.tsx         # お知らせ管理画面の一覧テーブル
   ├─ news-create-dialog.tsx # 「新規登録」ボタンとポップアップ
   ├─ news-edit-dialog.tsx   # 一覧の行の「編集」ボタンとポップアップ
   ├─ news-confirmation.tsx  # ポップアップ内の確認状態（新規登録・更新で共通）
   └─ news-delete-dialog.tsx # 一覧の行の「削除」ボタンと確認ダイアログ
```

画面ルートは以下とする。

```text
src/app/(main)/page.tsx     # 既存のトップ画面。newsService・NewsFeedの呼び出しに変更する
src/app/(main)/news/
└─ page.tsx                 # NEWS-02 お知らせ管理画面
```

Route Handlerは持たない。CSVダウンロード等の出力機能を持たないためである。

各ファイルの責務は以下のとおりである。

| ファイル | 責務 |
| --- | --- |
| `app/**/page.tsx` | 認証確認、URLパラメーターの取得、サービス呼び出し、UIの組み立て |
| `actions.ts` | 書き込み権限確認、入力値の受け取り、Server Actionの処理境界。トップ画面の追加取得（読み取り専用）もここに置く |
| `service.ts` | 検索、登録・更新・削除ユースケース、公開ステータスの判定 |
| `repository.ts` | Prismaを使用したデータベース操作。並び順に使う `COALESCE(startAt, createdAt)` はPrismaの`orderBy`で表現できないため、生SQL（`$queryRaw`）を使う唯一の箇所になる（→ [`01_データベース.md`](01_データベース.md#011-データベース設計)） |
| `validation.ts` | Zodを使用した入力値検証 |
| `types.ts` | 一覧・フォーム・検索条件の型定義、カテゴリの固定値 |
| `index.ts` | ニュースモジュールが外部へ公開するAPI |
| `ui/*.tsx` | 画面表示、フォーム入力、入力状態と確認状態の切り替え |

依存方向は `app → modules/news → shared` とし、Prismaは `repository.ts` 以外から直接使用しない。データベースへアクセスするファイルには `server-only` を適用する。

`actions.ts` が公開するServer Actionは**4つ**とする。登録・更新・削除（書き込み系3つ）と、トップ画面の追加取得（読み取り専用1つ）である。追加取得は状態を変えない操作だが、Route Handlerではなく他の3つと同じくServer Actionとして実装する（クライアントコンポーネントから直接呼び出せ、Route Handlerを新設する理由が無いため）。

`src/shared/layout/nav-config.ts` に「お知らせ管理」（`/news`、`adminOnly`ではなく`VIEWER`にだけ非表示にする新しい仕組みが必要。既存の`NavItem.adminOnly`は`ADMIN`限定用のため、`OPERATOR`にも見せたいお知らせ管理には使えない。`NavItem`に`hideForViewer?: boolean`を追加し、`adminOnly`と同様にフィルタ条件へ加える）を追加する。

## 00.8 テスト方針

テストは対象ファイルの隣へコロケーションする。機能ごとの確認項目は各機能のファイルの「テスト方針」に相当する節にある。ここには全機能に共通する権限の確認だけを置く。

### 00.8.1 権限

- `VIEWER`はトップ画面でお知らせを閲覧できる。
- `VIEWER`はお知らせ管理画面（`/news`）へ直接URLを入力しても入場できない（route guardで`/`へリダイレクトされる）。
- `VIEWER`にはナビゲーションメニューに「お知らせ管理」が表示されない。
- `VIEWER`による書き込み系Server Action（登録・更新・削除の3つ）の直接実行を、すべて`FORBIDDEN`で拒否する。
- `ADMIN`と`OPERATOR`は登録・更新・削除を実行できる。

## 00.9 対象外

以下は要件定義 §01.6・§01.8 で対象外・先送りと確定済みのため、本設計でも扱わない。既読管理・新規登録時のメール通知・添付ファイル・本文のリッチテキスト対応・カテゴリの追加や自由入力化・一般ユーザー向け画面での検索。重要度の廃止についても要件定義 §01.8 を参照すること。

このほか、本設計で新たに採用しないと決めたものを記す。

### 00.9.1 CSVダウンロード・Excel取得

マスタ機能にある一括出力機能（CSVダウンロード・マスタ情報Excel取得）に相当するものは、お知らせ機能には設けない。要件定義に出力機能への言及が無く、想定件数も少ないため、必要になった時点で改めて検討する。

### 00.9.2 マスタ分類のような子画面

お知らせにはマスタ分類に相当する「分類を管理する別画面」は無い。カテゴリは固定の3値であり、画面から追加・変更できない（要件定義 §01.8）。
