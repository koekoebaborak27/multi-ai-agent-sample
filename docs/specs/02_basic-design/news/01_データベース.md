# データベース設計

`News`モデル（旧`Announcement`）の設計・制約・並び順の実現方法。全機能が参照する。

お知らせ管理機能 基本設計書の一部。全体の索引は [`README.md`](README.md)、共通の前提は [`00_お知らせ管理共通.md`](00_お知らせ管理共通.md) を見ること。

## 01.1 データベース設計

### 01.1.1 ER概要

```text
News（他テーブルとのリレーションを持たない単独テーブル）
```

お知らせは他のテーブルから参照されず、他のテーブルも参照しない独立したテーブルである。

### 01.1.2 モデル名・テーブル名のリネーム

既存の `Announcement` モデルを `News` へリネームする（要件定義 §01.9）。理由は、実装・設計の両方で「お知らせ」を指す名前を `News` に統一し、`Announcement` という語を使わないようにするためである。

本番データベースに既存データがある前提で、`docs/prisma_operations.md` のexpand/contract方針に従って移行する。モデル名・テーブル名の変更は同ドキュメントの分類で「カラムのリネーム」と同様に扱い、`prisma migrate dev --create-only` で生成したマイグレーションへ手を入れ、`ALTER TABLE "Announcement" RENAME TO "News"` を使ってテーブルの行を保持したまま移行する（`DROP TABLE` + `CREATE TABLE`によるデータ消失を避ける）。あわせて `src/modules/announcement` を `src/modules/news` へリネームし、参照元（`src/app/(main)/page.tsx` など）を更新する。実行手順は工程2（実装）のチェックリストに含める。

### 01.1.3 Prismaモデル案

```prisma
/// ダッシュボード（トップ画面）に表示する「お知らせ」。
model News {
  id        String    @id @default(cuid())
  title     String    @db.VarChar(200)
  body      String    @db.VarChar(3000)
  category  String    // INCIDENT(障害情報) / MAINTENANCE(メンテナンス) / NEWS(お知らせ)。値の選定理由は §01.1.4
  published Boolean   @default(true)
  startAt   DateTime?
  endAt     DateTime?
  createdAt DateTime  @default(now())
  createdBy String? // 登録した利用者の User.id（FK は張らない。Master と同じ規約）
  updatedAt DateTime  @updatedAt
  updatedBy String? // 最後に更新した利用者の User.id（FK は張らない）

  @@index([category, startAt])
}
```

現行の `Announcement` モデルからの変更点は以下のとおりである（要件定義 §01.7）。

| 変更 | 内容 |
| --- | --- |
| 追加 | `category`・`startAt`・`endAt`・`createdBy`・`updatedBy` |
| 削除 | `deleted`（物理削除に方針を変えるため） |
| 変更なし | `id`・`title`・`body`・`published`・`createdAt`・`updatedAt` |

`published` は登録時に既定値 `true` とする（要件定義 §01.4.2「登録時の初期値はON」）。

`createdBy` と `updatedBy` の扱いは `Master` と同じである（外部キー制約なし、Server Actionが実行者のユーザーIDを渡す、値を特定できない場合は`null`）。

### 01.1.4 `category` の固定値とアルファベット順

`category` は次の3値の固定文字列とする。Prismaのネイティブ`enum`は使わず、既存の `User.role`・`Contract.status` と同じ「`String`カラム＋コード上の定数で固定値を縛る」規約に合わせる。

| 値 | 表示名 |
| --- | --- |
| `INCIDENT` | 障害情報 |
| `MAINTENANCE` | メンテナンス |
| `NEWS` | お知らせ |

**この3値は意図的にアルファベット順が表示優先順（障害情報→メンテナンス→お知らせ）と一致するように選んでいる。** `INCIDENT` < `MAINTENANCE` < `NEWS` の文字列比較順が、そのまま要件定義 §01.4.4 の並び順と同じになるため、`category`列を単純に昇順（`ORDER BY category ASC`）で並べるだけで優先順位が実現できる。CASE式や優先度を表す別カラムを持たずに済み、`category`の値さえ守れば並び順が崩れない。

この性質は`category`の値を変更しない限り成立する。値を追加・変更する場合（要件定義 §01.8で対象外と確定済みだが、将来変更する場合のために記す）は、新しい値のアルファベット順が意図した優先順と一致するかを必ず確認すること。

### 01.1.5 並び順の実現（`COALESCE(startAt, createdAt)`）

要件定義 §01.4.4「同じカテゴリの中では公開開始日時が新しいものを上にする」を、`startAt`が`NULL`の行（公開開始日時を空欄にしたお知らせ。登録した時点から公開したものとして扱う）を含めて正しく実現するため、並び替えには`startAt`をそのまま使わず、`COALESCE(startAt, createdAt)`（`startAt`が`NULL`なら`createdAt`で代替する）を使う。

`startAt`が空欄のお知らせは「登録した時点から公開したもの」として扱う（要件定義 §01.4.2）。並び順の観点でも、空欄のお知らせは登録日時を基準に他のお知らせと比較するのが要件の意図に合う。`NULL`のまま`ORDER BY startAt DESC`すると、PostgreSQLの既定（`DESC`は`NULLS FIRST`）により、空欄のお知らせが常に同じカテゴリの先頭へ来てしまい、実際の新旧と関係なく並んでしまう。

Prismaの`orderBy`はカラム同士の演算（`COALESCE`）を表現できないため、この並び替えを行う箇所（トップ画面の取得・お知らせ管理一覧の初期表示および「公開開始日時」列でのソート）は、`repository.ts`で生SQL（`Prisma.sql` / `$queryRaw`）を使う。これはお知らせ機能内で生SQLを使う唯一の箇所であり、他のクエリ（検索条件の絞り込み、カテゴリ・タイトル・公開終了日時での並び替えなど）は通常のPrismaクエリで組み立てる。

```sql
ORDER BY category ASC, COALESCE("startAt", "createdAt") DESC
```

管理画面の一覧が「公開開始日時」の値そのもの（`NULL`なら空欄表示）を表示する一方、並び替えの基準には上記の実効値を使う点に注意すること（→ [`20_お知らせ管理一覧.md`](20_お知らせ管理一覧.md)）。表示と並び替えの基準が異なるのは意図的な設計であり、「空欄＝未設定」という情報を管理者が画面上で失わないようにするためである。

`endAt`は「空欄なら期限を決めずに公開し続ける」という意味で、代替できる具体的な日時が存在しないため、`NULL`のまま扱う。並び替え対象に含める場合（§20.2）も`NULL`をそのまま`NULLS LAST`扱いで問題ない。

### 01.1.6 公開・非公開の判定

要件定義 §01.4.3のとおり、以下の**両方**を満たす場合にのみ利用者へ表示する。

```text
published = true
AND (startAt IS NULL OR startAt <= 現在日時)
AND (endAt IS NULL OR endAt >= 現在日時)
```

トップ画面の取得（`repository.ts`）ではこの条件をそのままSQLの`WHERE`句に反映する。お知らせ管理一覧では、この条件に加えて「非公開中」等の状態表示を行うため、判定結果を4値に変換する（→ [§20.3](20_お知らせ管理一覧.md#203-公開ステータスの判定)）。

### 01.1.7 制約

| 対象 | 制約 |
| --- | --- |
| タイトル | 最大200文字 |
| 本文 | 最大3000文字 |
| カテゴリ | `INCIDENT` / `MAINTENANCE` / `NEWS` のいずれか |
| 公開終了日時 | 指定する場合、公開開始日時以降であること（アプリケーション検証。§21.3） |

文字数・公開期間の前後関係の検証はZodによるアプリケーション検証で行う。一意制約や外部キー制約は持たない（他テーブルから参照されず、`title`等の重複も許可するため）。

削除は**物理削除**とする。論理削除を採用しない理由はマスタ機能と同じである（[`../master/01_データベース.md`](../master/01_データベース.md#0113-制約)）。削除したお知らせは復元できず、「誰が何を削除したか」はアプリケーションログでのみ追跡する（§00.6.1）。
