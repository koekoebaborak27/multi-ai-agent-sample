## 10.1 画面

ルートは `/login`（`src/app/(auth)/login/page.tsx`）。ログインしていなくても開ける。

| 状態 | 表示 |
|---|---|
| 通常表示 | 見出し「サンプル契約管理システム」、説明文「ログインしてください」、（Entra有効時）Microsoftログインボタン、「または」区切り、ユーザーID欄、パスワード欄、ログインボタン、「パスワードを忘れた場合はこちら」リンク、「システム紹介」リンク |
| パスワード再設定直後（`?message=password-reset`） | 上記に加えて「パスワードを変更しました。新しいパスワードでログインしてください。」を表示 |
| ログイン済みで開いた場合 | 画面を表示せず`/`（トップ画面）へ即リダイレクト |

Microsoftログインボタンは、`isEntraConfigured`（`AUTH_MICROSOFT_ENTRA_ID_ID`等の環境変数がすべて揃っているか）が`true`のときだけ表示する。

## 10.2 入力チェック

`validation.ts` の `credentialsLoginSchema`。

| 項目 | 条件 | エラー文言 |
|---|---|---|
| ユーザーID | 必須・64文字以内 | ユーザーIDを入力してください |
| パスワード | 必須 | パスワードを入力してください |

## 10.3 処理の流れ（ID・パスワード）

Server Action（`loginWithCredentials`）で行う。`withOp`で包む。

1. 入力チェックを行う。誤りがあればその場でエラーを返す
2. NextAuthの`signIn("credentials", ...)`を呼ぶ
3. NextAuthのCredentialsプロバイダ（`providers.ts`）が`authService.verifyCredentials`を呼び、次の順に確認する
   1. 利用者IDが存在し、削除済みでないこと
   2. アカウントがロックされていないこと
   3. パスワードハッシュを持っていること（Entra専用の利用者はここで失敗する）
   4. パスワードが一致すること（→ 失敗時は[10.5](#105-ログイン失敗とロック)）
4. 成功したら、利用者のロール・初回パスワード変更要否等をJWTへ格納し（→ [10.6](#106-セッション)）、`/`へ遷移する
5. 失敗（`AuthError`）した場合は、IDとパスワードのどちらが誤りかを区別せず「ユーザーIDまたはパスワードが正しくありません」を返す。ロック済みの場合は「アカウントがロックされています。管理者にお問い合わせください」を返す

## 10.4 Entraログインの処理の流れ

動作確認の位置づけは冒頭の注記を参照。

Server Action（`loginWithEntra`）で行う。

1. `signIn("microsoft-entra-id", { redirectTo: "/" })`を呼び、Microsoft側のログイン画面へ移動する
2. 認証が成功すると、このアプリの`/api/auth/[...nextauth]`へ戻ってくる
3. JWTコールバック内で`authService.provisionEntraUser`を呼び、Entraの`oid`（無ければ`providerAccountId`／`token.sub`）を突合キーとして次のいずれかを行う
   - 既存の利用者が見つかればその情報を使う
   - 見つからなければ、ロール`VIEWER`固定で新しい利用者を作成する（`externalId`・`email`・`displayName`を記録）
4. 利用者が削除済み・ロック中の場合はログインさせない（`ACCOUNT_DISABLED`エラー）
5. 成功したら`/`へ遷移する

## 10.5 ログイン失敗とロック

- ID・パスワードによるログイン失敗のたびに`User.failedAttempts`を1増やす
- `failedAttempts`が環境変数`MAX_ATTEMPTS`（既定20）以上になった時点で`User.lockedAt`に現在時刻を記録し、以後ロック済みとして扱う
- ロックの解除は、この画面では行わない。管理者による利用者情報の更新（`prisma/AGENTS.md`配下の利用者管理）か、パスワードリセット機能の再設定完了時に解除される（→ [`docs/specs/02_basic-design/password-reset/11_パスワード再設定.md`](../password-reset/11_パスワード再設定.md)）
- ログインに成功すると`failedAttempts`を0へ戻す
- Microsoft Entra ID ログインには、この失敗回数カウント・ロック機構は適用されない（パスワードを扱わないため）。削除済み・ロック中の判定のみ適用される

## 10.6 セッション

- NextAuthの`session: { strategy: "jwt", maxAge: 90 * 60 }`により、ログイン状態をサーバー側に保存せずJWTのみで表現する。有効期限は90分
- JWTへ格納する独自項目：`user_id`・`role`・`must_change_password`・`auth_method`（`"entra"`または`"credentials"`）
- 画面側（`session`コールバック経由）では`session.user.id`・`role`・`mustChangePassword`・`authMethod`として参照する
- サインインページの指定（`pages.signIn`）は`/login`。NextAuthが認証エラー等で自動的にこの画面へ戻す際もここを使う

## 10.7 ルートガード

すべてのリクエスト（`/api`・静的ファイルを除く）が最初に通る場所で、`route-guard.ts`の`decideRedirect`を呼んで移動先を判定する。判定に使う情報はJWTの中身のみで、データベースへは問い合わせない。

| 条件 | 移動先 |
|---|---|
| 未ログインで、`/login`・`/forgot-password`・`/reset-password`・`/about`以外を開いた（画面表示・保存処理とも） | `/login` |
| ログイン済みで`/login`を開いた（画面表示のみ） | `/` |
| ログイン済みで`mustChangePassword`が`true`、かつ`/settings/password`以外を開いた（画面表示のみ） | `/settings/password` |
| `/admin`配下を`ADMIN`以外が開いた（画面表示・保存処理とも） | `/` |
| `/news`配下を`VIEWER`が開いた（画面表示・保存処理とも） | `/` |

**画面遷移の案内（2・3行目）は、保存処理（Server Action）の呼び出し時には行わない。** 保存の要求をそのまま移動先へ送り直すと、ログイン直後に「`/` → `/settings/password` → `/` → …」と行き来し続けてしまうため。権限確認（4・5行目）は保存処理の呼び出しでも必ず適用する。

Server Actionの呼び出しかどうかは、`POST`メソッドかつ`next-action`ヘッダーを持つかで判定する。

## 10.8 モジュール構成

| ファイル | 役割 |
|---|---|
| `src/app/(auth)/login/page.tsx` | 画面本体。ログイン済み判定とメッセージ出し分け |
| `src/modules/auth/ui/login-form.tsx` | フォーム（クライアントコンポーネント） |
| `src/modules/auth/actions.ts` | `loginWithCredentials`・`loginWithEntra`・`signOutAction` |
| `src/modules/auth/auth.ts` | NextAuthの設定（プロバイダ・セッション・JWT/sessionコールバック） |
| `src/modules/auth/providers.ts` | 利用可能なログイン方法（プロバイダ）の組み立て |
| `src/modules/auth/service.ts` | `verifyCredentials`・`provisionEntraUser`（業務ロジック本体） |
| `src/modules/auth/repository.ts` | `User`テーブルへのアクセス |
| `src/modules/auth/route-guard.ts` | 移動先を決める判定ロジック（`src/proxy.ts`から分離） |
| `src/proxy.ts` | 全リクエストの入口。`route-guard.ts`の判定を実際のリダイレクト応答へ変換 |
