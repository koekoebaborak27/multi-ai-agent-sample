# 09.1 手順8 メール送信を設定する

手順8（**該当する場合のみ**）。パスワード再発行など、システムからメールを送る機能を使う案件だけ実施します。送信専用の Google アカウント作成・アプリパスワードの発行・ローカルと本番への設定・動作確認。

インフラ構築手順書の一部。全体の目次と進め方は [`README.md`](README.md) を見ること。

所要時間の目安: 30 分。

> 画面が本書と異なる場合は [00.1.6](infra_design_00_概要と全体構成.md#0016-uiは資料と異なる可能性あり) を参照してください。

## 09.1.1 このテンプレートが Gmail を使う理由

**このテンプレートでは、動作確認のためのメール送信に Gmail を使います**（2026-08-21 決定）。

Resend や Amazon SES といったメール配信の専門サービスは、**送信元として自分が管理するドメインを登録しないと、他人宛にメールを送れません**。ドメインの取得には年間の費用がかかります。パスワード再発行は「相手に届かなければ機能が成立しない」ため、無料で試せる範囲に収めるには Gmail が適しています。

| | Gmail | Resend / Amazon SES |
|---|---|---|
| 費用 | 無料 | サービス自体は無料枠があるが、**ドメイン代が別途かかる**（年 1,000 円前後〜） |
| 他人宛に送れるか | **送れる** | ドメインを登録するまで送れない |
| 1日の送信数の上限 | 約 500 通 | Resend 無料枠は 100 通／日・3,000 通／月（2026-08 時点） |
| 送信元アドレス | 使った Gmail アドレスになる | 独自ドメインのアドレスにできる |
| 業務としての適性 | **低い**（規約が想定していない使い方） | **高い** |

**案件へ本格的に流用する段階では、Resend または Amazon SES へ乗り換えます。** どちらもメール送信の共通規格である SMTP に対応しているため、**アプリのコードを変更せず、設定値の差し替えだけで移行できます**。乗り換え手順は [13.1.8](#1318-本格運用時に-resend--amazon-ses-へ乗り換える) を参照してください。

## 09.1.2 送信専用の Google アカウントを作る

[Google アカウント作成ページ](https://accounts.google.com/signup) で、**このシステム専用の**アカウントを新しく作ります。

| 項目 | 設定値 |
|---|---|
| 用途 | **個人で使用**（ビジネス用を選ぶと有料版の案内に誘導されます） |
| 名前 | 案件名など、受信者に差出人として見えてよいもの（例: `サンプル契約管理システム`） |
| メールアドレス | 用途がわかる名前（例: `<案件名>-mail@gmail.com`） |
| パスワード | 他で使っていない、新しく強いもの |

> **個人の主要アカウントは使わないでください。** この後で発行する「アプリパスワード」は、**そのアカウントからメールを送るための鍵**です。用途ごとにアカウントを分けておけば、万が一その鍵が漏れても、影響をこのシステムの範囲に閉じ込められます。

**つまずきやすい点**: 電話番号による本人確認を求められることがあります。既存アカウントと同じ番号でも通常は登録できますが、短期間に何個も作ると断られる場合があります。

## 09.1.3 2 段階認証を有効にする

作ったアカウントでログインした状態で、[2 段階認証プロセスの設定](https://myaccount.google.com/signinoptions/twosv) を開き、有効にします。電話番号への SMS が最も手軽です。

**なぜ必要か**: 次の手順で発行するアプリパスワードは、**2 段階認証が有効なアカウントでしか作れません**。Google は 2022 年に「安全性の低いアプリのアクセス」という古い仕組みを廃止したため、外部のプログラムから Gmail で送信する正規の手段はアプリパスワードだけです。この手順は省略できません。

**つまずきやすい点**: 別のアカウントでもログインしていると、そちらの設定画面が開くことがあります。画面右上のアカウントアイコンで、**送信専用に作ったアカウントが選ばれているか**を必ず確認してください。

## 09.1.4 アプリパスワードを発行する

[アプリパスワードの発行ページ](https://myaccount.google.com/apppasswords) を開きます。

> **このページは Google アカウントのメニューからは辿れません。** Google が導線を消したため、上のリンクから直接開く必要があります。

1. 「アプリ名」に案件名など（例: `サンプル契約管理システム`）を入力します
2. 「作成」を押します
3. **16 文字のパスワードが表示されます。この画面を閉じると二度と表示されません。** 控えてください

表示は `abcd efgh ijkl mnop` のように 4 文字ずつ区切られていますが、**設定するときは空白を詰めて `abcdefghijklmnop` と続けて書きます**（空白があると認証に失敗します）。

**つまずきやすい点**: 「アプリパスワードを利用できません」と表示される場合、2 段階認証がまだ反映されていないか、別のアカウントの画面を開いています。

## 09.1.5 ローカルに設定する

`.env.local` に次を設定します（項目の意味は [`.env.example`](../../../.env.example) の「メール送信」の節にも記載しています）。

```
APP_BASE_URL=http://localhost:3000
MAIL_TRANSPORT=smtp
MAIL_FROM=<送信専用のGmailアドレス>
MAIL_FROM_NAME=<差出人の表示名>
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=<送信専用のGmailアドレス>
SMTP_PASSWORD=<アプリパスワード16文字・空白は詰める>
```

| 項目 | 補足 |
|---|---|
| `MAIL_TRANSPORT` | `console` にすると実際には送らず、内容をログへ出すだけになります。**普段の開発はこちらで十分**です。実際に送って確かめるときだけ `smtp` にします |
| `MAIL_FROM` | **`SMTP_USER` と同じ値にします。** 違う値を書いても、Gmail は送信時に接続に使ったアカウントのアドレスへ自動的に書き換えます |
| `SMTP_PORT` | 587 を使います。接続してから暗号化に切り替える方式（STARTTLS）です |

**`.env.local` は Git の管理対象外**です（`.gitignore` に登録済み）。鍵をリポジトリへコミットしないよう、この設定を変更しないでください。

## 09.1.6 送信できることを確認する

アプリの製造が済んでいれば、パスワード再発行の申請画面から実際に申し込んで確認します。

製造前に接続だけ確かめたい場合は、プロジェクト直下に次の内容で一時ファイル（例: `tmp-smtp-check.mjs`）を作り、実行します。**確認が済んだら削除してください。**

```js
import nodemailer from "nodemailer";
const to = process.argv[2];
const t = nodemailer.createTransport({
  host: process.env.SMTP_HOST,
  port: Number(process.env.SMTP_PORT),
  secure: false, // 587番ポートは、接続してから暗号化に切り替える方式（STARTTLS）を使う
  auth: { user: process.env.SMTP_USER, pass: process.env.SMTP_PASSWORD },
});
await t.verify();
console.log("接続と認証に成功しました。");
const info = await t.sendMail({
  from: `"${process.env.MAIL_FROM_NAME}" <${process.env.MAIL_FROM}>`,
  to,
  subject: "【テスト】メール送信の確認",
  text: "このメールは、メール送信設定を確認するために送信されました。",
});
console.log("accepted:", info.accepted, "rejected:", info.rejected);
```

```bash
node --env-file=.env.local ./tmp-smtp-check.mjs 宛先アドレス@example.com
```

**確認すること**は 3 つです。

1. 「接続と認証に成功しました」と表示されること（失敗する場合は [13.1.9](#1319-うまくいかないとき) へ）
2. `rejected` が空であること
3. **送信専用アカウントとは別のアドレス宛に、実際に届くこと**。差出人が `MAIL_FROM_NAME` の表示名になっていること

## 09.1.7 本番（Cloud Run）に設定する

アプリパスワードは秘密の値なので、**Secret Manager に登録し、Cloud Run から参照させます**。他の環境変数と同じ扱いです（[05.1 手順4](infra_design_05_CloudRun構築.md#051-手順4-google-cloud-run-を構築する) の環境変数設定と同じ画面で行います）。

1. Google Cloud コンソールの **Secret Manager** で、シークレット `smtp-password` を作り、値にアプリパスワード 16 文字を登録します
2. 作成したシークレットの「権限」タブから、Cloud Run サービスの実行アカウントに **「Secret Manager のシークレット アクセサー」**（`roles/secretmanager.secretAccessor`）を付与します（[05.1.5 事前準備2](infra_design_05_CloudRun構築.md#0515-環境変数を設定する) と同じやり方。`database-url` 等の既存シークレットにも同様の設定がある）
3. Cloud Run のサービスを編集し、**シークレットを環境変数 `SMTP_PASSWORD` として参照**する設定を追加します
4. あわせて、次を**通常の環境変数**として設定します

| 環境変数 | 設定値 |
|---|---|
| `APP_BASE_URL` | Cloud Run のサービス URL（`AUTH_URL` と同じ値） |
| `MAIL_TRANSPORT` | `smtp` |
| `MAIL_FROM` | 送信専用の Gmail アドレス |
| `MAIL_FROM_NAME` | 差出人の表示名 |
| `SMTP_HOST` | `smtp.gmail.com` |
| `SMTP_PORT` | `587` |
| `SMTP_USER` | 送信専用の Gmail アドレス |

> **`MAIL_FROM` / `SMTP_USER` を自分個人のアドレスと間違えないよう注意してください。** どちらも「送信専用に新しく作った Google アカウント」のアドレスです。ログインしている個人アカウントのメールアドレスとは別物です。

> **サービスの実行アカウントが分からない場合**: Cloud Run の対象サービスを開き、「新しいリビジョンの編集とデプロイ」→「セキュリティ」タブで確認できます（デプロイしなければ設定は変わらないので、確認したら「キャンセル」で閉じて構いません）。通常は `<プロジェクト番号>-compute@developer.gserviceaccount.com`（Default compute service account）です。

5. 新しいリビジョンをデプロイし、本番の画面から実際に再発行を申し込んで、メールが届くことを確認します

> **本番で最初に確認すること**: Google Cloud は迷惑メール送信を防ぐため、**25 番ポートでの外部への送信を遮断しています**。本テンプレートは 587 番を使うため通常は問題ありませんが、本番で送信できない場合はまずこの点を疑ってください（[13.1.9](#1319-うまくいかないとき)）。

> **この機能を使う画面（パスワード再発行など）が、DB のマイグレーション（表の追加）を伴う場合の順序に注意してください。** 列・表の追加のような既存コードに影響しない変更であれば、**マイグレーションの適用 → PR マージ・本番デプロイ**の順にすると、機能へのリンク（例:「パスワードを忘れた場合はこちら」）が公開された直後からすぐ動作し、DB 未整備のままリンクだけ公開されてエラーになる時間帯を避けられます。

## 09.1.8 本格運用時に Resend / Amazon SES へ乗り換える

案件へ本格的に流用する際は、次の作業を行います。**アプリのコードを変更する必要はありません。**

1. 案件で使うドメインを用意します。**既にドメインを持っている場合は、その一部を切り出して（例: `mail.会社名.co.jp`）使えるので追加費用はかかりません**
2. 送信サービス（Resend または Amazon SES）にそのドメインを登録します
3. サービスから指示される DNS の記録（SPF / DKIM。**そのドメインからの送信が正当なものであることを証明する仕組み**）を、ドメインの管理画面へ登録します
4. サービス側でドメインの認証が通ったことを確認します
5. `SMTP_HOST` / `SMTP_USER` / `SMTP_PASSWORD` / `MAIL_FROM` を、そのサービスの値へ差し替えます

| サービス | `SMTP_HOST` の例 |
|---|---|
| Resend | `smtp.resend.com` |
| Amazon SES | `email-smtp.<リージョン>.amazonaws.com` |

乗り換え後は、送信専用の Google アカウントとアプリパスワードは不要になります。**アプリパスワードは Google アカウントの設定画面から削除してください。**

## 09.1.9 うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| `Invalid login` / `535` の認証エラー | アプリパスワードの空白が詰められていない。`abcd efgh ijkl mnop` → `abcdefghijklmnop` |
| 同上 | アカウント本体のパスワードを設定している。アプリパスワードは別物です（[13.1.4](#1314-アプリパスワードを発行する)） |
| アプリパスワードの発行ページで「利用できません」 | 2 段階認証が未設定か、別アカウントの画面を開いている（[13.1.3](#1313-2-段階認証を有効にする)） |
| 接続が止まったまま応答しない | ポートが 25 になっている。Google Cloud は 25 番を遮断しています。`SMTP_PORT=587` を確認 |
| ローカルでは送れるが本番で送れない | Cloud Run の環境変数と Secret Manager の参照設定を確認（[13.1.7](#1317-本番cloud-runに設定する)） |
| 送信元が設定と違うアドレスになる | Gmail の仕様です。`MAIL_FROM` を `SMTP_USER` と同じにしてください |
| 迷惑メールに入る | Gmail 以外の受信先で起こりやすい。本格運用時の乗り換え（[13.1.8](#1318-本格運用時に-resend--amazon-ses-へ乗り換える)）で解消します |
| 1 日の途中から送れなくなった | 送信数の上限（約 500 通／日）に達した可能性があります。翌日まで待つか、乗り換えを検討してください |
