# 09.1 構築後の運用

デプロイ・マイグレーション・ログ・費用・切り戻し・鍵の管理・本番で動かさないもの。

インフラ構築手順書の一部。全体の目次と進め方は [`README.md`](README.md) を見ること。


## 09.1.1 本番へ反映する

**`main` ブランチへの push が、そのまま本番デプロイになります。**

| 変更内容                         | 進め方                                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| ソースコード                       | 作業用ブランチ → Pull Request → CI 成功を確認 → マージ（手順は [`gitの操作ルール.md`](../../development/gitの操作ルール.md)） |
| ドキュメント（`.md` / `docs/` 配下）のみ | `main` へ直接 push してよい                                                                            |

> **ドキュメントだけの変更でも、本番のビルドとデプロイは実行されます。** GitHub Actions の検査は自動的にスキップされますが、**Cloud Build は別の仕組みのため動作します**（5〜10 分かかります）。無料枠の範囲であれば実害はありませんが、止めたい場合は次のいずれかを選びます。
> 
> - コミットメッセージに `[skip ci]` を付ける（Cloud Build も同じ文字列に対応しています）
> - Cloud Build のトリガー設定「含まれるファイルと無視されるファイルのフィルタ」で `**.md` / `docs/**` を除外する（**この設定は Git の管理外のため、リポジトリを複製しただけでは再現しません**）

## 09.1.2 データベースの構造を変更する

Cloud Run にはデプロイの前後に処理を挟む仕組みがないため、**マイグレーションは PC から手動で実行します。**

1. 作業用ブランチで [`prisma/schema.prisma`](../../../prisma/schema.prisma) を変更し、ローカルでマイグレーションを作成する（`pnpm prisma:migrate`）
2. Pull Request → CI 成功 → マージ
3. **本番データベースへマイグレーションを適用する**（下記）
4. 自動デプロイの完了を確認する

```powershell
Set-PSReadLineOption -HistorySaveStyle SaveNothing
$env:DATABASE_URL='<本番の接続文字列>'
pnpm exec prisma migrate status    # 未適用の変更を確認
pnpm exec prisma migrate deploy    # 適用
exit                               # ターミナルを閉じる
```

> **適用の順序に注意してください。** 列の追加のように既存のコードでも動作する変更は先に適用して構いません。列の削除や名前の変更のように既存のコードが動かなくなる変更は、デプロイのタイミングと合わせる必要があります。

## 09.1.3 ログを確認する

Cloud Run のサービス詳細画面の「ログ」タブで確認できます。

| 症状         | 探す文字列                                       |
| ---------- | ------------------------------------------- |
| コンテナが起動しない | `環境変数の検証に失敗しました:` — 続いて不足している変数名が日本語で表示されます |
| 画面がエラーになる  | `ERROR` レベルのログ                              |

## 09.1.4 費用を確認する

Google Cloud のコンソールで「お支払い」→「レポート」を開くと、利用状況と請求額を確認できます。無料枠の範囲であれば請求額は 0 円です。

Supabase は、プロジェクトのダッシュボードで使用量を確認できます。

## 09.1.5 以前の状態へ戻す（切り戻し）

問題のある内容を本番へ反映してしまった場合、元の状態へ戻せます。**戻し方は 2 種類あり、役割が違います。**

| 方法                         | 何が戻るか                 | 反映までの時間        | 使いどころ                         |
| -------------------------- | --------------------- | -------------- | ----------------------------- |
| **A. Cloud Run のリビジョンを戻す** | **動いているアプリだけ**        | 数十秒            | **まず止血する**。利用者への影響を最短で止める     |
| **B. GitHub の `main` を戻す** | **ソースコード**（結果としてアプリも） | 5〜10 分（自動デプロイ） | **恒久対応**。次のデプロイで問題が再発しないようにする |

> **A だけで終わらせないでください。** リビジョンを戻しても GitHub のソースコードは問題のある状態のままです。**次に誰かが `main` を更新した時点で、問題のあるコードが再びデプロイされます。** A で止血したあと、必ず B（または修正版のリリース）まで行ってください。

### A. Cloud Run のリビジョンを戻す

1. Google Cloud のコンソールで **Cloud Run** を開き、対象のサービス（例: `contract-app`）を選びます。
2. **「リビジョン」タブ**を開きます。デプロイのたびに作られた履歴が、新しい順に一覧表示されます。
3. **戻したいリビジョンを特定します。** 作成日時が、問題が起きる前の最後のデプロイと一致するものです。名前は `contract-app-00012-abc` のように連番が付いています。
4. 上部の **「トラフィックを管理」** を押します。
5. 戻したいリビジョンを選び、**トラフィックの割合を `100`%** にします。現在のリビジョンは `0`% になります。
6. **「保存」** を押します。
7. 反映を確認します。

```powershell
$base="https://<サービス名>-<プロジェクト番号>.us-central1.run.app"
Invoke-WebRequest "$base/api/health" -UseBasicParsing
```

> **トラフィック**とは、利用者からのアクセスのことです。「リビジョン A に 100%」と設定すると、すべてのアクセスがそのリビジョンへ送られます。**古いリビジョンは削除されずに残っているため、すぐに切り替えられます。**

> **環境変数の設定ミスが原因の場合は、リビジョンを戻す必要はありません。** 「新しいリビジョンの編集とデプロイ」から値を修正すれば、その内容で新しいリビジョンが作られます。

### B. GitHub の `main` を戻す

問題のあるコミットを打ち消す**新しいコミット**を作り、`main` へ反映します。これにより自動デプロイが動き、正常な状態がデプロイされます。

**コマンドで行う場合**

```powershell
# 1. main の最新を取得する
git checkout main
git pull

# 2. 取り消したいコミットを特定する（上が最新）
git log --oneline -5

# 3. そのコミットを打ち消すコミットを作る
git revert <コミットID>

# 4. main へ反映する（ここで自動デプロイが動く）
git push
```

**GitHub のサイト上で行う場合**

1. 対象の Pull Request のページを開きます。
2. マージ済みの Pull Request の下部にある **`Revert`** ボタンを押します。
3. 打ち消し用の Pull Request が自動で作られるので、CI の成功を確認してマージします。

> **`git revert` は「打ち消すコミットを新しく追加する」操作です。** 履歴は消えず、「いつ・何を取り消したか」が残ります。
> 
> **`git reset --hard` と強制 push（`git push --force`）は使わないでください。** 履歴そのものを書き換えるため、他の開発者の手元と食い違い、変更が失われる恐れがあります。

### データベースの変更を伴っていた場合

**マイグレーションで変更したデータベースの構造は、A でも B でも元に戻りません。** アプリのコードだけが戻ります。

| 状況              | 対応                                                                             |
| --------------- | ------------------------------------------------------------------------------ |
| 列や表を**追加**しただけ  | そのままで問題ありません。古いコードは追加分を使わないだけです                                                |
| 列や表を**削除・改名**した | 古いコードが動かなくなります。**構造を元に戻すマイグレーションを別途作成して適用してください**（[09.1.2](#0912-データベースの構造を変更する)） |

> このため、**列の削除や改名を含む変更は、切り戻しが難しくなります。** リリース前に十分な確認を行ってください。

## 09.1.6 鍵とパスワードの管理

| 対象                     | 漏洩時の対応                                                                 |
| ---------------------- | ---------------------------------------------------------------------- |
| Supabase の `secret` キー | Supabase のダッシュボードで無効化して再発行し、**Cloud Run の環境変数と、ローカルの `.env` の両方**を更新する |
| Supabase のデータベースパスワード  | 再生成し、接続文字列を作り直して Cloud Run の `DATABASE_URL` を更新する                      |
| `AUTH_SECRET`          | 新しい値を生成して Cloud Run の環境変数を更新する（利用者は再ログインが必要になります）                      |

## 09.1.7 本番で動かさないもの

| 対象                  | 理由                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| ジョブワーカー（pg-boss）    | 現時点で登録済みのジョブがなく、常時起動すると無料枠を消費するだけになるためです。実際のジョブを追加する段階で、起動方法を改めて検討します                               |
| ローカル開発用の PostgreSQL | [`docker/docker-compose.yml`](../../../docker/docker-compose.yml) の `db` は開発専用です。本番は Supabase を使います |

> **本番コンテナ内でワーカーを起動する場合**、`pnpm worker` は使えません。本番用のイメージには pnpm 本体が含まれていないためです。`./node_modules/.bin/tsx src/worker/index.ts` を使ってください。
