# 05.1 手順4 Google Cloud Run を構築する

手順4。Google Cloud プロジェクト作成・サービス作成・環境変数・Cloud Build のビルド設定。

インフラ構築手順書の一部。全体の目次と進め方は [`README.md`](README.md) を見ること。


所要時間の目安: 90 分。**本書の中で最も手間がかかり、つまずきやすい工程です。**

> 画面が本書と異なる場合は [00.1.6](infra_design_00_概要と全体構成.md#0016-uiは資料と異なる可能性あり) を参照してください。

## 05.1.1 アカウントを作成し、課金を有効にする

[Google Cloud](https://cloud.google.com/) でアカウントを作成し、クレジットカードを登録して課金を有効にします。無料枠の範囲では請求は発生しませんが、有効化しないと Cloud Run を使えません。

## 05.1.2 Google Cloud プロジェクトを作成する

上部のプロジェクト選択メニューから、新しいプロジェクトを作成します。

| 項目            | 設定値                                                           |
| ------------- | ------------------------------------------------------------- |
| プロジェクト名       | 任意（例: 案件名）                                                    |
| **プロジェクト ID** | 自動生成される値、または任意の一意な文字列。**作成後は変更できません**（[00.4 章](infra_design_00_概要と全体構成.md#004-あとから変更できない項目)） |

**このプロジェクトでの例**: プロジェクト ID は `multi-ai-agent-sample-2026`。

> **Google Cloud のプロジェクト**とは、リソース（サービス・データベース・権限など）をまとめる単位です。案件ごとに 1 つ作ると、費用や権限を分けて管理できます。

## 05.1.3 サービス作成画面を開く

左メニューから **Cloud Run** を開きます。

初回は概要ページが表示されます。**「ウェブサービスのデプロイ」の下にある「リポジトリの接続」（GitHub アイコンのカード）を押してください。**

> 「サービスを作成」というボタンを探しても見つからない場合があります。現在の Cloud Run は、概要ページに並ぶカードから作業を始める構成になっており、サービスの設定とビルドの設定が **1 つの画面に統合**されています。左メニューの「サービス」からは、作成済みサービスの一覧を開けます。

続いて、GitHub リポジトリとの接続を求められます。

| 項目    | 設定値                       | 補足                                         |
| ----- | ------------------------- | ------------------------------------------ |
| ソース   | **リポジトリから継続的にデプロイする**     | もう一方（既存のコンテナイメージ）を選ぶと、push による自動デプロイになりません |
| 接続方式  | **Developer Connect**（既定） | GitHub との接続に使う仕組みです                        |
| リポジトリ | 手順 1 で作成したリポジトリ           |                                            |
| ブランチ  | `main`                    |                                            |

初回は GitHub 側で連携の承認を求められます。画面の指示に従って許可してください。

## 05.1.4 サービスの設定値

同じ画面で、次のとおり設定します。**表のすべての項目を確認してください。**

| 項目             | 設定値                     | 理由                                                                    |
| -------------- | ----------------------- | --------------------------------------------------------------------- |
| **サービス名**      | 任意（例: `contract-app`）   | **作成後は変更できません**                                                       |
| **リージョン**      | **`us-central1`（アイオワ）** | **既定は `europe-west1` です。無料枠は米国リージョンが対象のため、必ず変更してください。作成後は変更できません**    |
| **認証**         | **パブリック アクセスを許可**       | 「認証が必要」にすると Google アカウントの認証が手前に入り、**アプリのログイン画面へ到達できなくなります**           |
| 課金             | リクエスト ベース（既定）           | リクエストを処理している間だけ課金される方式です                                              |
| インスタンスの最小数     | `0`（既定）                 | 待機中の費用が発生しません。代わりにコールドスタートが発生します                                      |
| **インスタンスの最大数** | **`2`**                 | **既定は空欄（＝100）です。想定外のアクセスがあると 100 個まで自動的に増え、無料枠を超えて課金されます。必ず設定してください** |
| Ingress        | すべて（既定）                 |                                                                       |
| コンテナ ポート       | `8080`（既定）              | Cloud Run がこの番号をアプリへ渡します                                              |
| メモリ            | `512 MiB`（既定）           | 実測値は 77MB のため十分です。**1GiB に上げると無料枠の消費が 2 倍の速さになります**                   |
| **サービス アカウント** | 一覧から選択する                | 「セキュリティ」タブにあります。**選択しないまま作成するとエラーになります**                              |

> **インスタンス**とは、アプリを動かすコンテナ 1 つ分のことです。アクセスが増えると自動的に数が増え、処理を分担します。最大数を制限しておくと、想定外のアクセスがあっても費用が青天井になりません。

### サービスアカウントについて

一覧に表示される `<プロジェクト番号>-compute@developer.gserviceaccount.com` を選べば動作します。

ただし、このアカウントは**プロジェクトの編集者権限**を持っており、必要以上に強い権限です。本テンプレートのアプリは Google Cloud の API を呼ばない（データベースもファイル保管も Supabase へ直接接続する）ため、**本来は権限を持たない専用のアカウントで動作します。**

本番運用では、構築後に権限のない専用サービスアカウントへ差し替えることを推奨します。差し替えは「新しいリビジョンの編集とデプロイ」→「セキュリティ」タブから行え、やり直しが効きます。

## 05.1.5 環境変数を設定する

同じ画面の「コンテナ、ネットワーキング、セキュリティ」→「変数とシークレット」で、次の 9 個を登録します。

| 変数名                         | 値                                 | 説明                                      |
| --------------------------- | --------------------------------- | --------------------------------------- |
| `DATABASE_URL`              | [03.1.3](infra_design_03_Supabase作成.md#0313-接続文字列を取得する) の接続文字列      | Session pooler のもの                      |
| `AUTH_SECRET`               | ランダムな長い文字列                        | ログイン情報の改ざんを防ぐ署名に使います                    |
| `AUTH_URL`                  | Cloud Run のエンドポイント URL            | 下記参照。**末尾のスラッシュは付けません**                 |
| `AUTH_TRUST_HOST`           | `true`                            | Cloud Run は転送用のサーバー経由でリクエストを受けるため必要です   |
| `LOG_PRETTY`                | `false`                           | 本番は構造化ログ（JSON 形式）で出力します                 |
| `STORAGE_TYPE`              | `supabase`                        | ファイルの保管先を Supabase に切り替えます              |
| `SUPABASE_URL`              | `https://<プロジェクトref>.supabase.co` | [03.1.5](infra_design_03_Supabase作成.md#0315-api-キーを取得する)                  |
| `SUPABASE_SERVICE_ROLE_KEY` | `secret` キー                       | [03.1.5](infra_design_03_Supabase作成.md#0315-api-キーを取得する)。**管理者権限の鍵です**    |
| `SUPABASE_STORAGE_BUCKET`   | `uploads`                         | [03.1.4](infra_design_03_Supabase作成.md#0314-ファイル保管用のバケットを作成する) で作成したバケット名 |

`AUTH_SECRET` は次のコマンドで生成できます。

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

### エンドポイント URL は作成前に分かる

**サービス名とリージョンを入力した時点で、画面にエンドポイント URL が表示されます。** そのため `AUTH_URL` は最初から設定でき、「一度デプロイして URL を確認してから設定し直す」という二度手間は不要です。

```
https://<サービス名>-<プロジェクト番号>.us-central1.run.app
```

> `PORT` は設定不要です。Cloud Run が `8080` を自動的に渡します。

設定が終わったら「作成」を押します。ここで最初のビルドが始まります。

## 05.1.6 Cloud Build のビルド設定を修正する

**初回のビルドは失敗します。** 本テンプレートの構成に合わせて設定を修正する必要があるためです。落ち着いて次の 2 点を確認してください。

### 原因1: GitHub からソースを取得する権限が足りない

```
FETCHSOURCE
ERROR: error fetching DeveloperConnect credentials:
googleapi: Error 403: Permission 'developerconnect.gitRepos...'
```

10 秒程度で、何も実行されずに終了します。

**対処**: Cloud Build のトリガー編集画面に、黄色い警告と **「すべて付与」ボタン**が表示されます。これを押して権限を付与してください。

> 権限の反映には時間差があります。作成直後の 1 回目が反映前に実行されて失敗した場合、**もう一度実行するだけで成功することもあります。**

### 原因2: ビルドの起点となるディレクトリが違う

```
Step 8/35 : COPY package.json pnpm-lock.yaml ./
COPY failed: file not found in build context: stat package.json: file does not exist
```

**これが最もつまずきやすい箇所です。**

Cloud Build は「Dockerfile が置かれているディレクトリ」を起点（ビルドコンテキスト）として扱います。本テンプレートの [`docker/Dockerfile`](../../../docker/Dockerfile) は**リポジトリ全体を起点とする前提**で書かれているため、そのままでは `package.json` を見つけられません。

> Dockerfile のパス指定（`docker/Dockerfile`）自体は正しく機能しています。**エラーの原因はパス指定ではなく起点の位置**であるため、切り分けを誤りやすい箇所です。

**対処**: Cloud Run のコンソールから作成したトリガーは、ビルド設定がその場で編集できる形式（インライン YAML）になっています。**Cloud Build → トリガー → 編集 → 「エディタを開く」**から、ビルドの記述を次のとおり修正します。

```yaml
      # 修正前（docker ディレクトリが起点になっている）
      - docker
      - '-f'
      - docker/Dockerfile

      # 修正後（起点をリポジトリ全体にし、末尾へ移動する）
      - '--target'
      - runner
      - '-f'
      - docker/Dockerfile
      - '.'
```

あわせて 2 つの設定を追加します。

| 設定                | 値        | 理由                                                                                 |
| ----------------- | -------- | ---------------------------------------------------------------------------------- |
| `--target`        | `runner` | Dockerfile には開発用と本番用の定義が含まれています。本番用（`runner`）を明示することで、将来定義が追加されても意図しないものがデプロイされません |
| `timeout`（最上位に記述） | `1800s`  | Cloud Build の既定の制限時間は 10 分です。初回のビルドはこれを超える場合があります                                  |

### 修正後は「実行」で再ビルドする

**「ビルドを再試行」ボタンでは、トリガーの修正が反映されません。** このボタンは、そのビルドが実行された時点の設定をそのまま使い直すためです。

修正後は **Cloud Build → トリガー → 「実行」** から手動で実行してください。

修正が反映されたかどうかは、ビルドの詳細画面に表示される `docker build` のコマンド全文で判別できます。末尾が `-f docker/Dockerfile .` になっていれば正しい状態です。
