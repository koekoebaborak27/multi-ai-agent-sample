## 1. このドキュメントについて

### 1.1 対象読者

- このテンプレートを使って**新しい案件の本番環境を構築する担当者**
- クラウドサービスの構築経験がない方を想定しています。用語はその都度説明します。

### 1.2 扱う範囲

|                   | 内容                                   | 本書の扱い                                                                                                         |
| ----------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| ソースコードの置き場        | GitHub リポジトリ、CI（自動検査）                | **扱う**                                                                                                        |
| 本番のデータベース・ファイル置き場 | Supabase（PostgreSQL / Storage）       | **扱う**                                                                                                        |
| 本番のアプリ実行環境        | Google Cloud Run、Cloud Build（自動デプロイ） | **扱う**                                                                                                        |
| 本番データの初期化         | マイグレーション、初期管理者の登録                    | **扱う**                                                                                                        |
| 自分の PC で開発する環境    | Docker、ローカル DB                       | 扱わない<br/>※参照<br/>[`README.md`](../../../README.md)（詳細版）／[`README_SIMPLE.md`](../../../README_SIMPLE.md)（最小手順） |
| アプリの機能・画面         | 契約管理などの業務機能                          | 扱わない<br/>※参照<br/>[`docs/specs/`](../)                                                                         |

### 1.3 前提

作業を始める前に、次の 2 つを終えておいてください。

1. **自分の PC でアプリが動くこと。** 手順は [`README_SIMPLE.md`](../../../README_SIMPLE.md) にあります。本書の手順 3（データベースの初期化）で、PC 上のコマンドから本番データベースへ接続するため、`pnpm` などが使える状態が必要です。
2. **テンプレートのソースコードが手元にあること。** まだ Git 管理していない状態（フォルダにファイルがあるだけ）で構いません。手順 1 で GitHub へ登録します。

### 1.4 所要時間と費用

| 項目   | 目安                                                                                              |
| ---- | ----------------------------------------------------------------------------------------------- |
| 所要時間 | 合計 3〜4 時間。うち Google Cloud Run（手順 4）が最も時間を要します                                                   |
| 費用   | **月額 0 円**。Cloud Run と Supabase の無料枠の範囲に収まる構成です。ただし Google Cloud はアカウント作成時に**クレジットカードの登録が必須**です |

> **無料枠**とは、各クラウドサービスが定めている「ここまでは無料で使ってよい」という上限です。Cloud Run は月あたり 200 万リクエスト・180,000 vCPU 秒・360,000 GiB 秒まで無料で、この上限を超えた分だけ課金されます。本書では上限を超えないための設定（[9.4](#94-サービスの設定値)）を必ず入れます。

### 1.5 表記ルール

- **`<` と `>` で囲んだ部分はプレースホルダ**です。自分の環境の値に置き換えてください。
  例: `https://<プロジェクトref>.supabase.co`
- 実際に構築したときの値を「**このプロジェクトでの例**」として併記しています。そのまま入力するのではなく、置き換えの参考にしてください。
- コマンドは **Windows PowerShell** を前提としています。macOS / Linux の場合は、環境変数の設定方法（`$env:NAME='値'` → `export NAME='値'`）が異なります。

### 1.6 UIは資料と異なる可能性あり

**本書に記載した画面名・ボタン名・項目の並びは、2026 年 8 月時点のものです。クラウドサービスの管理画面は更新されるため、実際の画面と異なる場合があります。**

実際に、本テンプレートの構築時にも次の食い違いが発生しました。

- 事前に用意した手順書は「サービスを作成」ボタンを押す前提だったが、**そのボタンは存在しなかった**
- 公式ドキュメントを先に読んでいたが、それでも画面と一致しなかった

画面が本書と異なる場合は、次の順で対処してください（またはAI等で調査してください）。

1. **設定したい項目名で探す。** ボタンの位置や画面の構成が変わっても、設定項目そのもの（「リージョン」「インスタンスの最大数」など）の名前は残っていることが多いためです。
2. **各手順の「設定値の表」を基準にする。** 本書は「どのボタンを押すか」ではなく「何をどの値にするか」を表で示しています。画面が変わっても、この表の値をすべて設定できていれば結果は同じです。
3. **公式ドキュメントを参照する。** [Cloud Run](https://cloud.google.com/run/docs) / [Supabase](https://supabase.com/docs)。
4. **本書を更新する。** 実際の画面と違っていた箇所は、次に構築する人のために本書へ反映してください。

## 2. 用語集

本書に出てくる用語です。分からない語が出てきたらここへ戻ってください。

### 2.1 アプリの実行に関する用語

| 用語           | 意味                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------- |
| **コンテナ**     | アプリと、その実行に必要な設定・ライブラリをひとまとめにした実行環境。PC やサーバーへ直接インストールせずにアプリを動かせます                                               |
| **イメージ**     | コンテナの「型」にあたるファイル。イメージを起動したものがコンテナです。本テンプレートのイメージは [`docker/Dockerfile`](../../../docker/Dockerfile) の記述から作られます |
| **レジストリ**    | イメージの保管場所。Google Cloud では Artifact Registry が使われ、ビルドしたイメージが自動で保存されます                                           |
| **デプロイ**     | 作成したアプリを、実際に利用できる場所（本番環境）へ配置して動かすこと                                                                            |
| **リビジョン**    | Cloud Run におけるデプロイ 1 回分の記録。デプロイのたびに新しいリビジョンが作られ、**過去のリビジョンへ戻すこともできます**（[11.5](#115-以前の状態へ戻す切り戻し)）              |
| **コールドスタート** | アクセスがない間はコンテナを停止しておき、リクエストが来たときに起動する方式で発生する待ち時間。本構成では起動に数秒〜十数秒かかります。待機中の費用がかからない代わりの制約です                       |

### 2.2 サービスの名前

| 用語                    | 意味                                                                         |
| --------------------- | -------------------------------------------------------------------------- |
| **GitHub**            | ソースコードを保管し、変更履歴を管理するサービス                                                   |
| **GitHub Actions**    | GitHub 上で自動処理を実行する仕組み。本テンプレートでは**検査（CI）だけ**を行い、デプロイはしません                   |
| **Google Cloud Run**  | コンテナを動かすサービス。アクセスに応じて自動で起動・停止します                                           |
| **Cloud Build**       | Google Cloud 上でイメージを作る（ビルドする）サービス。GitHub への push を検知して自動で動きます              |
| **Developer Connect** | Google Cloud と GitHub を接続するための仕組み。Cloud Build が GitHub のソースコードを取得できるようにします |
| **Supabase**          | PostgreSQL データベースとファイルストレージを提供するサービス                                       |
| **Artifact Registry** | Google Cloud のイメージ保管場所（レジストリ）                                              |

### 2.3 設定・運用に関する用語

| 用語             | 意味                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| **環境変数**       | データベースの接続先やパスワードなど、**実行環境ごとに変わる設定値**。ソースコードに直接書かず、実行環境側に登録します                                                 |
| **マイグレーション**   | データベースの表（テーブル）や列の構造を、プログラムが期待する状態へ変更する処理。変更内容は [`prisma/migrations/`](../../../prisma/migrations/) に履歴として残ります |
| **seed（シード）**  | 動作に必要な初期データをデータベースへ登録する処理。本テンプレートでは初期管理者ユーザーを作ります                                                             |
| **リージョン**      | サービスを動かす地域（データセンターの場所）。利用者から遠いと通信に時間がかかります。なお、本資料では無料枠を利用するため意図的にリージョンを指定しています。                               |
| **サービスアカウント**  | 人ではなく**プログラムが使うアカウント**。Cloud Run のコンテナは、このアカウントの権限で動きます                                                       |
| **IAM**        | 「誰が何をしてよいか」を管理する Google Cloud の仕組み                                                                            |
| **コネクションプーラー** | データベースへの接続を再利用して、接続の作りすぎを防ぐ中継役。Supabase では接続方式の 1 つとして提供されます（[7.3](#73-接続文字列を取得する)）                           |
| **署名 URL**     | 一定時間だけ有効な、ファイル取得用の URL。非公開のファイルを、権限を持たないブラウザへ安全に渡すために使います                                                     |

## 3. 全体構成

### 3.1 構成図

```
   開発者のPC                    GitHub                        Google Cloud
┌─────────────────┐          ┌──────────────────────┐
│  ソースコード     │ ① push  │  作業用ブランチ        │
│  git / gh       ├─────────▶│  feature/xxx         │
└────────┬────────┘          └──────────┬───────────┘
         │                              │ ② Pull Request を作成
         │                              ▼
         │                   ┌──────────────────────┐
         │                   │  GitHub Actions      │
         │                   │  CI（検査のみ）        │
         │                   └──────────┬───────────┘
         │                              │ ③ CI 成功後にマージ
         │                              ▼
         │                   ┌──────────────────────┐   ④  ┌──────────────────────┐
         │                   │  main ブランチ        ├─────▶│  Cloud Build         │
         │                   └──────────────────────┘ 検知 │  イメージを作る        │
         │                                                 └──────────┬───────────┘
         │                                                            │ ⑤ デプロイ（自動）
         │                                                            ▼
         │                                                 ┌──────────────────────┐
         │                                                 │  Cloud Run           │
         │                                                 │  contract-app        │
         │                                                 └──────────┬───────────┘
         │  ⑥ マイグレーション / seed（PCから手動）                      │ 接続
         └────────────────────────────────────────────────────────────┤
                                                                      ▼
                                                           ┌──────────────────────┐
                                                           │  Supabase            │
                                                           │  PostgreSQL/Storage  │
                                                           └──────────────────────┘
```

①〜⑤ の流れは [3.3](#33-デプロイの流れ) で説明します。

> **⑥ のマイグレーションと seed は手動です。** Cloud Run にはデプロイの前後に処理を挟む仕組みがないため、**開発者の PC から本番データベースへ直接実行します**（手順は [8 章](#8-手順3-本番データベースを初期化する) と [11.2](#112-データベースの構造を変更する)）。自動化する場合は Cloud Run Jobs などの別の仕組みが必要です。

### 3.2 何がどこで動くか

| 役割           | 使うサービス                    | 補足                                                                         |
| ------------ | ------------------------- | -------------------------------------------------------------------------- |
| ソースコードの保管    | GitHub                    | private リポジトリ                                                              |
| コードの自動検査（CI） | GitHub Actions            | lint / 型チェック / テスト / ビルド。**デプロイはしない**                                      |
| イメージの作成      | Cloud Build               | `main` への push で自動実行                                                       |
| アプリの実行       | Cloud Run                 | Web 画面の配信                                                                  |
| データベース       | Supabase（PostgreSQL）      |                                                                            |
| ファイル保管       | Supabase（Storage）         | 非公開バケット。ブラウザへは署名 URL で渡す                                                   |
| ジョブワーカー      | Cloud Run（**現時点では動かさない**） | 将来的に Cloud Run 上で動かす想定。現時点では登録済みのジョブがないため起動しない。詳細は [11.7](#117-本番で動かさないもの) |

### 3.3 デプロイの流れ

[3.1 の構成図](#31-構成図) の番号に対応します。

1. **①** 開発者が作業用ブランチで変更し、GitHub へ push する
2. **②** Pull Request を作成する。これをきっかけに GitHub Actions が検査（CI）を実行する
3. **③** CI が成功したら `main` へマージする
4. **④** `main` の更新を Cloud Build が検知し、イメージを作る（5〜10 分）
5. **⑤** Cloud Build が Cloud Run へ新しいリビジョンを**自動的にデプロイする**
6. 新しいリビジョンへアクセスが切り替わる

> **`main` が更新されると、本番へ自動的に反映されます。** 構築完了後は特に注意してください（[11.1](#111-本番へ反映する)）。
> 
> **問題のある内容を反映してしまった場合は、元の状態へ戻せます。** 手順は [11.5 以前の状態へ戻す（切り戻し）](#115-以前の状態へ戻す切り戻し) にあります。**復旧できることを先に知っておくと、落ち着いて対処できます。**

## 4. あとから変更できない項目

**この章は作業前に必ず読んでください。** 次の 5 項目は、あとから変更できません。変更するには作り直しが必要です。

| #   | 項目                          | どこで決めるか                             | 変更するには                                             |
| --- | --------------------------- | ----------------------------------- | -------------------------------------------------- |
| 1   | **Supabase のリージョン**         | [7.2](#72-プロジェクトを作成する)              | プロジェクトの作り直し（データの移行が必要）                             |
| 2   | **Google Cloud のプロジェクト ID** | [9.2](#92-google-cloud-プロジェクトを作成する) | プロジェクトの作り直し                                        |
| 3   | **Cloud Run のサービス名**        | [9.4](#94-サービスの設定値)                 | サービスの作り直し（URL が変わる）                                |
| 4   | **Cloud Run のリージョン**        | [9.4](#94-サービスの設定値)                 | サービスの作り直し（URL が変わる）                                |
| 5   | **Supabase のデータベースパスワード**   | [7.2](#72-プロジェクトを作成する)              | 再生成は可能。ただし接続文字列を作り直し、**Cloud Run の環境変数も更新**する必要がある |

特に **1 と 4 は組み合わせが重要**です。Cloud Run の無料枠は米国リージョンが対象で、本書では `us-central1`（アイオワ）を使います。データベースが地理的に遠いと、すべての問い合わせで太平洋を横断することになり、画面表示が遅くなります。そのため **Supabase も米国東部（East US / North Virginia）を選びます。**

一方で、次の項目は**あとから変更できます**。迷って作業が止まるより、まず動かすことを優先してください。

| 項目                     | 変更方法               |
| ---------------------- | ------------------ |
| Cloud Run の環境変数        | 新しいリビジョンとして編集・デプロイ |
| Cloud Run のメモリ・インスタンス数 | 同上                 |
| Cloud Run のサービスアカウント   | 同上                 |
| Cloud Build のビルド設定     | トリガーの編集            |

## 5. 事前準備

### 5.1 用意するアカウント

| サービス         | 必要なもの                | 備考                        |
| ------------ | -------------------- | ------------------------- |
| GitHub       | アカウント                | private リポジトリは無料で作成できます   |

> **クレジットカードの登録について**: Google Cloud は登録時にカード情報を求めますが、無料枠の範囲内であれば請求は発生しません。ただし設定を誤ると課金される可能性があるため、[9.4](#94-サービスの設定値) の「インスタンスの最大数」を必ず設定してください。

| ツール               | 用途                 | 確認コマンド                              |
| ----------------- | ------------------ | ----------------------------------- |
| Git               | ソースコードの登録          | `git --version`                     |
| GitHub CLI（`gh`）  | GitHub の操作をコマンドで行う | `gh --version`                      |
| Node.js 22 / pnpm | マイグレーション・seed の実行  | `node --version` / `pnpm --version` |

GitHub CLI を導入していない場合は [GitHub CLI](https://cli.github.com/) からインストールし、次のコマンドで認証します。

```powershell
gh auth login
```

## 6. 手順1 GitHub リポジトリを用意する

所要時間の目安: 30 分。

> 画面が本書と異なる場合は [1.6](#16-uiは資料と異なる可能性あり) を参照してください。

### 6.1 コミットの署名を設定する

Git は、コミット（変更の記録）に名前とメールアドレスを埋め込みます。**会社アカウントと個人アカウントを使い分けている場合は、このリポジトリだけの設定を入れてください。**

```powershell
git init -b main
git config --local user.name  "<GitHubのユーザー名>"
git config --local user.email "<GitHubのメールアドレス>"
```

`--local` はこのリポジトリの `.git/config` にだけ書き込まれ、PC 全体の設定（`--global`）より優先されます。**他のリポジトリには影響しません。**

> **メールアドレスの選び方**: GitHub が発行する `<ID>+<ユーザー名>@users.noreply.github.com` 形式のアドレスを使うと、実際のメールアドレスを履歴に残さずに済みます。GitHub の Settings → Emails で確認できます。

### 6.2 登録してはいけないファイルを確認する

```powershell
git add -A
git status --short
```

一覧に次のファイルが含まれていないことを確認してください。含まれている場合は [`.gitignore`](../../../.gitignore) を見直します。

| ファイル            | 理由                                               |
| --------------- | ------------------------------------------------ |
| `.env`          | パスワードや秘密鍵が書かれています                                |
| `node_modules/` | 容量が大きく、`pnpm install` で復元できます                    |
| `.next/`        | ビルドの生成物です                                        |
| 案件固有の資料         | 実在するサーバー情報・IP アドレス・アカウント ID などを含む資料は、除外を検討してください |

### 6.3 コミット前に検査を通す

GitHub へ登録する前に、PC 上で CI と同じ検査を実行します。ここで失敗を潰しておくと、後の工程がスムーズです。

```powershell
pnpm lint
pnpm format:check
pnpm typecheck
pnpm exec prisma validate
pnpm test
pnpm build
```

すべて成功したらコミットします。

```powershell
git commit -m "chore: 初回コミット"
```

### 6.4 GitHub へ登録する

```powershell
gh repo create <リポジトリ名> --private --source=. --remote=origin --push
```

**このプロジェクトでの例**: リポジトリ名は `multi-ai-agent-sample`、公開設定は private。

> **push（プッシュ）**とは、PC 上の変更を GitHub へ送信することです。

#### 発生しやすいエラー: `workflow` スコープ不足

次のエラーで push だけが失敗する場合があります。

```
! [remote rejected] HEAD -> main
  (refusing to allow an OAuth App to create or update workflow `.github/workflows/ci.yml` without `workflow` scope)
```

GitHub は `.github/workflows/` 配下（自動処理の定義）を特別扱いしており、**`workflow` という権限を持つ資格情報でしか登録できません**。次の 2 行で解決します。

```powershell
gh auth refresh -h github.com -s workflow
git -c credential.helper= -c credential.helper="!gh auth git-credential" push -u origin main
```

> **2 行目が必要な理由**: Windows では Git Credential Manager という別の仕組みが資格情報を管理しており、`gh auth refresh` で権限を追加しても、そちらの情報は古いままです。2 行目は「このコマンドの実行中だけ、`gh` の資格情報を使う」という指定で、設定ファイルは書き換えません。

### 6.5 CI が動くことを確認する

`main` への push をきっかけに、GitHub Actions の検査が自動で始まります。

```powershell
gh run list --limit 3
```

`completed  success  CI` のように表示されれば成功です。ブラウザで確認する場合は、リポジトリの `Actions` タブを開きます。

検査の内容は [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) にあり、次の 8 つを順に実行します。

1. `pnpm lint` — 書き方の問題を検出
2. `pnpm format:check` — 書式の統一を確認
3. `prisma validate` — データベース定義の検証
4. `prisma generate` — データベース操作コードの生成
5. `pnpm typecheck` — 型の矛盾を検査
6. `prisma migrate deploy` — **空のデータベースから構造を再現できることの検証**
7. `pnpm test` — 単体テスト
8. `pnpm build` — 本番ビルド

> **CI（継続的インテグレーション）**とは、変更のたびに自動で検査を実行し、問題を早期に見つける仕組みです。

### 6.6 ブランチ保護を設定する

> **ブランチ保護**とは、`main` ブランチへの変更に条件を付ける GitHub の機能です。「CI が成功していなければマージできない」「直接 push できない」といった制限を、**仕組みとして強制**できます。

**`main` の更新はそのまま本番へ反映されるため、本番運用では設定することを推奨します。**

#### 推奨する設定

Settings → Branches → **Add branch protection rule** で、対象を `main` として次を有効にします。

| 設定項目                                                               | 効果                                           |
| ------------------------------------------------------------------ | -------------------------------------------- |
| **Require a pull request before merging**                          | `main` への直接 push を禁止し、必ず Pull Request を経由させる |
| **Require status checks to pass before merging**（対象に `verify` を指定） | **CI が成功していない Pull Request をマージできなくする**      |

#### 設定できない場合

private リポジトリでこの機能を使うには、**GitHub Pro（有料）またはリポジトリの public 化**が必要です。設定していない状態で `gh` から確認すると、次のように表示されます。

```powershell
gh api repos/<ユーザー名>/<リポジトリ名>/branches/main/protection
# → Upgrade to GitHub Pro or make this repository public to enable this feature. (HTTP 403)
```

選択肢は 3 つあります。

| 選択肢               | 費用  | 判断の目安                                                                      |
| ----------------- | --- | -------------------------------------------------------------------------- |
| GitHub Pro を契約する  | 有料  | **複数人で開発する本番運用ではこれを推奨**                                                    |
| リポジトリを public にする | 無料  | 公開して問題ない内容か十分に確認する必要がある。Public リポジトリは誰でも閲覧できるため、ソースコードや設定情報が全世界に公開される点に注意。 |
| 設定せず、運用ルールで守る     | 無料  | 少人数・検証段階であればこの選択も成り立つ                                                      |

**このプロジェクトでの例**: 検証段階のため 3 番目（運用ルール）を選び、[`docs/todo/TODO.md`](../../todo/TODO.md) に検討課題として記録しています。

#### 設定しない場合に受け入れるリスク

3 番目を選ぶ場合は、次の 2 点が**仕組みでは防げない**ことを理解したうえで運用します。

| リスク                 | 起こること                 | 運用でどう防ぐか                             |
| ------------------- | --------------------- | ------------------------------------ |
| CI が失敗していてもマージできる   | 検査を通っていないコードが本番へ反映される | マージ前に必ず CI の結果を確認する                  |
| `main` へ直接 push できる | レビューを経ないコードが本番へ反映される  | コードの変更は必ず作業用ブランチと Pull Request を経由する |

いずれの場合も、問題のある内容を反映してしまったときは元の状態へ戻せます（[11.5](#115-以前の状態へ戻す切り戻し)）。

> **ドキュメント（`.md` / `docs/` 配下）のみの変更は、`main` へ直接コミットしてよい**という例外を設けています。アプリの動作に影響しないためです。詳細は [`README.md`](../../../README.md#ドキュメントだけの変更でciを実行しないmainへ直接push) を参照してください。

手順は [`README.md`](../../../README.md#変更をgitに反映する開発フロー) にあります。

## 7. 手順2 Supabase を作成する

所要時間の目安: 30 分。

> 画面が本書と異なる場合は [1.6](#16-uiは資料と異なる可能性あり) を参照してください。

### 7.1 アカウントを作成する

[Supabase](https://supabase.com/) でサインアップします。GitHub アカウントでのサインアップが手軽です。

### 7.2 プロジェクトを作成する

新規プロジェクトの作成画面で、次のとおり設定します。

| 項目                              | 設定値                          | 理由                                                                                   |
| ------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------ |
| Name                            | 任意（例: 案件名）                   |                                                                                      |
| **Database password**           | 生成して**必ず控える**                | 接続文字列に埋め込みます。紛失した場合は再生成が必要です                                                         |
| **Region**                      | **East US (North Virginia)** | Cloud Run の無料枠が米国リージョン限定のため、データベースも近い場所に置きます。**作成後は変更できません**（[4 章](#4-あとから変更できない項目)） |
| GitHub (optional)               | **連携しない**                    | Supabase 側でスキーマを自動反映する機能ですが、本テンプレートはデータベース構造を Prisma で管理するため、二重管理になります               |
| Enable Data API                 | **オフ**                       | データベースの表を自動で外部公開する機能です。本テンプレートは使わないため、オフにして攻撃対象を減らします                                |
| Automatically expose new tables | オフ                           | Data API をオフにすれば影響しません                                                               |
| Enable automatic RLS            | オフ                           | 行単位のアクセス制御機能です。本テンプレートは管理者権限で直接接続するため、設定しても効果がありません                                  |

> **Data API をオフにしてもファイル保管（Storage）は使えます。** これらは別のサービスとして提供されています。

作成には数分かかります。

### 7.3 接続文字列を取得する

**この手順を誤ると、アプリからデータベースへ接続できません。** Supabase は 3 種類の接続方式を提供しており、本テンプレートで使えるのは **Session pooler** だけです。

| 接続方式               | ポート  | Cloud Run から接続       | マイグレーションの実行              |
| ------------------ | ---- | -------------------- | ------------------------ |
| Direct connection  | 5432 | **できない**（IPv6 専用のため） | できる                      |
| **Session pooler** | 5432 | **できる**              | **できる**                  |
| Transaction pooler | 6543 | できる                  | **できない**（対応していない命令があるため） |

#### 取得手順

1. ダッシュボード上部の **Connect** を押します。
2. 表示されるダイアログのタブから **Direct connection string** を選びます。
3. その中の **Session pooler** の文字列をコピーします。

**タブの選択で誤りやすい点があります。**

| タブ                           | 注意                                                                                                                                              |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework（初期選択）              | 別のライブラリ向けの設定です。下部に「Database access requires the Data API」という警告と **Enable Data API ボタンが表示されますが、押さないでください**（[7.2](#72-プロジェクトを作成する) で意図的にオフにしています） |
| ORM                          | Prisma 向けの設定が表示されますが、**Transaction pooler を前提とした内容のため、このテンプレートでは動作しません**                                                                        |
| **Direct connection string** | **ここを使います**                                                                                                                                     |

#### Session pooler の見分け方

コピーした文字列が次の 3 条件を満たしているか確認してください。

| 条件                               | 例                                         |
| -------------------------------- | ----------------------------------------- |
| ホスト名に `pooler` を含む               | `aws-0-us-east-1.pooler.supabase.com`     |
| ポートが **5432**                    | `:5432`（**6543 は Transaction pooler です**） |
| ユーザー名が `postgres.<プロジェクトref>` 形式 | `postgres.abcdefghijklmnop`               |

> **プロジェクト ref** とは、Supabase が各プロジェクトへ割り当てる識別子です。ユーザー名の `postgres.` に続く部分がそれにあたります。**この値は [7.4](#74-ファイル保管用のバケットを作成する) で使う URL にも含まれます。**

#### パスワードを埋め込む

コピーした文字列には `[YOUR-PASSWORD]` というプレースホルダが含まれています。**角かっこごと**、[7.2](#72-プロジェクトを作成する) で控えたパスワードに置き換えてください。

```
postgresql://postgres.<プロジェクトref>:<パスワード>@aws-0-us-east-1.pooler.supabase.com:5432/postgres
```

パスワードに `@ : / ? # [ ] %` が含まれる場合は、URL エンコードが必要です（`@` → `%40` など）。Supabase が生成するパスワードは英数字のみのため、通常は不要です。

### 7.4 ファイル保管用のバケットを作成する

> **バケット**とは、ファイルを保管する入れ物のことです。

1. 左メニューの **Storage** を開きます。
2. 新しいバケットを作成し、名前を **`uploads`** にします。
3. **公開設定は private（非公開）にします。** 契約書類などを扱うため、URL を知っていれば誰でも取得できる状態にはしません。

> バケット名は [`.env.example`](../../../.env.example) の `SUPABASE_STORAGE_BUCKET` と一致させる必要があります。既定値は `uploads` です。

### 7.5 API キーを取得する

1. **Settings → API Keys** を開きます（画面によっては Settings → API）。
2. **`secret` 側のキー**をコピーします。

| キーの種類                          | 使うか      | 説明                                 |
| ------------------------------ | -------- | ---------------------------------- |
| `publishable`（旧 `anon`）        | **使わない** | ブラウザへ公開する前提の鍵です。非公開バケットへはアクセスできません |
| **`secret`（旧 `service_role`）** | **使う**   | 管理者権限の鍵です。**外部へ漏らさないでください**        |

あわせて **Supabase の URL** を控えます。これは接続文字列に含まれるプロジェクト ref から組み立てられます。

```
https://<プロジェクトref>.supabase.co
```

> **キーの形式について**: Supabase が現在発行するキーは `sb_secret_...` という形式（40 文字程度）です。以前は数百文字の形式でしたが、どちらでも本テンプレートは動作します。

## 8. 手順3 本番データベースを初期化する

所要時間の目安: 20 分。

作成したばかりの Supabase データベースは空の状態です。**PC 上のコマンドから**、表を作り、最初の管理者ユーザーを登録します。

> **この手順の実行中は、本番データベースへ接続した状態になります。** 手順 6（ターミナルを閉じる）まで必ず実施してください。

### 8.1 コマンド履歴にパスワードを残さないようにする

PowerShell は既定で、実行したコマンドをすべてファイルへ保存します。本番のパスワードを扱うため、この機能をこのセッションだけ無効にします。

```powershell
Set-PSReadLineOption -HistorySaveStyle SaveNothing
```

### 8.2 接続先を設定する

[7.3](#73-接続文字列を取得する) で作成した接続文字列を設定します。

```powershell
$env:DATABASE_URL='postgresql://postgres.<プロジェクトref>:<パスワード>@aws-0-us-east-1.pooler.supabase.com:5432/postgres'
```

> **引用符はシングルクォート（`'`）を使ってください。** PowerShell のダブルクォート（`"`）の中では `$` が変数として解釈され、パスワードに `$` が含まれていると別の文字列に置き換わってしまいます。

> **`.env` ファイルへ本番の接続文字列を書かないでください。** 書いた場合、以降のローカル開発（`pnpm dev`）が本番データベースへ接続してしまいます。上記のように `$env:` で設定すると、そのターミナルを閉じたときに消えます。

### 8.3 接続を確認する

データベースを変更しないコマンドで、接続できることを先に確認します。

```powershell
pnpm exec prisma migrate status
```

`1 migration has not yet been applied`（まだ適用されていない変更がある）のように表示されれば、接続は成功しています。

### 8.4 マイグレーションを適用する

```powershell
pnpm exec prisma migrate deploy
```

`All migrations have been successfully applied.` と表示されれば完了です。表が作成されました。

### 8.5 初期管理者を登録する

**手順 8.2 と同じターミナルで**実行してください。

```powershell
$env:SEED_ADMIN_PASSWORD='<推測されにくいパスワード>'
pnpm prisma:seed
```

`Seed 完了: 初期ADMIN(admin)` と表示されれば成功です。

| 項目      | 値                            |
| ------- | ---------------------------- |
| ログイン ID | `admin`                      |
| パスワード   | `SEED_ADMIN_PASSWORD` に指定した値 |

> **同じターミナルで実行する理由**: `pnpm prisma:seed` は `.env` ファイルを読まないため、手順 8.2 で設定した `DATABASE_URL` が同じターミナルに残っている必要があります。

> **このコマンドは、登録したパスワードを画面へそのまま表示します。** 画面共有中は注意してください。

#### 注意: パスワードの再設定は seed ではできない

[`prisma/seed.ts`](../../../prisma/seed.ts) は「ユーザーが既に存在する場合は何もしない」動作のため、**もう一度実行しても既存ユーザーのパスワードは変わりません。** パスワードが分からなくなった場合は、データベースを直接更新する必要があります。

### 8.6 ターミナルを閉じる

```powershell
exit
```

**この手順を省略しないでください。** `DATABASE_URL` が本番を指したままのターミナルで `pnpm dev` を実行すると、開発サーバーが本番データベースへ接続します。

## 9. 手順4 Google Cloud Run を構築する

所要時間の目安: 90 分。**本書の中で最も手間がかかり、つまずきやすい工程です。**

> 画面が本書と異なる場合は [1.6](#16-uiは資料と異なる可能性あり) を参照してください。

### 9.1 アカウントを作成し、課金を有効にする

[Google Cloud](https://cloud.google.com/) でアカウントを作成し、クレジットカードを登録して課金を有効にします。無料枠の範囲では請求は発生しませんが、有効化しないと Cloud Run を使えません。

### 9.2 Google Cloud プロジェクトを作成する

上部のプロジェクト選択メニューから、新しいプロジェクトを作成します。

| 項目            | 設定値                                                           |
| ------------- | ------------------------------------------------------------- |
| プロジェクト名       | 任意（例: 案件名）                                                    |
| **プロジェクト ID** | 自動生成される値、または任意の一意な文字列。**作成後は変更できません**（[4 章](#4-あとから変更できない項目)） |

**このプロジェクトでの例**: プロジェクト ID は `multi-ai-agent-sample-2026`。

> **Google Cloud のプロジェクト**とは、リソース（サービス・データベース・権限など）をまとめる単位です。案件ごとに 1 つ作ると、費用や権限を分けて管理できます。

### 9.3 サービス作成画面を開く

左メニューから **Cloud Run** を開きます。

初回は概要ページが表示されます。**「ウェブサービスのデプロイ」の下にある「リポジトリの接続」（GitHub アイコンのカード）を押してください。**

> 「サービスを作成」というボタンを探しても見つからない場合があります。現在の Cloud Run は、概要ページに並ぶカードから作業を始める構成になっており、サービスの設定とビルドの設定が **1 つの画面に統合**されています。左メニューの「サービス」からは、作成済みサービスの一覧を開けます。

続いて、GitHub リポジトリとの接続を求められます。

| 項目    | 設定値                       | 補足                                         |
| ----- | ------------------------- | ------------------------------------------ |
| ソース   | **リポジトリから継続的にデプロイする**     | もう一方（既存のコンテナイメージ）を選ぶと、push による自動デプロイになりません |
| 接続方式  | **Developer Connect**（既定） | GitHub との接続に使う仕組みです                        |
| リポジトリ | 手順 1 で作成したリポジトリ           |                                            |
| ブランチ  | `main`                    |                                            |

初回は GitHub 側で連携の承認を求められます。画面の指示に従って許可してください。

### 9.4 サービスの設定値

同じ画面で、次のとおり設定します。**表のすべての項目を確認してください。**

| 項目             | 設定値                     | 理由                                                                    |
| -------------- | ----------------------- | --------------------------------------------------------------------- |
| **サービス名**      | 任意（例: `contract-app`）   | **作成後は変更できません**                                                       |
| **リージョン**      | **`us-central1`（アイオワ）** | **既定は `europe-west1` です。無料枠は米国リージョンが対象のため、必ず変更してください。作成後は変更できません**    |
| **認証**         | **パブリック アクセスを許可**       | 「認証が必要」にすると Google アカウントの認証が手前に入り、**アプリのログイン画面へ到達できなくなります**           |
| 課金             | リクエスト ベース（既定）           | リクエストを処理している間だけ課金される方式です                                              |
| インスタンスの最小数     | `0`（既定）                 | 待機中の費用が発生しません。代わりにコールドスタートが発生します                                      |
| **インスタンスの最大数** | **`2`**                 | **既定は空欄（＝100）です。想定外のアクセスがあると 100 個まで自動的に増え、無料枠を超えて課金されます。必ず設定してください** |
| Ingress        | すべて（既定）                 |                                                                       |
| コンテナ ポート       | `8080`（既定）              | Cloud Run がこの番号をアプリへ渡します                                              |
| メモリ            | `512 MiB`（既定）           | 実測値は 77MB のため十分です。**1GiB に上げると無料枠の消費が 2 倍の速さになります**                   |
| **サービス アカウント** | 一覧から選択する                | 「セキュリティ」タブにあります。**選択しないまま作成するとエラーになります**                              |

> **インスタンス**とは、アプリを動かすコンテナ 1 つ分のことです。アクセスが増えると自動的に数が増え、処理を分担します。最大数を制限しておくと、想定外のアクセスがあっても費用が青天井になりません。

#### サービスアカウントについて

一覧に表示される `<プロジェクト番号>-compute@developer.gserviceaccount.com` を選べば動作します。

ただし、このアカウントは**プロジェクトの編集者権限**を持っており、必要以上に強い権限です。本テンプレートのアプリは Google Cloud の API を呼ばない（データベースもファイル保管も Supabase へ直接接続する）ため、**本来は権限を持たない専用のアカウントで動作します。**

本番運用では、構築後に権限のない専用サービスアカウントへ差し替えることを推奨します。差し替えは「新しいリビジョンの編集とデプロイ」→「セキュリティ」タブから行え、やり直しが効きます。

### 9.5 環境変数を設定する

同じ画面の「コンテナ、ネットワーキング、セキュリティ」→「変数とシークレット」で、次の 9 個を登録します。

| 変数名                         | 値                                 | 説明                                      |
| --------------------------- | --------------------------------- | --------------------------------------- |
| `DATABASE_URL`              | [7.3](#73-接続文字列を取得する) の接続文字列      | Session pooler のもの                      |
| `AUTH_SECRET`               | ランダムな長い文字列                        | ログイン情報の改ざんを防ぐ署名に使います                    |
| `AUTH_URL`                  | Cloud Run のエンドポイント URL            | 下記参照。**末尾のスラッシュは付けません**                 |
| `AUTH_TRUST_HOST`           | `true`                            | Cloud Run は転送用のサーバー経由でリクエストを受けるため必要です   |
| `LOG_PRETTY`                | `false`                           | 本番は構造化ログ（JSON 形式）で出力します                 |
| `STORAGE_TYPE`              | `supabase`                        | ファイルの保管先を Supabase に切り替えます              |
| `SUPABASE_URL`              | `https://<プロジェクトref>.supabase.co` | [7.5](#75-api-キーを取得する)                  |
| `SUPABASE_SERVICE_ROLE_KEY` | `secret` キー                       | [7.5](#75-api-キーを取得する)。**管理者権限の鍵です**    |


```

```

> `PORT` は設定不要です。Cloud Run が `8080` を自動的に渡します。

設定が終わったら「作成」を押します。ここで最初のビルドが始まります。

### 9.6 Cloud Build のビルド設定を修正する

**初回のビルドは失敗します。** 本テンプレートの構成に合わせて設定を修正する必要があるためです。落ち着いて次の 2 点を確認してください。

#### 原因1: GitHub からソースを取得する権限が足りない

```
FETCHSOURCE
ERROR: error fetching DeveloperConnect credentials:
googleapi: Error 403: Permission 'developerconnect.gitRepos...'
```

10 秒程度で、何も実行されずに終了します。

**対処**: Cloud Build のトリガー編集画面に、黄色い警告と **「すべて付与」ボタン**が表示されます。これを押して権限を付与してください。

> 権限の反映には時間差があります。作成直後の 1 回目が反映前に実行されて失敗した場合、**もう一度実行するだけで成功することもあります。**

#### 原因2: ビルドの起点となるディレクトリが違う

```
Step 8/35 : COPY package.json pnpm-lock.yaml ./
COPY failed: file not found in build context: stat package.json: file does not exist
```

**これが最もつまずきやすい箇所です。**

Cloud Build は「Dockerfile が置かれているディレクトリ」を起点（ビルドコンテキスト）として扱います。本テンプレートの [`docker/Dockerfile`](../../../docker/Dockerfile) は**リポジトリ全体を起点とする前提**で書かれているため、そのままでは `package.json` を見つけられません。

> Dockerfile のパス指定（`docker/Dockerfile`）自体は正しく機能しています。**エラーの原因はパス指定ではなく起点の位置**であるため、切り分けを誤りやすい箇所です。

**対処**: Cloud Run のコンソールから作成したトリガーは、ビルド設定がその場で編集できる形式（インライン YAML）になっています。**Cloud Build → トリガー → 編集 → 「エディタを開く」**から、ビルドの記述を次のとおり修正します。

```yaml
      # 修正前（docker ディレクトリが起点になっている）
      - docker
      - '-f'
      - docker/Dockerfile

      # 修正後（起点をリポジトリ全体にし、末尾へ移動する）
      - '--target'
      - runner
      - '-f'
      - docker/Dockerfile
      - '.'
```

あわせて 2 つの設定を追加します。

| 設定                | 値        | 理由                                                                                 |
| ----------------- | -------- | ---------------------------------------------------------------------------------- |
| `--target`        | `runner` | Dockerfile には開発用と本番用の定義が含まれています。本番用（`runner`）を明示することで、将来定義が追加されても意図しないものがデプロイされません |
| `timeout`（最上位に記述） | `1800s`  | Cloud Build の既定の制限時間は 10 分です。初回のビルドはこれを超える場合があります                                  |

#### 修正後は「実行」で再ビルドする

**「ビルドを再試行」ボタンでは、トリガーの修正が反映されません。** このボタンは、そのビルドが実行された時点の設定をそのまま使い直すためです。

修正後は **Cloud Build → トリガー → 「実行」** から手動で実行してください。

修正が反映されたかどうかは、ビルドの詳細画面に表示される `docker build` のコマンド全文で判別できます。末尾が `-f docker/Dockerfile .` になっていれば正しい状態です。

## 10. 手順5 動作を確認する

所要時間の目安: 30 分。

### 10.1 URL を確認する

Cloud Run のサービス詳細画面に、エンドポイント URL が表示されます。

```powershell
$base="https://<サービス名>-<プロジェクト番号>.us-central1.run.app"
```

### 10.2 疎通を確認する

ブラウザを開かずに、コマンドで確認できます。

```powershell
Invoke-WebRequest "$base/api/health" -UseBasicParsing            # {"data":{"status":"ok"}}
Invoke-WebRequest "$base/api/health?check=db" -UseBasicParsing   # {"data":{"status":"ok","db":"up"}}
Invoke-WebRequest "$base/login" -UseBasicParsing                 # 200
```

| 確認内容                   | 期待する結果       | 失敗した場合                                |
| ---------------------- | ------------ | ------------------------------------- |
| `/api/health`          | `status: ok` | アプリが起動していません → [13 章](#13-トラブルシュート)   |
| `/api/health?check=db` | `db: up`     | データベースへ接続できていません → `DATABASE_URL` を確認 |
| `/login`               | 200          | ログイン画面の配信に問題があります                     |

> 初回アクセスはコールドスタートのため、応答まで数秒〜十数秒かかります。

### 10.3 システムの動作確認をする

ブラウザで `$base` を開き、[8.5](#85-初期管理者を登録する) で登録した管理者でログインして動作確認をします。

1. ログインする。
2. **画面からデータを登録し、一覧に表示されることを確認する**（データベースへの書き込みと読み出しの確認）

### 10.4 自動デプロイを確認する

`main` へ変更を反映したときに、本番へ自動デプロイされることを確認します。

デプロイが反映されたかどうかは、**画面が読み込む JavaScript ファイルの名前の変化**で判定します。

```powershell
$l=(Invoke-WebRequest "$base/login" -UseBasicParsing).Content
([regex]::Matches($l,'/_next/static/chunks/[a-z0-9_\-]+\.js') | ForEach-Object { $_.Value }) | Select-Object -Unique
```

デプロイの前後でこのファイル名が変われば、新しいリビジョンへ切り替わっています。

> **CSS ファイルの名前では判定できません。** このテンプレートが使う Tailwind CSS は、実際に使われている見た目の指定だけを集めて CSS を生成するため、指定が増えない変更ではファイル名が変わりません。

## 11. 構築後の運用

### 11.1 本番へ反映する

**`main` ブランチへの push が、そのまま本番デプロイになります。**

| 変更内容                         | 進め方                                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| ソースコード                       | 作業用ブランチ → Pull Request → CI 成功を確認 → マージ（手順は [`README.md`](../../../README.md#変更をgitに反映する開発フロー)） |
| ドキュメント（`.md` / `docs/` 配下）のみ | `main` へ直接 push してよい                                                                            |

> **ドキュメントだけの変更でも、本番のビルドとデプロイは実行されます。** GitHub Actions の検査は自動的にスキップされますが、**Cloud Build は別の仕組みのため動作します**（5〜10 分かかります）。無料枠の範囲であれば実害はありませんが、止めたい場合は次のいずれかを選びます。
> 
> - コミットメッセージに `[skip ci]` を付ける（Cloud Build も同じ文字列に対応しています）
> - Cloud Build のトリガー設定「含まれるファイルと無視されるファイルのフィルタ」で `**.md` / `docs/**` を除外する（**この設定は Git の管理外のため、リポジトリを複製しただけでは再現しません**）

### 11.2 データベースの構造を変更する

Cloud Run にはデプロイの前後に処理を挟む仕組みがないため、**マイグレーションは PC から手動で実行します。**

1. 作業用ブランチで [`prisma/schema.prisma`](../../../prisma/schema.prisma) を変更し、ローカルでマイグレーションを作成する（`pnpm prisma:migrate`）
2. Pull Request → CI 成功 → マージ
3. **本番データベースへマイグレーションを適用する**（下記）
4. 自動デプロイの完了を確認する

```powershell
Set-PSReadLineOption -HistorySaveStyle SaveNothing
$env:DATABASE_URL='<本番の接続文字列>'
pnpm exec prisma migrate status    # 未適用の変更を確認
pnpm exec prisma migrate deploy    # 適用
exit                               # ターミナルを閉じる
```

> **適用の順序に注意してください。** 列の追加のように既存のコードでも動作する変更は先に適用して構いません。列の削除や名前の変更のように既存のコードが動かなくなる変更は、デプロイのタイミングと合わせる必要があります。

### 11.3 ログを確認する

Cloud Run のサービス詳細画面の「ログ」タブで確認できます。

| 症状         | 探す文字列                                       |
| ---------- | ------------------------------------------- |
| コンテナが起動しない | `環境変数の検証に失敗しました:` — 続いて不足している変数名が日本語で表示されます |
| 画面がエラーになる  | `ERROR` レベルのログ                              |

### 11.4 費用を確認する

Google Cloud のコンソールで「お支払い」→「レポート」を開くと、利用状況と請求額を確認できます。無料枠の範囲であれば請求額は 0 円です。

Supabase は、プロジェクトのダッシュボードで使用量を確認できます。

### 11.5 以前の状態へ戻す（切り戻し）

問題のある内容を本番へ反映してしまった場合、元の状態へ戻せます。**戻し方は 2 種類あり、役割が違います。**

| 方法                         | 何が戻るか                 | 反映までの時間        | 使いどころ                         |
| -------------------------- | --------------------- | -------------- | ----------------------------- |
| **A. Cloud Run のリビジョンを戻す** | **動いているアプリだけ**        | 数十秒            | **まず止血する**。利用者への影響を最短で止める     |
| **B. GitHub の `main` を戻す** | **ソースコード**（結果としてアプリも） | 5〜10 分（自動デプロイ） | **恒久対応**。次のデプロイで問題が再発しないようにする |

> **A だけで終わらせないでください。** リビジョンを戻しても GitHub のソースコードは問題のある状態のままです。**次に誰かが `main` を更新した時点で、問題のあるコードが再びデプロイされます。** A で止血したあと、必ず B（または修正版のリリース）まで行ってください。

#### A. Cloud Run のリビジョンを戻す

1. Google Cloud のコンソールで **Cloud Run** を開き、対象のサービス（例: `contract-app`）を選びます。
2. **「リビジョン」タブ**を開きます。デプロイのたびに作られた履歴が、新しい順に一覧表示されます。
3. **戻したいリビジョンを特定します。** 作成日時が、問題が起きる前の最後のデプロイと一致するものです。名前は `contract-app-00012-abc` のように連番が付いています。
4. 上部の **「トラフィックを管理」** を押します。
5. 戻したいリビジョンを選び、**トラフィックの割合を `100`%** にします。現在のリビジョンは `0`% になります。
6. **「保存」** を押します。
7. 反映を確認します。

```powershell
$base="https://<サービス名>-<プロジェクト番号>.us-central1.run.app"
Invoke-WebRequest "$base/api/health" -UseBasicParsing
```

> **トラフィック**とは、利用者からのアクセスのことです。「リビジョン A に 100%」と設定すると、すべてのアクセスがそのリビジョンへ送られます。**古いリビジョンは削除されずに残っているため、すぐに切り替えられます。**

> **環境変数の設定ミスが原因の場合は、リビジョンを戻す必要はありません。** 「新しいリビジョンの編集とデプロイ」から値を修正すれば、その内容で新しいリビジョンが作られます。

#### B. GitHub の `main` を戻す

問題のあるコミットを打ち消す**新しいコミット**を作り、`main` へ反映します。これにより自動デプロイが動き、正常な状態がデプロイされます。

**コマンドで行う場合**

```powershell
# 1. main の最新を取得する
git checkout main
git pull

# 2. 取り消したいコミットを特定する（上が最新）
git log --oneline -5

# 3. そのコミットを打ち消すコミットを作る
git revert <コミットID>

# 4. main へ反映する（ここで自動デプロイが動く）
git push
```

**GitHub のサイト上で行う場合**

1. 対象の Pull Request のページを開きます。
2. マージ済みの Pull Request の下部にある **`Revert`** ボタンを押します。
3. 打ち消し用の Pull Request が自動で作られるので、CI の成功を確認してマージします。

> **`git revert` は「打ち消すコミットを新しく追加する」操作です。** 履歴は消えず、「いつ・何を取り消したか」が残ります。
> 
> **`git reset --hard` と強制 push（`git push --force`）は使わないでください。** 履歴そのものを書き換えるため、他の開発者の手元と食い違い、変更が失われる恐れがあります。

#### データベースの変更を伴っていた場合

**マイグレーションで変更したデータベースの構造は、A でも B でも元に戻りません。** アプリのコードだけが戻ります。

| 状況              | 対応                                                                             |
| --------------- | ------------------------------------------------------------------------------ |
| 列や表を**追加**しただけ  | そのままで問題ありません。古いコードは追加分を使わないだけです                                                |
| 列や表を**削除・改名**した | 古いコードが動かなくなります。**構造を元に戻すマイグレーションを別途作成して適用してください**（[11.2](#112-データベースの構造を変更する)） |

> このため、**列の削除や改名を含む変更は、切り戻しが難しくなります。** リリース前に十分な確認を行ってください。

### 11.6 鍵とパスワードの管理

| 対象                     | 漏洩時の対応                                                                 |
| ---------------------- | ---------------------------------------------------------------------- |
| Supabase の `secret` キー | Supabase のダッシュボードで無効化して再発行し、**Cloud Run の環境変数と、ローカルの `.env` の両方**を更新する |
| Supabase のデータベースパスワード  | 再生成し、接続文字列を作り直して Cloud Run の `DATABASE_URL` を更新する                      |
| `AUTH_SECRET`          | 新しい値を生成して Cloud Run の環境変数を更新する（利用者は再ログインが必要になります）                      |

### 11.7 本番で動かさないもの

| 対象                  | 理由                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| ジョブワーカー（pg-boss）    | 現時点で登録済みのジョブがなく、常時起動すると無料枠を消費するだけになるためです。実際のジョブを追加する段階で、起動方法を改めて検討します                               |
| ローカル開発用の PostgreSQL | [`docker/docker-compose.yml`](../../../docker/docker-compose.yml) の `db` は開発専用です。本番は Supabase を使います |

> **本番コンテナ内でワーカーを起動する場合**、`pnpm worker` は使えません。本番用のイメージには pnpm 本体が含まれていないためです。`./node_modules/.bin/tsx src/worker/index.ts` を使ってください。

### 12.1 何を新しく作るか

| 対象                      | 2 つ目以降         | 理由                                                      |
| ----------------------- | -------------- | ------------------------------------------------------- |

| Supabase アカウント          | **そのまま使う**     |                                                         |

### 12.2 テンプレートを複製する

複製の方法は 3 つあります。**どれを選んでも、以降の手順（本書の手順 1 以降）は同じです。**

| 方法                       | 手順                                                                                               | 向いている場合           |
| ------------------------ | ------------------------------------------------------------------------------------------------ | ----------------- |
| **テンプレートリポジトリ機能を使う**（推奨） | 元のリポジトリの Settings → General → **Template repository** を有効にしておき、`Use this template` から新しいリポジトリを作る | 今後も繰り返し複製する場合     |
| **コマンドで複製する**            | `gh repo create <新リポジトリ名> --private --template <ユーザー名>/<元リポジトリ名>`                                | 上と同じ結果をコマンドで得たい場合 |
| **フォルダごとコピーする**          | 元のフォルダをコピーし、**`.git` フォルダを削除**してから本書の [6.1](#61-コミットの署名を設定する) を実施する                              | 元の変更履歴を引き継ぎたくない場合 |

> **`.git` フォルダの削除を忘れないでください。** フォルダをコピーしただけでは元のリポジトリとの紐付けが残っており、**元のシステムへ push してしまう恐れがあります。**

#### 複製したあとに変更する箇所

| 対象                      | 変更内容                                            |
| ----------------------- | ----------------------------------------------- |
| `package.json` の `name` | 新しいシステムの名前                                      |
| `README.md` / `docs/`   | システム名・説明                                        |
| **`AUTH_SECRET`**       | **必ず新しく生成する。** 使い回すと、片方の鍵が漏れたときに両方のシステムが影響を受けます |
| **初期管理者のパスワード**         | **必ず変える**（[8.5](#85-初期管理者を登録する)）                |
| Supabase の接続情報・キー       | 新しいプロジェクトの値                                     |
| Cloud Run のサービス名        | 新しい名前（URL になります）                                |

> **元のシステムの `.env` をコピーしないでください。** 接続先が元のシステムのデータベースのままになり、**別システムのつもりで既存データを書き換えてしまいます。** `.env.example` からコピーし直してください。

### 12.3 Supabase と Google Cloud の分け方

#### Supabase

**システムごとにプロジェクトを分けてください。** データベースが混在すると、片方の作業がもう片方へ影響します。

> **無料枠で同時に稼働できるプロジェクト数には上限があります。** 上限に達した場合は、使わないプロジェクトを停止するか、有料プランを検討してください。最新の条件は [Supabase の料金ページ](https://supabase.com/pricing)で確認できます。

**リージョンは、対応する Cloud Run と近い場所を選びます**（[4 章](#4-あとから変更できない項目)）。1 つ目と同じ構成にするのであれば、East US (North Virginia) です。

#### Google Cloud

| 方針                  | 内容                              | 判断の目安                                        |
| ------------------- | ------------------------------- | -------------------------------------------- |
| **プロジェクトを分ける**（推奨）  | システムごとに Google Cloud プロジェクトを作る  | 費用・権限・ログをシステム単位で分けられる。**案件ごとに担当者が違う場合は特に推奨** |
| 同じプロジェクト内にサービスを追加する | 1 つのプロジェクトに Cloud Run サービスを複数作る | 管理する画面が 1 つで済む。ただし費用の内訳が分かりにくくなる             |

> **どちらの方針でも、無料枠は「アカウント単位」ではなく利用量の合計に対して適用されます。** システムが増えるほど無料枠の消費は早くなるため、[9.4](#94-サービスの設定値) のインスタンスの最大数は**システムごとに必ず設定してください。**

### 12.4 2 つ目以降の作業手順

本書の手順を、次のとおり読み替えて実施します。

| 手順                                             | 2 つ目以降                                                |
| ---------------------------------------------- | ----------------------------------------------------- |
| [手順1 GitHub](#6-手順1-github-リポジトリを用意する)         | アカウント作成は不要。**リポジトリの作成から**実施（[12.2](#122-テンプレートを複製する)） |
| [手順2 Supabase](#7-手順2-supabase-を作成する)          | アカウント作成は不要。**プロジェクトの作成から**実施                          |
| [手順3 データベースの初期化](#8-手順3-本番データベースを初期化する)        | **そのまま実施。** 接続文字列が新しいプロジェクトのものであることを必ず確認する            |
| [手順4 Cloud Run](#9-手順4-google-cloud-run-を構築する) | アカウント作成・課金の有効化は不要。**プロジェクトまたはサービスの作成から**実施            |

## 13. トラブルシュート

### 13.1 ビルド・デプロイの問題

| 症状                                                                 | 原因                                               | 対処                                                                                    |
| ------------------------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------- |
| ビルドが 10 秒程度で失敗し、`Permission 'developerconnect.gitRepos...'` と表示される | GitHub からソースを取得する権限が不足している                       | トリガー編集画面の「すべて付与」を押す。権限の反映には時間差があるため、再実行で解決する場合もある（[9.6](#96-cloud-build-のビルド設定を修正する)） |
| `COPY failed: ... stat package.json: file does not exist`          | ビルドの起点が `docker/` になっている                         | ビルド設定の起点を `.`（リポジトリ全体）に変更する（[9.6](#96-cloud-build-のビルド設定を修正する)）                       |
| ビルド設定を直したのに、同じ場所で同じように失敗する                                         | 「ビルドを再試行」を使っている                                  | 「再試行」は修正前の設定を使い直す。**Cloud Build → トリガー → 「実行」**から実行する                                 |
| ビルドが制限時間で打ち切られる                                                    | 既定の制限時間（10 分）を超えた                                | ビルド設定に `timeout: 1800s` を追加する                                                         |
| `main` へ push したのにデプロイされない                                         | トリガーの対象ブランチが違う、またはコミットメッセージに `[skip ci]` が含まれている | Cloud Build のトリガー設定を確認する                                                              |

### 13.2 起動・接続の問題

| 症状                                                | 原因                                        | 対処                                                                                 |
| ------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| コンテナが起動せず、ログに `環境変数の検証に失敗しました:` と出る               | 必須の環境変数が不足している                            | 表示された変数名を Cloud Run の環境変数へ追加する（[9.5](#95-環境変数を設定する)）                               |
| `/api/health` は成功するが `/api/health?check=db` が失敗する | データベースへ接続できていない                           | 接続文字列が **Session pooler**（ポート 5432・ホスト名に `pooler` を含む）か確認する（[7.3](#73-接続文字列を取得する)） |
| データベースへの接続がタイムアウトする                               | Direct connection の接続文字列を使っている            | Session pooler へ変更する。Direct connection は Cloud Run から到達できない                        |
| `prisma migrate deploy` が失敗する                     | Transaction pooler（ポート 6543）の接続文字列を使っている  | Session pooler（ポート 5432）へ変更する                                                      |
| 認証エラーで接続できない                                      | パスワードの置換漏れ、または PowerShell のダブルクォートによる変数展開 | `[YOUR-PASSWORD]` を角かっこごと置換し、**シングルクォート**で囲む（[8.2](#82-接続先を設定する)）                  |

### 13.3 画面・ログインの問題

| 症状                           | 原因                           | 対処                                                                                |
| ---------------------------- | ---------------------------- | --------------------------------------------------------------------------------- |
| アプリの画面ではなく Google のログイン画面が出る | サービスの認証設定が「認証が必要」になっている      | 「パブリック アクセスを許可」へ変更する（[9.4](#94-サービスの設定値)）                                         |
| ログイン後にログイン画面へ戻り続ける           | `AUTH_URL` が実際の URL と一致していない | Cloud Run の環境変数を確認する。**末尾のスラッシュは付けない**                                            |
| ログインできず、失敗を繰り返した             | アカウントがロックされた（20 回で自動ロック）     | **自動では解除されません。** データベースの該当ユーザーの `lockedAt` を `null`、`failedAttempts` を `0` に戻す    |
| 初期管理者のパスワードが分からない            | seed の再実行では上書きできない           | データベースを直接更新する（[8.5](#85-初期管理者を登録する)）                                              |
| 画面のデザインが崩れている                | 静的ファイルが配信されていない              | ビルド設定で `--target runner` が指定されているか確認する                                            |
| ファイルの取得が失敗する                 | 非公開バケットに対して公開 URL を使っている     | `getSignedUrl` を使う（[`README.md`](../../../README.md#ブラウザへファイルを渡すurlgetsignedurl)） |

### 13.4 費用の問題

| 症状          | 原因                    | 対処                                                   |
| ----------- | --------------------- | ---------------------------------------------------- |
| 想定外の請求が発生した | インスタンスの最大数が既定（100）のまま | **`2` に設定する**（[9.4](#94-サービスの設定値)）。リビジョンの編集で変更できる    |
| 無料枠の消費が早い   | メモリを 1GiB 以上に設定している   | 512MiB へ戻す。実測値は 77MB のため十分です                         |
| リージョンを間違えた  | 米国以外のリージョンで作成した       | 無料枠の対象外です。**サービスを作り直してください**（[4 章](#4-あとから変更できない項目)） |
