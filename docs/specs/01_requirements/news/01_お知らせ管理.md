# お知らせ管理 要件定義

ダッシュボード（トップ画面）に表示する「お知らせ」を、管理者・運用者が自分たちで登録・更新・削除できるようにするための要件。2026-08-24 に利用者と1問1答で確認して確定した内容をまとめる。

## 01.1 目的と背景

このテンプレートには「お知らせ」を表示する仕組みの下ごしらえ（データの入れ物と、公開中のものを新しい順に取り出す処理）だけがあり、**登録・更新・削除をする画面が無い**。お知らせを出したいときは、開発者がデータベースへ直接書き込むしかない状態になっている。

そこで、**管理者・運用者が自分たちで画面から登録・更新・削除できるようにする**。詳細画面は作らず、一覧の上にポップアップを開いて入力する形にする（他の画面遷移を増やさず、操作を一箇所で完結させるため）。

## 01.2 用語

> **カテゴリ**とは、お知らせの種類を表す区分のこと。「お知らせ」「メンテナンス」「障害情報」の3種類から選ぶ。

> **重要度**とは、お知らせの優先度を表す区分のこと。「低」「中」「高」の3段階。一覧の絞り込みや管理のために持たせるもので、利用者向けの画面には表示しない。

> **公開期間**とは、お知らせを利用者に見せる期間のこと。開始日時・終了日時をそれぞれ任意で指定できる。両方とも空にすると、常に公開されているものとして扱う。

> **公開／非公開トグル**とは、公開期間とは別に、管理者・運用者が手動で表示・非表示を切り替えられる印のこと。公開期間の途中でも、これをOFFにすれば一時的に非表示にできる。

## 01.3 現在の状態

| 項目 | 状態 |
|---|---|
| データの入れ物（`Announcement`モデル） | ある。ただし `title`（タイトル）・`body`（本文）・`published`（公開中かどうか）・`deleted`（論理削除の印）・登録日時・更新日時しか持っていない |
| 登録・更新・削除の画面 | **無い** |
| 公開中のものを取り出す処理 | ある（`listLatest()`。新しい順に取得するだけの簡単なもの） |
| カテゴリ・重要度・公開期間・登録者/更新者の記録 | **無い** |

## 01.4 実現すること

### 01.4.1 画面構成（3画面）

| 画面 | 対象者 | 内容 |
|---|---|---|
| トップ画面のお知らせウィジェット | 全ロール（`ADMIN`/`OPERATOR`/`VIEWER`） | 公開中のお知らせを最新20件まで表示する。「さらに表示」リンクを置く |
| お知らせ一覧（閲覧専用） | 全ロール | トップ画面の「さらに表示」の遷移先。公開中のもののみを表示する |
| お知らせ管理（新設） | `ADMIN`・`OPERATOR`のみ | 一覧の上のポップアップで登録・更新・削除を行う画面。**詳細画面は作らない** |

### 01.4.2 お知らせが持つ項目

| 項目 | 必須 | 内容 |
|---|---|---|
| タイトル | 必須 | 最大200文字 |
| 本文 | 必須 | 最大3000文字。プレーンテキストとし、改行だけをそのまま反映する（太字・リンクなどの装飾には対応しない） |
| カテゴリ | 必須 | 「お知らせ」「メンテナンス」「障害情報」の固定選択肢から1つ選ぶ |
| 重要度 | 必須 | 「低」「中」「高」の3段階から1つ選ぶ |
| 公開開始日時 | 任意 | 空にした場合は、登録した時点から公開したものとして扱う |
| 公開終了日時 | 任意 | 空にした場合は、期限を決めずに公開し続ける |
| 公開／非公開トグル | － | 登録時の初期値はON。ONでも公開期間外なら表示されない |
| 登録者・更新者 | 自動で記録 | ログイン中の利用者を記録する（誰が最後に触ったかを追えるようにする） |

**入力の決まりごと**

- 公開終了日時が公開開始日時より前になっている場合は、登録・更新を止めて、該当する入力欄の下に赤字でエラーを出す
- 公開開始日時・公開終了日時は、日付だけでなく時刻まで指定できるようにする

### 01.4.3 公開・非公開の判定

利用者にお知らせを見せるかどうかは、次の**両方を満たす場合のみ**とする。

1. 公開／非公開トグルがON
2. 現在日時が公開期間内（開始日時・終了日時のどちらか、または両方が空の場合はその条件を満たしているものとみなす）

### 01.4.4 並び順と見た目（トップ画面・お知らせ一覧）

- 並び順：**障害情報 → メンテナンス → 通常のお知らせ（カテゴリ「お知らせ」）** の順に優先して並べ、同じカテゴリの中では公開開始日時が新しいものを上にする
- 1件ごとの表示：「公開日時：タイトル」を太字で1行表示し、改行のあとに本文を全文（クリック操作なしで）表示する
- カテゴリによる文字色分け：障害情報＝赤字、メンテナンス＝青字、通常のお知らせ＝黒字
- 公開日時の表示は時刻まで含める（例：`2026-08-24 09:00`）
- 公開中のお知らせが0件のときは「現在お知らせはありません」と表示する

### 01.4.5 お知らせ一覧（閲覧専用画面）

- 表示対象は**公開中のもののみ**（過去に公開が終わったものは含めない）
- 1ページ20件、ページ番号で切り替える形にする
- 検索・絞り込みは持たせない
- 表示形式はトップ画面のウィジェットと同じ繰り返しレイアウトにする

### 01.4.6 お知らせ管理（`ADMIN`・`OPERATOR`向け）

- 独立した専用ページとして新設する（マスタ管理と同じ配置の考え方）
- **`VIEWER`にはナビゲーションメニューへ表示しない。加えて、URLを直接開いても画面へ入れないようにする**（権限チェックを画面表示側だけでなく遷移の入口側にも置く）
- 一覧には、**公開期間外（公開前・公開終了後）や非公開中のものも含めて全件**表示する（管理者は先の予定や過去の履歴も含めて編集できる必要があるため）
- 列構成：タイトル・カテゴリ・重要度・公開開始日時・公開終了日時・公開ステータス・登録者・更新者・操作（編集／削除）
  - 公開ステータスは「公開中」「公開前」「終了」「非公開中」の4種類を判定して表示する（公開期間の判定と、公開／非公開トグルの両方を加味する）
- 検索：カテゴリ・重要度・文言（タイトルと本文の両方を対象にした部分一致）の3条件で絞り込めるようにする
- 並び替え：列見出しをクリックして自由に並び替えられるようにする（初期表示は公開開始日時の新しい順）
- ページング：1ページ20件、ページ番号で切り替える
- 登録・更新：一覧の上に開くポップアップで行う。**入力 → 内容確認画面 → 登録・更新**の2段階の流れにする（全ロールに見える情報なので、誤登録を防ぐため確認を挟む）
- 削除：**物理削除**（データベースから完全に削除する）とし、取り消せないことを確認ダイアログで示す

### 01.4.7 権限

| 操作 | `ADMIN` | `OPERATOR` | `VIEWER` |
|---|---|---|---|
| トップ画面・お知らせ一覧の閲覧 | ○ | ○ | ○ |
| お知らせ管理画面への入場 | ○ | ○ | × |
| 登録・更新・削除 | ○ | ○ | × |

## 01.5 安全のために守ること

- 登録・更新・削除の権限チェックは、画面の表示だけでなく**サーバー側の処理（Server Action）でも必ず行う**
- お知らせ管理画面は、`VIEWER`が直接URLを入力した場合でも入場できないよう、**遷移の入口（route guard）で権限を確認する**
- 本文はプレーンテキストとして扱い、HTMLタグなどをそのまま実行させない（表示時に適切にエスケープする）
- 削除は物理削除で元に戻せないため、削除ボタンを押した際は必ず確認ダイアログを経由させる

## 01.6 前提と制約

- 既読管理（誰が読んだか）は持たない
- 新規登録時のメール等による通知は行わない
- 添付ファイルには対応しない
- 本文はプレーンテキストのみとし、リッチテキスト（装飾・Markdown等）には対応しない
- お知らせ一覧・トップ画面のウィジェットに、検索・絞り込み機能は持たせない（お知らせ管理画面のみに検索を持たせる）

## 01.7 既存機能への影響

| 影響を受けるもの | 内容 |
|---|---|
| `prisma/schema.prisma` の `Announcement` モデル | `category`（カテゴリ）・`importance`（重要度）・`startAt`/`endAt`（公開開始・終了日時）・`createdBy`/`updatedBy`（登録者・更新者）を追加する。`deleted`（論理削除の印）は物理削除に方針を変えるため削除する。`published` は公開／非公開トグルとして引き続き使う |
| トップ画面（ダッシュボード） | お知らせウィジェットと「さらに表示」リンクを新設する |
| ナビゲーションメニュー | `ADMIN`・`OPERATOR`向けに「お知らせ管理」への導線を追加する（`VIEWER`には表示しない） |
| ルーティング | お知らせ一覧（閲覧専用）とお知らせ管理（`ADMIN`/`OPERATOR`限定）の2つの新しいページを追加する |

## 01.8 対象外・先送りするもの

- **既読管理**（誰が読んだかの記録・未読バッジ）。要望が出てから検討する
- **新規登録時のメール通知**。要望が出てから検討する
- **添付ファイル**。要望が出てから検討する
- **本文のリッチテキスト対応**（太字・リンク等の装飾、Markdown）。プレーンテキストで運用してみて、必要になってから検討する
- **カテゴリ・重要度の追加や自由入力化**。固定の3種類・3段階で運用してみて、必要になってから増やす
- **一般ユーザー向け画面での検索・絞り込み**。お知らせ管理画面の検索のみで対応する

## 01.9 設計の進め方として決めたこと

要件を確定するにあたって、設計・製造の前提として次を決めた。

| 項目 | 決定 |
|---|---|
| 削除方式 | 既存の `Announcement` モデルは論理削除（`deleted`フラグ）の方針だったが、**物理削除に変更する**。スキーマ変更（`deleted`カラムの削除）が必要 |
| 登録・更新のUIパターン | `src/modules/user/ui/user-edit-dialog.tsx` のダイアログ（Dialog + Server Action）を土台にしつつ、確認画面を挟む2段階の流れは `src/modules/master/` 配下の登録・更新パターンを踏襲する |
| 一覧のソートUI | お知らせ管理画面は `src/shared/ui` の `SortableTableHead` を用いた列見出しソートを使う（マスタ一覧と同じ実装方針） |
| 画面配置 | お知らせ管理は、マスタ管理と同様に独立した専用ページとして配置する |
| 設計書の分け方 | この要件定義をもとに、基本設計書は `docs/specs/02_basic-design/news/` へ機能・画面ごとに分割して作成する（マスタ・パスワード再発行と同じ粒度） |
