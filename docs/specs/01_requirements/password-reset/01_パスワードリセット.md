## 01.1 目的と背景

パスワードを忘れた利用者は、現在は管理者に連絡してパスワードを設定し直してもらうしかない。ログインに続けて失敗して使えなくなった（ロックされた）場合も、それを元に戻す画面が無い。

そこで、**利用者が自分のメールアドレスを使って本人であることを示し、自分でパスワードを設定し直せる**ようにする。あわせて、ロックされた状態もこの手順で元に戻せるようにする。

**新しいパスワードをメールで送る方式は採用しない。** メールに書かれたパスワードは受信箱に残り続けるため、メールを見られた時点でそのまま使われてしまう。代わりに、**再設定用のURLをメールで送り、そのURLの画面で利用者自身が新しいパスワードを入力する**方式にする。

## 01.2 用語

> **再設定用URL**とは、パスワードを設定し直す画面を開くための、一度だけ使える専用のURLのこと。有効期限があり、期限を過ぎたものと一度使ったものは開けなくなる。

> **ロック**とは、ログインに続けて失敗した利用者が、それ以上ログインを試せなくなった状態のこと。失敗できる回数は環境変数 `MAX_ATTEMPTS`（初期値20回）で決まる。

## 01.3 現在の状態

| 項目 | 状態 |
|---|---|
| 利用者のメールアドレス | 保存する場所は用意されている（`User.email`）が、入力は任意で、重複も許している |
| メールアドレスの変更 | **できない**。新規登録のときだけ入力でき、更新画面では表示名と役割しか変えられない |
| メールの送信 | **仕組みが無い**。送信用の部品も、送信先の契約もまだ無い |
| パスワードの変更 | ログイン後の変更画面はある（8文字以上・英字と数字を含む） |
| ロックの解除 | **画面が無い**。ロックされると解除する手段が無い |

## 01.4 実現すること

### 01.4.1 画面の流れ

1. ログイン画面に「パスワードを忘れた場合はこちら」のリンクを置く
2. リンクを押すと**再発行の申請画面**が開く。利用者は**メールアドレスだけ**を入力して送信する
3. 入力されたアドレスが登録済みなら、そのアドレス宛に**再設定用URL**を送る
4. 利用者はメールのURLを開き、**パスワード再設定画面**で新しいパスワードを2回入力して確定する
5. 完了したら**ログイン画面へ戻す**。「新しいパスワードでログインしてください」と伝える
6. パスワードが変わったことを知らせるメールを、同じアドレスへ送る

### 01.4.2 メールアドレスの登録

- 利用者を**新しく登録するときはメールアドレスを必須**にする
- メールアドレスは**重複を許さない**。同じアドレスを複数の利用者で共有することはできなくなる（申請画面でアドレスだけから利用者を特定するため）
- すでに登録されている利用者でメールアドレスが空のものは、そのまま残してよい。管理者が順に埋める
- **利用者の更新画面でメールアドレスを変更できるようにする**（管理者が変更する）
- **利用者本人も、ログイン後の画面から自分のメールアドレスを変更できるようにする**（→ [01.4.7](#0147-メールアドレスの変更)）

### 01.4.3 再発行の申請

- 入力項目は**メールアドレスのみ**
- 送信後は、**そのアドレスが登録済みかどうかにかかわらず同じ完了画面**を表示する（「登録がありません」とは出さない）
- 送信できる回数は、**同じ宛先につき24時間で5回まで**。それを超えた場合もメールを送らないだけで、画面の表示は変えない

### 01.4.4 再設定用URL

- 有効期限は**30分**
- **一度使ったら無効**にする
- 同じ利用者が新しく申請した場合、それまでに発行して未使用のURLは無効にする

### 01.4.5 パスワードの再設定

- 入力項目は「新しいパスワード」と「確認用のパスワード」の2つ
- パスワードの条件は**既存の変更画面と同じ**（8文字以上、英字と数字をそれぞれ含む、確認用と一致する）
- 期限切れ・使用済み・存在しないURLで開いた場合は、**その旨を伝えて申請画面へ案内する**
- 再設定に成功したときは、あわせて次の3つを行う
  - 次回ログイン時のパスワード変更の強制（`mustChangePassword`）を解除する
  - ログインの連続失敗回数を 0 に戻す
  - **ロックされていた場合は解除する**
- 再設定が終わっても**自動ではログインさせず**、ログイン画面へ戻す

### 01.4.6 送信するメール

| 種類 | 内容 |
|---|---|
| 再設定のお知らせ | 再設定用URLと、有効期限が30分であること、心当たりが無い場合は無視してよいことを書く |
| 変更完了のお知らせ | パスワードが変更されたこと、身に覚えが無い場合は管理者へ連絡してほしいことを書く |

### 01.4.7 メールアドレスの変更

メールアドレスは本人確認の手掛かりになるため、**変更できるのは管理者と本人だけ**とする。

| 誰が | どこで | 確認の手順 |
|---|---|---|
| 管理者 | 利用者の更新画面 | 無し（その場で変わる） |
| 本人 | ログイン後の自分の設定画面 | **変更先のアドレスへ確認用URLを送り、それを開いて初めて確定する** |

本人が変更する場合の流れは次のとおり。

1. 新しいメールアドレスを入力して申し込む
2. **新しいアドレス宛**に確認用URLを送る（有効期限は再設定用URLと同じ30分。一度使うと無効）
3. URLを開いた時点で、登録されているメールアドレスを新しいものへ変える
4. 変わったことを、**変更前のアドレス宛**にも知らせる

**確認が済むまで、登録されているメールアドレスは変えない。** 途中で放置された申し込みは、期限切れとして扱う。

## 01.5 安全のために守ること

- **どのメールアドレスが登録済みかを画面から分からないようにする。** 申請画面の表示・応答の内容を、登録の有無で変えない
- **再設定用URLの値をそのままの形でデータベースに保存しない。** 保存した情報が漏れても、そこからURLを組み立てられないようにする
- **URLは推測できない十分な長さの値**にする
- 同じ宛先への送信回数を制限し、大量送信の踏み台にされないようにする
- メールアドレスの変更を本人が行う場合は、**確認用URLを開くまで登録内容を変えない**。他人のアドレスを誤って（あるいは意図的に）登録したままにできないようにする
- 誰がいつ再発行を申請し、いつ再設定したかを記録に残す。記録は**いま使っているログの仕組みへ出す**（専用の履歴画面は作らない）

## 01.6 前提と制約

- メールの送信は、**メール送信の共通規格である SMTP** で行う（2026-08-21 変更。当初は Resend の独自の呼び出し方を使う想定だったが、乗り換えやすさを優先して共通規格に改めた）
- **このテンプレートでの動作確認は Gmail の SMTP を使う。** ドメインを持たなくても無料で他人宛に送れるため。案件へ本格的に流用する段階では Resend や Amazon SES へ乗り換える（どちらも SMTP に対応しているため設定値の差し替えだけで移行できる）。理由と乗り換え手順は [基本設計書 §02.6](../../02_basic-design/password-reset/02_メール送信.md#026-送信サービスの選び方と制約)
- 無料枠の範囲で運用する。1通あたりの価値が低い通知を増やしすぎない
- 開発中は実際にメールを送らず、内容を画面（コンソール）へ出して確認できるようにする
- 本番のURLを組み立てるため、アプリの公開URLを **`APP_BASE_URL`** という新しい設定として持つ（認証用の `AUTH_URL` とは別にする）
- 送信元のアドレスも設定として持ち、**送信サービスを乗り換えても設定の差し替えだけで済む**ようにする

## 01.7 既存機能への影響

| 影響を受けるもの | 内容 |
|---|---|
| 利用者の新規登録 | メールアドレスを必須にする。重複したアドレスは登録できなくなる |
| 利用者の更新 | メールアドレスの入力欄を追加する |
| データベース | `User.email` に重複を許さない設定を加える。再設定用URLを管理する入れ物を新しく追加する |
| 利用者本人の設定画面 | 自分のメールアドレスを変更する画面を新しく用意する |
| ログイン画面 | 「パスワードを忘れた場合はこちら」のリンクを追加する |
| 本番環境 | メール送信の接続情報（`SMTP_*`）・送信元アドレス・公開URL（`APP_BASE_URL`）の設定を追加する |

## 01.8 対象外・先送りするもの

- **Microsoft アカウント（Entra ID）だけでログインする利用者の扱い。** 今回は特別扱いをしない
- **管理者がロックを解除する専用画面。** 今回の再発行で解除できるため、必要になってから検討する
- **すでに登録されている利用者のメールアドレスを一括で埋める仕組み。** 管理者が画面から順に登録する

## 01.9 設計の進め方として決めたこと

要件を確定するにあたって、設計・製造の前提として次を決めた。

| 項目 | 決定 |
|---|---|
| 送信元アドレス | 設定で差し替えられる形にする。テンプレートでは送信専用に作った Gmail アドレスを使い、案件へ流用する際に独自ドメインのアドレスへ移す |
| 公開URLの持ち方 | 新しい設定 `APP_BASE_URL` を作る。ローカルは `http://localhost:3000`、本番は Cloud Run のURL |
| 操作の記録 | いま使っているログの仕組みへ出すだけにする。専用の履歴画面や履歴テーブルは作らない（発行したURLの記録自体は新しい表に残る） |
| メールアドレスの変更 | 管理者と本人の両方ができる。本人が変える場合は確認用URLで確かめる（→ [01.4.7](#0147-メールアドレスの変更)） |
| 設計書の分け方 | 契約先・契約管理機能と同じ粒度で、`docs/specs/02_basic-design/password-reset/` へ機能ごとに分割する |

なお、メール本文の文面は設計書側（メール送信の節）で確定する。
