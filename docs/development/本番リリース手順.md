# 本番リリース手順（全体の流れ）

変更を `main` へ反映してから、本番へ届くまでの全体像。個々の手順はリンク先の各ドキュメントが正本で、ここでは重複させない。

`main` への push が、そのまま Cloud Build 経由の自動デプロイになる。**ただし DB の構造変更（`prisma/schema.prisma` の変更）だけは自動化されておらず、ローカルから手動で適用する。**

## 全体の流れ

```text
作業用ブランチで変更
        │
        ├─ DBの構造変更を伴う？
        │     Yes → schema.prisma を編集し、ローカルでマイグレーションを作成する
        │     No  → そのまま次へ
        │
Pull Request を作成 → CI 成功を確認 → マージ
        │
main への push を Cloud Build が検知し、自動でビルド・デプロイ（5〜10分）
        │
        ├─ DBの構造変更を伴う？
        │     Yes → 本番の DATABASE_URL に対して手動で `prisma migrate deploy` を実行する
        │     No  → 何もしない
        │
デプロイ・疎通を確認する（/api/health?check=db 等）
```

## マイグレーションを自動化していない理由

Cloud Run にはデプロイ前後に処理を挟む仕組みがなく、Cloud Run Jobs や Cloud Build のデプロイ後ステップで自動化することも技術的には可能だが、以下の理由で見送り、手動運用を推奨する。

- 自動化すると、本番の `DATABASE_URL` を CI/CD 側のシークレットとして別途管理する対象が増える
- 列の削除・リネームのような**後方非互換な変更は、コードのデプロイと適用タイミングを人が判断する必要がある**（§3-2 参照）。自動適用にすると、意図しないタイミングで適用されるリスクが増す
