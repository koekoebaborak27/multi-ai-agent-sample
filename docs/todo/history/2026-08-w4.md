## 2026-08-24 お知らせ管理機能の要件定義を実施

**課題**: `src/modules/announcement/` はスタブのみで、公開中のお知らせを一覧取得する処理しか無く、登録・更新・削除の画面が無かった。`prisma/schema.prisma` の `Announcement` モデルも `title`/`body`/`published`/`deleted` しか持っていなかった。

**進め方**: `/grill-me`（grillingスキル）で1問1答形式のヒアリングを実施。既存の類似実装（`src/modules/user/`のポップアップ編集、`src/modules/master/`の一覧+ポップアップCRUD・確認画面パターン）を事前に調査したうえで質問した。

**確定した主な内容**:

- 画面は3枚。トップ画面のお知らせウィジェット（全ロール、公開中の最新20件）・お知らせ一覧（閲覧専用、全ロール、公開中のみ、20件/ページ）・お知らせ管理（新設、`ADMIN`/`OPERATOR`限定、一覧+ポップアップの2段階確認でCRUD、`VIEWER`はメニュー非表示かつ直接URLアクセスも不可）
- 項目はタイトル（200文字）・本文（3000文字、プレーンテキスト）・カテゴリ（お知らせ/メンテナンス/障害情報の固定3種）・重要度（低/中/高）・公開開始/終了日時（任意）・公開/非公開トグル・登録者/更新者
- 表示条件は「公開トグルON かつ 現在日時が公開期間内」の両方を満たす場合のみ。並び順は障害情報→メンテナンス→通常の順にピン留めし、同カテゴリ内は公開開始日時の新しい順
- 既存の`Announcement`は論理削除（`deleted`フラグ）方針だったが、**物理削除へ変更**することを確定（要スキーマ変更）
- 既読管理・通知メール・添付ファイル・リッチテキストは対象外

**成果物**: [`docs/specs/01_requirements/news/01_お知らせ管理.md`](../../specs/01_requirements/news/01_お知らせ管理.md) を新規作成。`docs/todo/TODO.md` に「お知らせ管理機能」区分（設計→実装→単体テスト仕様書作成→単体テスト実施の4項目）を追加し、公開用テンプレートの切り出しより先に着手する優先順位で「次にやること」を書き換えた。コード変更なし。

## 2026-08-24 お知らせ管理機能のDBスキーマ変更（工程2）を完了

**やったこと**: `prisma/schema.prisma`の`Announcement`モデルを`News`へリネームし、設計書（[`01_データベース.md`](../../specs/02_basic-design/news/01_データベース.md)）どおりに`category`（`String`、必須）・`startAt`/`endAt`（任意日時）・`createdBy`/`updatedBy`（任意、FKなし）を追加し、`title`/`body`にそれぞれ`VarChar(200)`/`VarChar(3000)`の上限を設定、`deleted`を削除した。マイグレーションは`pnpm prisma:migrate -- --create-only`で雛形を生成し、自動生成される`DROP TABLE`+`CREATE TABLE`（データ消失）を手で書き換えて、`ALTER TABLE "Announcement" RENAME TO "News"`によりテーブルの行を保持したまま移行する内容にした（[`prisma_operations.md`](../../prisma_operations.md)のexpand/contract方針に沿ったパターンA+B）。あわせて、物理削除方針への変更に伴い`deleted = true`だった行を`DELETE`で物理削除し、カテゴリの概念が無かった既存行には`category = 'NEWS'`（お知らせ）を仮の値として埋めてから`NOT NULL`化した。

**詰まった点**: ローカル環境（非対話シェル）では`prisma migrate dev`が「テーブルが空でない場合のデータ消失警告」に対する確認プロンプトを出せず、`Prisma Migrate has detected that the environment is non-interactive`で必ず失敗した。ローカルDBの`Announcement`テーブルにあったseed由来の2行（使い捨てデータ）を一時的に削除して警告が出ない状態にしてから雛形を生成することで回避した。生成コマンドがユーザー確認なしでは実行をブロックされる場面があり、都度ユーザーの許可を得てから実行した。また、途中で`--name`未指定と誤判定されて対話プロンプト待ちのままスタックしたプロセス（`prisma migrate dev`の子プロセス）が発生し、PostgreSQLのアドバイザリロックを握ったまま残ったため、ユーザーの許可を得てプロセスを強制終了してから再実行した。

- Cloud Run Jobsで自動化: 専用Jobを新設し、本番`DATABASE_URL`をSecret Manager経由で参照。Cloud Build側にJob起動のトリガー設定も追加で必要
- Cloud Buildのデプロイ後ステップで自動化: `cloudbuild.yaml`にマイグレーション適用ステップを追加。Node/Prisma CLIを動かす環境構築と、本番`DATABASE_URL`をCloud Build側のシークレットとして渡す設定が必要

**理由**: どちらの自動化案も、本番DB接続情報をCI/CD側のシークレットとして新たに管理する対象が増える。加えて、列の削除・リネームのような後方非互換な変更は、コードのデプロイとマイグレーション適用のタイミングを人が判断する必要があり（[`prisma_operations.md`](../../prisma_operations.md) §3-2）、自動適用にすると意図しないタイミングで適用されるリスクが増す。これらを踏まえ現状維持を選択した。

**あわせて実施したこと**: ユーザーから「本番リリース手順の全体像をどこかに明記したい」と要望があり、`docs/development/gitの操作ルール.md`（PR〜マージまで）と`infra_design_10_構築後の運用.md`（自動デプロイ・マイグレーション適用の詳細）に分散していた情報をまとめる案内ページ [`docs/development/本番リリース手順.md`](../../development/本番リリース手順.md) を新設した。詳細手順は複製せず既存ドキュメントへリンクするに留め、`gitの操作ルール.md`冒頭と`README.md`のドキュメント一覧表から参照を追加した。コード変更なし、ドキュメントのみ。これで「公開用テンプレート切り出し前の準備」区分が完了した（2/2）。
