## 2026-08-15 アプリからworkerを呼び出す処理を実装

**第5段階（Cloud Run Jobs を含む本番構成）の工程1-1を完了した。** 設計書 [`30_CSVダウンロード.md`](../../specs/02_basic-design/master/30_CSVダウンロード.md) §30.1.7.4 の1番目の作業で、依頼（`requestExport`）のたびに、本番でだけ Cloud Run Admin API 経由で worker（Cloud Run Jobs）を単発起動するようにした。

セッション冒頭では、前回セッションの続きと思われる未コミットのdocs変更（見出し番号のリンク修正など35ファイル）が残っていた。すべて `docs/` 配下のみだったため、`AGENTS.md` の規約どおり `main` へ直接コミット・push してから、今回の作業用ブランチ `feat/infra-cloud-run-jobs` を作成した。

**実装したファイル。**

- [`src/shared/config/env.ts`](../../../src/shared/config/env.ts): `WORKER_INVOKE_MODE`（`none` / `cloud-run-job`）・`CLOUD_RUN_JOB_NAME`・`CLOUD_RUN_JOB_REGION`・`GOOGLE_CLOUD_PROJECT` を追加。`cloud-run-job` のときは後者3項目を `superRefine` で必須にし、設定漏れを起動時点で検知できるようにした
- [`.env.example`](../../../.env.example): 上記4項目を追記
- `src/shared/jobs/invoke-worker.ts`（新規）: `invokeWorker()`。Cloud Run上のメタデータサーバーからアクセストークンを取得し、Cloud Run Admin API v2 の `jobs.run` を呼ぶ。[`shared/storage/supabase.ts`](../../../src/shared/storage/supabase.ts) と同じ方針で、専用ライブラリ（`google-auth-library` 等）は使わず `fetch` で完結させた
- [`src/modules/master/service.ts`](../../../src/modules/master/service.ts): `requestExport` の `boss.send` 直後に `invokeWorker()` を呼び、設計書§30.1.5.1の手順7を満たす
- `src/shared/jobs/invoke-worker.test.ts`（新規）: `fetch` をモックして、`none` のとき何も送らないこと・`cloud-run-job` のとき正しい宛先へ送ること・起動要求が失敗しても例外を投げないことを検証
- 既存の `export.test.ts` / `service.test.ts` に `invoke-worker` のモックを追加（`boss.ts` と同じパターン）

**設計判断（ユーザー確認済み）: 起動要求が失敗しても依頼自体は失敗させない。** ジョブは既に pg-boss へ積まれているため、`invokeWorker()` は失敗時も例外を投げず `logger.warn` にだけ残す。Cloud Run Jobs は1-3以降で作成するため、`cloud-run-job` 経路の本番動作確認はまだできない（1-8へ持ち越し）。

**詰まった点。** `invoke-worker.ts` が `logger.ts` を経由して `env.LOG_LEVEL` を参照するため、`env` を `{ PAGE_SIZE: 30 }` のように部分的にしかモックしていない既存テスト（`export.test.ts` / `service.test.ts`）が、`service.ts` 経由で `invoke-worker.ts` を読み込んだ際に `pino` の初期化でクラッシュした。原因は `invoke-worker.ts` を丸ごとモックしていなかったことで、既存の `boss.ts` と同じ扱い（`vi.mock("@/shared/jobs/invoke-worker", () => ({ invokeWorker: vi.fn() }))`）を追加して解消した。

**検証。** `pnpm lint` / `format:check` / `typecheck` / `test`（14ファイル188テスト）が全て成功。ローカルの常駐 worker（`pnpm worker`）を手動起動し、ブラウザで ADMIN によるマスタ検索一覧のCSVダウンロード（依頼 → 生成 → 受け取り）が従来どおりエラーなく完了することを確認した（`WORKER_INVOKE_MODE` 未設定＝`none` のため `invokeWorker()` は即座に返る）。

次は1-2（worker専用の実行用イメージをDockerfileに用意する）。1-3以降はGoogle Cloudコンソール操作が中心になる見込み。
