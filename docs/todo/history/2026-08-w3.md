## 2026-08-15 worker専用の実行用イメージをDockerfileに用意

**第5段階の工程1-2を完了した。** 設計書 [`30_CSVダウンロード.md`](../../specs/02_basic-design/master/30_CSVダウンロード.md) §30.1.7.4 の1番目の作業で、`worker` を Cloud Run Jobs から起動できるイメージとして用意した。worker 側のコード（単発モード `--once`）は工程1-1で既に実装済みだったため、今回は Dockerfile 側のステージ追加のみ。

**変更したファイル。**

- [`docker/Dockerfile`](../../../docker/Dockerfile): `runner` ステージを `runner-base`（共通の土台）と、それを継承する `runner`（app用）・`worker`（Cloud Run Jobs用）に分割した。`worker` ステージは `ENTRYPOINT ["./node_modules/.bin/tsx", "src/worker/index.ts"]` + `CMD []` とし、`--once` などの追加引数は起動時（Cloud Run Jobs のジョブ実行引数、または `docker run <image> --once`）に渡す形にした
- [`README.md`](../../../README.md) の「本番デプロイ」節: `runner`/`worker` のステージ分割とENTRYPOINT化を反映

**詰まった点。** 当初 `CMD ["./node_modules/.bin/tsx", "src/worker/index.ts"]` だけにして `docker run <image> --once` を試したところ、`node: bad option: --once` で失敗した。`ENTRYPOINT` が無いと `docker run` に渡した引数が **CMD 全体を上書き**してしまい、`tsx` 自体が呼ばれなくなるため。`ENTRYPOINT` を固定し `CMD []` にすることで解消した。

**検証。** `docker build -f docker/Dockerfile --target worker` が成功し、`docker run <image> --once`（キュー空）で「pg-boss ready（単発実行）」→ 数秒後に「処理すべきジョブが無いため終了」→ exit code 0 を確認。引数なしでの常駐起動（`pg-boss ready（アイドル待受）`）も確認した。`runner` と `worker` のイメージサイズは同一（1.34GB、共通レイヤーのため実ディスク増加なし）。`pnpm lint` / `format:check` / `typecheck` / `test`（14ファイル188テスト）も成功。検証用イメージは作業後に削除済み。

次は1-3（Cloud Run Jobs の作成）。Google Cloud コンソール操作が中心になるため、着手前に手順書のドラフトを用意する。

## 2026-08-15 Cloud Run Jobs単体実行で監査ログへの機密情報平文記録を発見しSecret Manager化で対応

**§08.1.1〜08.1.2（Jobs 単体の手動実行とログ確認）を実施し、成功を確認した。** `gcloud run jobs execute contract-worker` で実行し、期待するログ（`worker 起動完了: pg-boss ready（単発実行）` → `処理すべきジョブが無いため、worker を終了します`）と正常終了（`Container called exit(0).`、`succeededCount: 1`）を確認した。gcloud CLI はこのマシンに既にインストール・認証済みだったが、シェルの PATH が通っていなかったため、`$env:LOCALAPPDATA\Google\Cloud SDK\google-cloud-sdk\bin` を都度 PATH へ追加して実行した。

**ログ確認の過程で、Cloud Audit Log（`cloudaudit.googleapis.com/system_event`、`RunJob` イベント）にジョブの実行仕様（環境変数を含む）がそのまま複製されることを発見した。** `contract-worker`（Cloud Run Jobs）・`contract-app`（Cloud Run Service）はいずれも機密情報を「直接値」の環境変数として設定しており（[infra_design_05](../../specs/99_infra/infra_design_05_CloudRun構築.md) §05.1.5、[infra_design_07](../../specs/99_infra/infra_design_07_CloudRunJobs構築.md) §07.1.4 の従来の記載）、Cloud Logging を閲覧できる人なら誰でも `DATABASE_URL`（DB パスワードを含む）・`AUTH_SECRET`・`SUPABASE_SERVICE_ROLE_KEY`（管理者権限キー）を平文で見られる状態だった。

**ユーザー確認のうえ、工程1-9として Secret Manager 化のみ対応した。値のローテーションは、このプロジェクトが検証目的であることから対応不要と判断した。**

**実施した内容。**

- Secret Manager にシークレット3件（`database-url` / `auth-secret` / `supabase-service-role-key`）を作成。値は既存の Cloud Run 設定から一時ファイル経由（画面に表示せず）で取得・登録し、登録後に一時ファイルは削除した
- サービスアカウント（app・worker共通の既定の Compute Engine サービスアカウント）へ、3シークレットそれぞれの `roles/secretmanager.secretAccessor` をシークレット単位で付与（プロジェクト全体へは付与していない）
- `contract-worker`: `gcloud run jobs update` で `DATABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` を `--set-secrets` に切り替え

## 2026-08-16 マスタCSVをworker経由の非同期方式からapp内の同期方式へ作り直し

**§08.1.3（工程1-8）を非エンジニアのユーザーとチャットで一手順ずつ進める中で、`contract-worker` の環境変数設定漏れと、Cloud Run Jobs自体の起動待ちの長さという2つの問題を発見し、後者への対応としてマスタCSVの設計を非同期（worker）から同期（app内完結）へ全面的に作り直した。**

**経緯。** ブラウザで本番のCSVダウンロードを試したところ「時間がかかっています」のタイムアウト表示になった。Cloud Run コンソールの実行履歴とログを読みながら原因を切り分けた。

1. 最初の実行（`kxmj5`）は「処理すべきジョブが無い」と即座に終了しており、依頼したはずのジョブが処理されていなかった。
2. 直前の実行（`xhjbn`）のログを確認すると、ジョブは処理されていたが `Error: SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY が未設定です` で失敗していた。`gcloud run jobs describe` で確認すると、`contract-worker` に `SUPABASE_URL` が設定されていなかった。前日（2026-08-15）のSecret Manager切り替え作業で `--set-env-vars` を明示的に列挙し直した際、非機密の `SUPABASE_URL` だけがリストから漏れていたと判明。`gcloud run jobs update --update-env-vars` で追加し、ユーザーの承認を得て本番へ適用した（このマシンには `gcloud` CLIが導入済みだったが `PATH` が通っておらず、都度 `$env:PATH` へ追加して実行した）。
3. 修正後に再試行すると処理自体は成功（`✓ job:master.export`）していたが、依然として毎回タイムアウトした。`gcloud run jobs executions describe --format=json` で実行の状態遷移（`conditions`）を確認したところ、`ContainerReady` / `ResourcesAvailable` は作成から1秒以内に完了しているのに、`Started`（実際の処理開始）までは毎回1分半〜3分かかっていた。イメージ取得やリソース準備ではなく、Cloud Run Jobs自体の実行スケジューリングに時間がかかっていることが分かった。

**判断。** ユーザーと相談し、「appのリクエスト処理の中で重い処理をしない」という当初の設計理由（Cloud Runのリクエスト時間制限・無料枠の限られたリソースを共有していることによるクラッシュリスク）を踏まえつつも、**実測したCSV生成自体の処理時間が1〜2秒しかかからないため、この機能に限っては非同期化のコストに見合わない**と結論。app と worker を分けるという設計原則自体は変えず、**マスタCSVはworker（Cloud Run Jobs・pg-boss）を経由せず、appの中で1リクエスト完結の同期処理に作り直す**方針にした。worker本番構成（Cloud Run Jobs・専用サービスアカウント・Secret Manager）は、[`docs/todo/TODO.md`](../TODO.md) に既にある「マスタ情報Excel取得機能（workerサンプル）」で再利用する前提で維持する。

**実施した内容（`feat/master-csv-sync` ブランチ）。**

- Route Handlerを2本新設（`/api/master/exports/csv`・`/api/master/categories/exports/csv`）し、1リクエストで件数チェック→CSV生成→ファイル返却まで完結させた。旧来の依頼・状態確認・受け取りの3つのRoute Handler/Server Action（`requestMasterExportAction`・`requestMasterCategoryExportAction`・状態確認/受け取りRoute Handler）を削除

- `worker/index.ts` の `master.export` キュー購読を削除し、テンプレート標準の空の雛形へ戻した。`src/shared/jobs/invoke-worker.ts`（appからworkerを起動するCloud Run Admin API呼び出し）と、対応する環境変数（`WORKER_INVOKE_MODE`/`CLOUD_RUN_JOB_NAME`/`CLOUD_RUN_JOB_REGION`/`GOOGLE_CLOUD_PROJECT`）を削除
