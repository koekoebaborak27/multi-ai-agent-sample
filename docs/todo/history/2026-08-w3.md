## 2026-08-15 worker専用の実行用イメージをDockerfileに用意

**第5段階の工程1-2を完了した。** 設計書 [`30_CSVダウンロード.md`](../../specs/02_basic-design/master/30_CSVダウンロード.md) §30.1.7.4 の1番目の作業で、`worker` を Cloud Run Jobs から起動できるイメージとして用意した。worker 側のコード（単発モード `--once`）は工程1-1で既に実装済みだったため、今回は Dockerfile 側のステージ追加のみ。

**変更したファイル。**

- [`docker/Dockerfile`](../../../docker/Dockerfile): `runner` ステージを `runner-base`（共通の土台）と、それを継承する `runner`（app用）・`worker`（Cloud Run Jobs用）に分割した。`worker` ステージは `ENTRYPOINT ["./node_modules/.bin/tsx", "src/worker/index.ts"]` + `CMD []` とし、`--once` などの追加引数は起動時（Cloud Run Jobs のジョブ実行引数、または `docker run <image> --once`）に渡す形にした
- [`README.md`](../../../README.md) の「本番デプロイ」節: `runner`/`worker` のステージ分割とENTRYPOINT化を反映

**詰まった点。** 当初 `CMD ["./node_modules/.bin/tsx", "src/worker/index.ts"]` だけにして `docker run <image> --once` を試したところ、`node: bad option: --once` で失敗した。`ENTRYPOINT` が無いと `docker run` に渡した引数が **CMD 全体を上書き**してしまい、`tsx` 自体が呼ばれなくなるため。`ENTRYPOINT` を固定し `CMD []` にすることで解消した。

**検証。** `docker build -f docker/Dockerfile --target worker` が成功し、`docker run <image> --once`（キュー空）で「pg-boss ready（単発実行）」→ 数秒後に「処理すべきジョブが無いため終了」→ exit code 0 を確認。引数なしでの常駐起動（`pg-boss ready（アイドル待受）`）も確認した。`runner` と `worker` のイメージサイズは同一（1.34GB、共通レイヤーのため実ディスク増加なし）。`pnpm lint` / `format:check` / `typecheck` / `test`（14ファイル188テスト）も成功。検証用イメージは作業後に削除済み。

次は1-3（Cloud Run Jobs の作成）。Google Cloud コンソール操作が中心になるため、着手前に手順書のドラフトを用意する。

## 2026-08-16 マスタCSVをworker経由の非同期方式からapp内の同期方式へ作り直し

**§08.1.3（工程1-8）を非エンジニアのユーザーとチャットで一手順ずつ進める中で、`contract-worker` の環境変数設定漏れと、Cloud Run Jobs自体の起動待ちの長さという2つの問題を発見し、後者への対応としてマスタCSVの設計を非同期（worker）から同期（app内完結）へ全面的に作り直した。**

**経緯。** ブラウザで本番のCSVダウンロードを試したところ「時間がかかっています」のタイムアウト表示になった。Cloud Run コンソールの実行履歴とログを読みながら原因を切り分けた。

- 詳細画面に登録者・更新者を表示するか → 表示する（`Party`/`Contract`に`createdBy`/`updatedBy`を追加するマイグレーションが必要。設計のみで、実施は工程1）
- 契約の契約先選択プルダウン（現状は先頭`env.PAGE_SIZE`＝30件のみ表示）をどうするか → 検索できるコンボボックス（shadcn/uiの`Command`）に変更する。契約検索一覧の契約先絞り込みでも同じ部品を使う

**主な設計判断。**
- 契約先の削除は、紐づく契約が1件でも存在する場合はエラー（`PARTY_HAS_CONTRACTS`）にする。マスタ分類削除の「配下マスタが0件の場合だけ削除可」（[`master/24_マスタ分類削除.md`](../../specs/02_basic-design/master/24_マスタ分類削除.md)）と同じ、事前カウント確認＋外部キー制約による最終保証の二重構成
- 契約先分類・契約分類・契約先・状態はいずれも任意の絞り込み条件のため、一覧の初期値は（マスタ検索一覧の「登録済み分類の先頭」ではなく）「すべて」にする
- 契約の削除には契約先のような依存関係チェックを設けない。`ContractItem`（契約条項）を登録・参照する画面がまだ無く、削除しても外部キー制約に抵触しないため
- 一覧に埋め込まれている削除ボタンは撤去し、削除は詳細画面からのみ行う方式へ変更する（マスタ管理画面と同じ）
