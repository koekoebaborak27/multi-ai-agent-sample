# 単体テスト仕様書: メールアドレス変更申込（EML-01）

## 1. テスト対象
- 対象機能: 本人によるメールアドレス変更の申し込み画面。新しいアドレス宛に確認用URLを送る
- 対象画面またはAPI: `/settings/email`
- 対象ファイル:
  - `src/app/(main)/settings/email/page.tsx`
  - `src/modules/password-reset/ui/request-email-change-form.tsx`
  - `src/modules/password-reset/actions.ts`（`requestEmailChangeAction`）
- 関連DBテーブル: `EmailChangeToken`
- 関連設計書: [`docs/specs/02_basic-design/password-reset/20_メールアドレス管理.md`](../../../../specs/02_basic-design/password-reset/20_メールアドレス管理.md)（§20.2）

## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: 任意のロールでログイン済みの利用者（役割を問わない画面のため、ロールは1種類で確認すれば足りる）
- 権限: ログイン済みであること（未ログインの場合はTC-006で確認）
- 事前DB状態:
  - メールアドレス登録済みの利用者を1名用意する（TC-001・TC-003・TC-004用）
  - メールアドレス未登録の利用者を1名用意する（TC-002用）
  - 上記とは別に、既にメールアドレスが登録されている利用者をもう1名用意する（TC-005の重複確認用）
- 使用するテストデータ: 上記利用者の現在のメールアドレス、新しいメールアドレス、他利用者が使用中のメールアドレス

## 3. テスト観点
- 正常系: 画面表示、申し込み完了までの流れ、未登録時の表示
- 異常系: 現在のアドレスと同じ値、他利用者が使用中のアドレス、未ログイン時のアクセス
- 境界値: 該当なし（自動テストでカバー済み。§7参照）
- 権限: 未ログイン時に画面が開けないこと
- DB更新: `EmailChangeToken` の発行、`User.email` はこの時点では変わらないこと
- 画面表示: 現在のアドレスの表示（登録済み／未登録）、申し込み完了後の表示切り替え

## 7. 補足
- 必須・メール形式・254文字以内の入力チェック、および現在のアドレスと同じ場合・重複時のロジックは `src/modules/password-reset/validation.test.ts` / `service.test.ts` で自動テスト済み。入力欄が `type="email" required` のため、空欄・形式不備のままではブラウザ標準の検証が先に働き、アプリ側のエラー表示（「メールアドレスを入力してください」等）には画面操作では到達しない。そのため、これらのケースは本仕様書には含めない。
- 確認メールの送信に失敗した場合はエラーが画面に表示される仕様（設計書§20.2）だが、送信失敗を画面から意図的に再現する手段が無いため、本仕様書では確認しない。
