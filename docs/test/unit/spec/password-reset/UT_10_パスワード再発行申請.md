# 単体テスト仕様書: パスワード再発行申請（PWR-01）

## 1. テスト対象
- 対象機能: パスワード再発行の申請画面。メールアドレスを入力して再設定用URLの送信を申し込む
- 対象画面またはAPI: `/forgot-password`
- 対象ファイル:
  - `src/app/(auth)/forgot-password/page.tsx`
  - `src/modules/password-reset/ui/forgot-password-form.tsx`
  - `src/modules/password-reset/actions.ts`（`requestPasswordResetAction`）
  - `src/app/(auth)/login/page.tsx`（「パスワードを忘れた場合はこちら」リンク）
- 関連DBテーブル: `PasswordResetToken`
- 関連設計書: [`docs/specs/02_basic-design/password-reset/10_再発行申請.md`](../../../../specs/02_basic-design/password-reset/10_再発行申請.md)、[`00_パスワードリセット共通.md`](../../../../specs/02_basic-design/password-reset/00_パスワードリセット共通.md)

## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: 不要（ログインしていない状態で操作する）
- 権限: 誰でも開ける画面（`src/modules/auth/route-guard.ts` の `PUBLIC_PATHS` に `/forgot-password` を含む）
- 事前DB状態:
  - メールアドレスが登録済みの利用者を1名用意する（TC-002・TC-006用）
  - 上記利用者について、`PasswordResetToken` を `createdAt` が24時間以内のものを5件登録済みにしておく（TC-004用。24時間の発行回数の上限に達した状態を再現する）
  - 登録されていないメールアドレスを1つ用意する（TC-003用）
- 使用するテストデータ: 上記の登録済み利用者のメールアドレス、未登録のメールアドレス

## 3. テスト観点
- 正常系: 登録済み・未登録・送信上限到達のいずれでも同じ受付完了画面になること
- 異常系: 該当なし（形式チェックは `type="email" required` のブラウザ標準検証が先に働くため、画面操作ではアプリ側のエラー表示に到達しない。§7参照）
- 境界値: 該当なし
- 権限: 該当なし（ログイン不要画面）
- DB更新: 登録済み利用者のときだけ `PasswordResetToken` が1件増えること、それ以外（未登録・上限到達）は増えないこと
- 画面表示: 入力前後の表示切り替え、ログイン画面からのリンク

## 7. 補足
- 入力チェック（必須・メール形式・254文字以内）は `src/modules/password-reset/validation.test.ts` で自動テスト済み。加えて、入力欄・送信ボタンともに `type="email" required` の属性を持つため、空欄や不正な形式のままボタンを押してもブラウザ標準の検証（ネイティブバリデーション）が先に働き、アプリ側の `role="alert"` エラー表示（「メールアドレスを入力してください」等）には画面操作では到達しない。そのため、これらのエラー表示ケースは本仕様書には含めない。
- TC-004の送信上限（5件）や、`service.ts` のその他の分岐（古い未使用URLの無効化など）は `src/modules/password-reset/service.test.ts` で自動テスト済み。TC-004は「上限到達時も画面表示・応答時間の見た目が変わらないこと」という画面側の観点のみを確認する。
- 二重送信防止（送信後に入力欄が消えること）はTC-002・TC-003・TC-004のスクリーンショットで併せて確認できるため、独立したケースは設けない。
