# 単体テスト仕様書: マスタ更新（MST-05 / MST-03）

## 1. テスト対象
- 対象機能: マスタ更新（MST-05）・マスタ確認画面（MST-03・更新モード）
- 対象画面またはAPI: `/master/{masterId}/edit`（マスタ更新画面）
- 対象ファイル:
  - `src/app/(main)/master/[masterId]/edit/page.tsx`
  - `src/modules/master/ui/master-update-form.tsx`
  - `src/modules/master/ui/master-confirmation.tsx`
  - `src/modules/master/actions.ts`（`updateMasterAction`）
  - `src/modules/master/service.ts`（`updateMaster` / `assertCategoryExists` / `assertMasterCodeAvailable`）
  - `src/modules/master/repository.ts`（`updateMaster`）
  - `src/modules/master/validation.ts`（`updateMasterSchema`）
  - `src/shared/constants/roles.ts`（`canWrite`）
- 関連DBテーブル: `Master`、`MasterCategory`
- 関連設計書: [`docs/specs/02_basic-design/master/13_マスタ更新.md`](../../../specs/02_basic-design/master/13_マスタ更新.md)、[`docs/specs/02_basic-design/master/11_マスタ新規登録.md`](../../../specs/02_basic-design/master/11_マスタ新規登録.md)（§6.3 確認画面・§7 検証仕様）

## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: ADMINロール（正常系・異常系の実行）、VIEWERロール（TC-011の権限確認用）
- 権限: 「更新」画面へのアクセスと更新実行はADMIN/OPERATORロールに限る（`canWrite`）。VIEWERロールは画面を直接開いても詳細画面へリダイレクトされる。
- 事前DB状態:
  - 更新対象のマスタが分類Aに1件登録済み。
  - 分類Bが登録済みで、分類Bに「別コード重複確認用」のマスタコードを持つマスタが1件登録済み（TC-006で使用）。
  - 分類Cが登録済み（TC-005で削除して使用）。
- 使用するテストデータ:
  - 更新対象マスタの初期値（分類A・コード・内容）
  - 変更後の分類（分類B・分類C）、変更後のコード・内容

## 3. テスト観点
- 正常系: 3項目同時更新、値を変えない更新（自分自身との重複で拒否されない）、所属分類だけの変更
- 異常系: 変更後コードの形式エラー、変更後分類が存在しない、確認画面遷移時のコード重複、実行時点のコード重複、同時更新エラー
- 権限: VIEWERロールでの画面アクセス制御
- DB更新: `Master.categoryId` / `code` / `content` / `updatedBy` の更新、`createdBy` が変わらないこと、移動元分類が0件になっても削除されないこと
- 画面表示: 確認画面の変更前後表示（変更なし項目への「変更なし」併記を含む）、「入力内容を修正」での入力値保持、「キャンセル」での破棄

## 7. 補足
- TC-005・TC-007・TC-008は、確認画面表示後に別の利用者が操作した状況をブラウザの複数タブ操作では再現しにくいため、確認画面を表示したままDBを直接操作する手順とした。
- 「変更前のマスタコードは、更新後ただちに同じマスタ分類で再利用できる」（設計書§12.3）という仕様は、TC-003で分類を移した後、移動元の分類・変更前コードで新規登録できることを別途マスタ新規登録（UT_11）のテストデータ準備の中で暗黙に確認しているため、本仕様書では独立したテストケースとしては設けない。
