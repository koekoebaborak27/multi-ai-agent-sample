# 単体テスト仕様書: 契約先更新（PTY-05 / PTY-03）

## 1. テスト対象
- 対象機能: 契約先更新（PTY-05）・契約先確認画面（PTY-03・更新モード）・楽観ロック
- 対象画面またはAPI: `/parties/{partyId}/edit`（契約先更新画面）
- 対象ファイル:
  - `src/app/(main)/parties/[partyId]/edit/page.tsx`
  - `src/modules/party/ui/party-update-form.tsx`
  - `src/modules/party/ui/party-confirmation.tsx`
  - `src/modules/party/actions.ts`（`updatePartyAction`）
  - `src/modules/party/service.ts`（`update`）
  - `src/modules/party/repository.ts`（`updateIfUnchanged`）
  - `src/modules/party/validation.ts`（`updatePartySchema`）
- 関連DBテーブル: `Party`、`MasterCategory`、`Master`
- 関連設計書: [`docs/specs/02_basic-design/party-contract/13_契約先更新.md`](../../../specs/02_basic-design/party-contract/13_契約先更新.md)

## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: ADMINロール（正常系・異常系の実行）、VIEWERロール（TC-010の権限確認用）
- 権限: 更新画面へのアクセスと更新実行はADMIN/OPERATORロールに限る。VIEWERロールは画面を直接開くと対象契約先の詳細画面へリダイレクトされる。
- 事前DB状態:
  - 契約先分類が設定された契約先が1件登録済み（更新対象）。
  - 契約先分類（`CONTRACT_COMPANY_TYPE`）配下のマスタが2件以上登録済み（分類変更用）。
- 使用するテストデータ:
  - 変更後の名称（例: `更新確認商事`）、変更後の分類、変更後の連絡先

## 3. テスト観点
- 正常系: 名称・分類・連絡先の単独更新、3項目同時更新、分類の未設定への変更、値を変えない実行
- 異常系: 存在しない契約先の更新、存在しない契約先分類マスタIDへの変更、同時更新競合
- 境界値: 該当なし（新規登録と同じ検証のため`UT_11`でカバー済み）
- 権限: VIEWERロールでの画面アクセス制御
- DB更新: `Party` の `name` / `companyTypeMasterId` / `contactInfo` / `updatedBy` / `updatedAt` の更新、`createdBy` が変わらないこと
- 画面表示: 確認画面の変更前後表示（「変更なし」表記を含む）、「入力内容を修正」での入力値保持、「キャンセル」での破棄

## 7. 補足
- TC-006・TC-008は、確認画面表示後に別の利用者が操作した状況を再現するため、確認画面を表示したままDBを直接操作する手順とした（マスタ機能のUT_13と同じ考え方）。
- 名称・連絡先の文字数境界値（200文字/500文字）は`UT_11_契約先新規登録.md`で確認済みのため本仕様書では割愛する（入力検証スキーマは新規登録・更新で共通の`createPartySchema`相当の制約を使うため）。
