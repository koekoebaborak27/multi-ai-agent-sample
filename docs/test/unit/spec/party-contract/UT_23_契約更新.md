# 単体テスト仕様書: 契約更新（CTR-05 / CTR-03）

## 1. テスト対象
- 対象機能: 契約更新（CTR-05）・契約確認画面（CTR-03・更新モード）・楽観ロック
- 対象画面またはAPI: `/contracts/{contractId}/edit`（契約更新画面）
- 対象ファイル:
  - `src/app/(main)/contracts/[contractId]/edit/page.tsx`
  - `src/modules/contract/ui/contract-update-form.tsx`
  - `src/modules/contract/ui/contract-confirmation.tsx`
  - `src/modules/contract/actions.ts`（`updateContractAction`）
  - `src/modules/contract/service.ts`（`update`）
  - `src/modules/contract/repository.ts`（`updateIfUnchanged`）
  - `src/modules/contract/validation.ts`（`updateContractSchema`）
- 関連DBテーブル: `Contract`、`Party`、`MasterCategory`、`Master`
- 関連設計書: [`docs/specs/02_basic-design/party-contract/23_契約更新.md`](../../../specs/02_basic-design/party-contract/23_契約更新.md)

## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: ADMINロール（正常系・異常系の実行）、VIEWERロール（TC-011の権限確認用）
- 権限: 更新画面へのアクセスと更新実行はADMIN/OPERATORロールに限る。VIEWERロールは画面を直接開くと対象契約の詳細画面へリダイレクトされる。
- 事前DB状態:
  - 契約先・契約分類が設定された契約が1件登録済み（更新対象）。
  - `MasterCategory`（`CONTRACT_TYPE`）配下のマスタが2件以上登録済み（分類変更用）。
- 使用するテストデータ:
  - 変更後の契約名（例: `更新確認契約`）、変更後の開始日・終了日、変更後の状態、変更後の契約分類

## 3. テスト観点
- 正常系: 契約名・期間・状態・契約分類の単独更新、契約先以外4項目の同時更新、契約分類の未設定への変更、値を変えない実行
- 異常系: 存在しない契約の更新、存在しない契約分類マスタIDへの変更、同時更新競合、契約先変更の無視
- 境界値: 該当なし（新規登録と同じ検証のため`UT_21`でカバー済み）
- 権限: VIEWERロールでの画面アクセス制御
- DB更新: `Contract` の `title` / `startDate` / `endDate` / `status` / `categoryMasterId` / `updatedBy` / `updatedAt` の更新、`createdBy` と `partyId` が変わらないこと
- 画面表示: 契約先が読み取り専用表示になること、確認画面の変更前後表示（「変更なし」表記を含む）、「入力内容を修正」での入力値保持、「キャンセル」での破棄

## 7. 補足
- TC-009・TC-011は、確認画面表示後に別の利用者が操作した状況を再現するため、確認画面を表示したままDBを直接操作する手順とした。
- 契約名の文字数境界値（200文字/201文字）は`UT_21_契約新規登録.md`で確認済みのため本仕様書では割愛する（入力検証スキーマは新規登録・更新で同じ`title`制約を使うため）。
- 契約先を変更したい場合は対象契約を削除して登録し直す運用（§23.1.2）のため、契約先の変更自体を正常系として確認するテストケースは設けない。
