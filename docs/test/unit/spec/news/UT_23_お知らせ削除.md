# 単体テスト仕様書: お知らせ削除（NEWS-02）

## 1. テスト対象
- 対象機能: お知らせ削除・削除確認ダイアログ（NEWS-02）
- 対象画面またはAPI: `/news` の行ごとの「削除」ダイアログ、`deleteNewsAction`
- 対象ファイル: `src/modules/news/ui/news-delete-dialog.tsx`、`src/modules/news/actions.ts`、`src/modules/news/service.ts`、`src/modules/news/repository.ts`、`src/modules/news/validation.ts`
- 関連DBテーブル: `News`
- 関連設計書: [`23_お知らせ削除.md`](../../../../specs/02_basic-design/news/23_お知らせ削除.md)

## 2. 前提条件
- 実行環境: ローカル環境。本番URL・本番DBには接続しない。
- ログインユーザー: ADMIN（TC-001〜TC-004）、VIEWER（TC-005）。
- 権限: ADMIN/OPERATORは削除可能。VIEWERの削除Server Actionは `FORBIDDEN` で拒否される。
- 事前DB状態: 削除対象の公開中 `News` を各ケースごとに1件用意する。タイトル・カテゴリ・`updatedAt` が判別できること。
- 使用するテストデータ: `NEWS-DELETE-001` を含むタイトルの公開中お知らせ。

## 3. テスト観点
- 正常系: 確認ダイアログからの物理削除、一覧・トップ画面からの消失。
- 異常系: 同時更新、確認後に対象が既に削除済み、VIEWERの直接実行拒否。
- 境界値: 削除中の二重送信防止。
- 権限: Server Actionの書き込み権限確認。
- DB更新: `News` の物理削除、エラー時に状態を変えないこと。
- 画面表示: ダイアログの警告・対象情報・キャンセル・完了トースト。
- エビデンス取得: ダイアログ、成功、各エラー画面をPNGで保存する。

## 6. 未確定事項
- VIEWERのServer Action直接実行を画面テストで再現する方法と、同時更新・対象なし再現用のDB直接操作方法はテスト実行時に確認する。

## 7. 補足
- 削除は復元できない物理削除である。テストデータは各ケース用に個別作成し、他ケースと共有しない。
- 削除中の二重送信防止は、テスト実行時に「削除中...」表示と「削除する」ボタンの無効化を確認する。通信を遅延させる具体的方法は未確定のため、独立したケースにはせずTC-002の実行中確認に含める。
