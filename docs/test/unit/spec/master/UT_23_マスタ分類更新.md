## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: ADMINロール（正常系・異常系の実行）、VIEWERロール（TC-008の権限確認用）
- 権限: 「更新」画面へのアクセスと更新実行はADMIN/OPERATORロールに限る（`canWrite`）。VIEWERロールは画面を直接開いても詳細画面へリダイレクトされる。
- 事前DB状態:
  - `MasterCategory` に更新対象の分類が1件登録済み。
  - `MasterCategory` に「分類名重複確認用（更新）」という名称の別の分類が1件登録済みであること（TC-003・TC-004で使用）。
- 使用するテストデータ:
  - 更新対象の分類名（例: `更新対象分類`）
  - 変更後の分類名、既存分類と同名の分類名
  - 30文字ちょうどの分類名、31文字の分類名

## 3. テスト観点
- 正常系: 名称変更での更新完了、名称を変えない更新（自分自身との重複で拒否されない）
- 異常系: 確認画面遷移時の名称重複、実行時点の名称重複、同時更新エラー、未入力
- 境界値: 分類名30文字（更新可）／31文字（拒否）
- 権限: VIEWERロールでの画面アクセス制御
- DB更新: `MasterCategory.name` / `updatedBy` の更新、`createdBy` が変わらないこと、所属する `Master.categoryId` が変わらないこと
- 画面表示: 確認画面の表示項目（更新モード）、「入力内容を修正」での入力値保持、「キャンセル」での破棄
- 画面表示: 「実行」ボタン押下時の警告確認ダイアログ（表示内容・初期フォーカス・キャンセル動作、エラー時のダイアログ内表示。§00.5.1）

## 7. 補足
- TC-004・TC-005は、確認画面表示後に別の利用者が操作した状況をブラウザの複数タブ操作では再現しにくいため、確認画面を表示したままDBを直接操作する手順とした。
- 分類名を変更しても所属するマスタの `categoryId` が変わらないことは、マスタ分類が1件以上のマスタを持つ状態で更新を実行し、`Master` テーブルの該当行の `categoryId` が更新前後で変化しないことを確認して満たす（TC-001の事前条件で登録マスタ件数が判別できる分類を使うことで兼ねる）。
- 確認画面（更新モード）の「実行」ボタンは、押下時に警告確認ダイアログを挟む（§00.5.1）。対象分類を限定した判定は行わず、すべてのマスタ分類で表示されるため、TC-001〜TC-006・TC-012はいずれもこのダイアログの「OK」またはキャンセルの操作手順を含む。新規登録モードの確認画面（`UT_22_マスタ分類新規登録.md`）ではこのダイアログは表示されない。
