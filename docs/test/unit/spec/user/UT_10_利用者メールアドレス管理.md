# 単体テスト仕様書: 利用者メールアドレス管理（20.1 管理者による登録と変更）

パスワード再発行機能（20.1）で利用者管理画面に追加された、メールアドレスの登録・変更・一覧表示に関する観点のみを対象とする。ユーザーID・表示名・ロール・パスワードなど、メールアドレス以外の既存項目に関する単体テスト仕様書は別途作成する。

## 1. テスト対象
- 対象機能: 利用者管理画面でのメールアドレスの登録・変更・一覧表示
- 対象画面またはAPI: `/admin/users`
- 対象ファイル:
  - `src/app/(main)/admin/users/page.tsx`
  - `src/modules/user/ui/user-form.tsx`（新規登録）
  - `src/modules/user/ui/user-edit-dialog.tsx`（編集）
  - `src/modules/user/ui/user-table.tsx`（一覧）
  - `src/modules/user/actions.ts`（`createUserAction` / `updateUserAction`）
  - `src/modules/user/service.ts`（`create` / `update` のメールアドレス重複チェック）
- 関連DBテーブル: `User`
- 関連設計書: [`docs/specs/02_basic-design/password-reset/20_メールアドレス管理.md`](../../../../specs/02_basic-design/password-reset/20_メールアドレス管理.md)（§20.1）

## 2. 前提条件
- 実行環境: ローカル環境（`pnpm dev` で起動した検証用サーバー。本番URL・本番DBには接続しない）
- ログインユーザー: ADMINロールでログイン済み
- 権限: ADMINのみが開ける画面（本仕様書ではADMINロールでの操作のみを確認し、他ロールでのアクセス制御確認は対象外とする。§7参照）
- 事前DB状態:
  - メールアドレスが既に登録されている利用者を1名用意する（TC-002・TC-005の重複確認用）
  - メールアドレスが未登録の利用者を1名用意する（TC-006用）
  - 新規登録・編集の対象とする利用者（メールアドレス登録済み）を1名用意する（TC-003・TC-004用）
- 使用するテストデータ: 新規登録用の未使用メールアドレス、他利用者が使用中のメールアドレス

## 3. テスト観点
- 正常系: 新規登録時のメールアドレス登録、編集での変更、未登録利用者の編集画面表示
- 異常系: 新規登録・編集での重複メールアドレス
- 境界値: 該当なし（自動テストでカバー済み。§7参照）
- 権限: 該当なし（§7参照）
- DB更新: `User.email` の登録・書き換え
- 画面表示: 一覧のメール列表示、編集ダイアログの初期値表示

## 7. 補足
- 新規登録画面のメールアドレス入力欄は `type="email" required` のため、空欄・形式不備のままではブラウザ標準の検証が先に働き、アプリ側のバリデーションエラー（「メールアドレスは必須です」等）には画面操作では到達しない。そのため、これらのケースは本仕様書には含めない（`src/modules/user/validation.test.ts` で自動テスト済み）。
- 編集画面のメールアドレス入力欄は `required` を持たないため空欄保存が可能（TC-006で確認）。形式不備（不正な文字列）は `type="email"` によりブラウザ標準の検証で止まるため、こちらも画面操作では再現しない。
- ADMIN以外のロールで `/admin/users` にアクセスした場合のアクセス制御は、利用者管理画面全体に関わる観点でありパスワード再発行機能のスコープを超えるため、ユーザーとの確認の上、本仕様書には含めなかった。利用者管理機能自体の単体テスト仕様書を作成する際に別途扱うことを想定する。
- メールアドレスの重複チェックにデータベースの一意制約が絡む経路（アプリのチェックをすり抜けて `@unique` 制約に引っかかるケース）は、タイミング再現が難しいため本仕様書には含めない。`src/modules/user/service.test.ts` で自動テストされていない場合は、対応要否を別途判断する。
