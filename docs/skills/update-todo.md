# スキル: TODO とドキュメントの更新

[`docs/todo/TODO.md`](../todo/TODO.md) を最新の作業状況へ更新し、その内容が
[`README.md`](../../README.md) / [`README_SIMPLE.md`](../../README_SIMPLE.md) に影響する場合は、同じ変更の中で併せて更新する。

このファイルが手順の**正本**。Claude Code / GitHub Copilot / Codex の各入口ファイルは、ここを読ませるだけの薄いラッパーであり、手順を複製しない。

## どのファイルに書くかを先に決める

**書き込む前に、書き先を決める。** 同じ内容を 2 か所に書かない。**判断に迷ったら `TODO.md` 以外を選ぶ。**

| 書きたいこと | 書く場所 |
|---|---|
| **残タスク・進捗・次の一手** | [`docs/todo/TODO.md`](../todo/TODO.md) |
| 設計・仕様の決定（画面項目・データモデル・採用/不採用の理由） | [`docs/specs/`](../specs/) の設計書。マスタ機能は [`basic_design_master.md`](../specs/02_basic-design/basic_design_master.md) |
| 本番構築の手順 | [`docs/specs/99_infra/READ_ME_INFRA.md`](../specs/99_infra/README.md) |
| 設定値・落とし穴・実測値（コピペできるコマンド付き） | [`docs/todo/TODO_補足.md`](../todo/notes/README.md) |
| 何をやったか・なぜそうしたか・どこで詰まったか | [`docs/todo/TODO_履歴.md`](../todo/history/README.md) |
| UI / デザイン規約 | [`DESIGN.md`](../../DESIGN.md) |
| 初めてこのリポジトリを触る人が必要とする情報 | [`README.md`](../../README.md) |

**`TODO.md` に書いてよいのは「いま何が残っているか」だけ。** 仕様の要約・手順・実装内容・検証結果を `TODO.md` へ書かない。他ファイルへ書いたものは、本編からリンクで参照する。

> **なぜこの制約があるか**: 2026-08-10 時点で `TODO.md` は 378 行あり、その半分以上が設計書・履歴・補足・`README.md` と重複していた。同じ内容を 2 か所で維持していたため、更新のたびに時間がかかっていた。重複を各担当ファイルへ委譲して 140 行へ整理し、あわせてこの書き分け表と下記の 3 つのルールを設けた。

## 使うタイミング

- 「TODO を更新して」「作業結果を TODO に反映して」と指示されたとき
- セットアップ手順・デプロイ手順・画面構成・コマンドを変更する作業を終えたとき
- セッションを終える前に、次の担当者へ引き継ぐ内容を残すとき

## 手順

### 1. 現状を把握する

- `docs/todo/TODO.md` を**全文読む**（部分読みのまま書き換えない。セクション同士が相互参照しているため）
- 補足・履歴に書く / それを直す場合は、そのファイルも読む（本編だけ見て重複を書かない）
- `git status` / `git log --oneline -5` / `git diff` で、まだ TODO に反映されていない変更を確認する
- 今回のセッションで実際に実行したコマンドと、その結果（成功／失敗／所要時間）を洗い出す

### 2. TODO を更新する

- 完了した項目は `- [ ]` → `- [x]` にする。**項目自体は削除しない**（実施履歴として残す）
- 手順どおりに進まなかった場合は、項目本文を「実際にやったこと」へ書き換える
- 新たに判明したタスクは、**上から順に消化できる依存順**で挿入する（例: Supabase → Cloud Run）
- 詰まった点・落とし穴・設定値は [`docs/todo/TODO_補足.md`](../todo/notes/README.md) へ、**そのままコピペできるコマンド付き**で書く。書き先の判断は上の[書き分け表](#どのファイルに書くかを先に決める)に従う
- 完了した区分（全項目が `[x]`）は「完了済みの作業」の表へ移し、件数と履歴リンクを直す
- 毎回、次の 4 か所を最新化する。

  | 場所 | 書くこと |
  |---|---|
  | 本編「進捗サマリ」 | 各区分の `済 / 全体` を実数に合わせる |
  | 本編「次にやること」 | 次のセッションが**最初に打つコマンド**まで具体的に書く |
  | 本編「現在の状態」 | 事実のみ。推測・予定・仕様を混ぜない |
  | [`docs/todo/history/`](../todo/history/README.md) | 今回のセッションを**末尾**に追加（`## YYYY-MM-DD <やったことの要約>`）。**このファイルは時系列順（古いものが上）**なので、冒頭の目次にも同じく末尾へ 1 行足す |

**本編を太らせないための 3 つのルール。**

1. **進捗は「進捗サマリ」にだけ書く。** 「次にやること」「現在の状態」「チェックリスト」に `N / M 完了` を重ねて書かない。同じ数字が複数箇所にあると、毎回すべてを直すことになり、片方だけ古くなる
2. **完了項目は 1 行 + 履歴へのリンクにする。** 実装内容・検証結果・詰まった点は [`docs/todo/history/`](../todo/history/README.md) にだけ書く。本編は次の形にとどめる。

   ```markdown
   - [x] **7. マスタの新規登録と確認（MST-02 / MST-03）を実装する**（2026-08-10）→ [履歴](../todo/history/2026-08-w2.md#2026-08-10-マスタの新規登録と確認を実装)
   ```

3. **コミットハッシュ・PR 番号を本文へ埋め込まない。** `main` のハッシュは push のたびに古くなる。`git log --oneline -1` のような**確認コマンドを置く**（PR 番号は履歴側に残す）

- 見出しは記号を避ける（GitHub のアンカーは記号を落とすため、`## 本番 DB への適用手順` → `#本番-db-への適用手順` のように素直に変換できる形にする）
- 補足・履歴に節を足したら、そのファイル冒頭の目次と、本編からの参照リンクも合わせて足す
- 日付は必ず絶対日付（`2026-08-01`）で書く。「今日」「先週」と書かない
- 秘密情報（接続文字列の実値・パスワード・トークン・API キー）は書かない。`<プロジェクトref>` / `実際のパスワード` のようなプレースホルダにする

### 3. README への影響を判定する

下表に該当する変更があったときだけ README を触る。
**TODO のチェックを付けた・履歴を書いただけでは README は変更しない。**

| TODO 側の変更 | `README.md` | `README_SIMPLE.md` |
|---|---|---|
| 起動・セットアップ手順（docker compose のコマンド、`.env` の作り方、seed 手順） | 「はじめてローカル環境を構築する」の該当手順 | 対応する手順（1〜7） |
| pnpm / docker コマンドの追加・変更・廃止 | 「よく使うコマンド」 | 「よく使うコマンド」 |
| 画面・ルート・モジュールの追加/削除 | 「主な機能」の表 | 変更しない |
| 認証・ロール・ストレージの仕様変更 | 「認証と権限（RBAC）」/「ファイルストレージ」 | 変更しない |
| デプロイ先・本番手順・本番環境変数の変更 | 「本番デプロイ」と冒頭の箇条書き | 変更しない（本番手順は扱わない方針） |
| CI ステップの増減 | 「CI（GitHub Actions）」の番号付きリスト | 変更しない |
| ドキュメントの追加・削除・改名 | 「ドキュメント」の表 | 変更しない |
| エージェント指示ファイル・スキルの追加/変更 | 「AIエージェントによる開発」の表 | 「AIエージェントで開発する」の表 |
| 繰り返し発生したトラブルと対処 | 「セットアップ時によくある問題」 | 変更しない（README へ誘導済み） |

判定に迷ったら **「このリポジトリを初めて触る人が README だけ読んで詰まるか」** で決める。詰まるなら書く。詰まらないなら TODO に留める。

### 4. README を更新するときの制約

- `README_SIMPLE.md` は**初学者向けの最小手順**。分岐・理由・トラブル対処は書かず、`README.md` の該当セクションへリンクする
- 両方に同じコマンドが載っている箇所（docker compose の起動・seed・停止、検査コマンド）は、**必ず両方そろえて直す**
- リンクは相対パスの Markdown 形式。見出しを変更した場合は、その見出しへのアンカーリンク（`README.md#セットアップ時によくある問題` 等）の参照元も直す
- 文体は既存に合わせる（です・ます調、用語の初出は `> **用語**とは…` の引用ブロック）

### 5. 検証して報告する

- 変更したファイルの相対リンク先が実在することを確認する
- **`TODO.md` が 150 行を超えていないか確認する。** 超えていたら、どの節が他ファイルの内容を抱え込んでいるかを[書き分け表](#どのファイルに書くかを先に決める)で点検し、移す

  ```powershell
  (Get-Content docs/todo/TODO.md | Measure-Object -Line).Lines
  ```

- **`TODO.md` の見出しを変えないこと。** `#次にやること` / `#マスタ機能の製造工程` / `#残っているタスク` / `#完了済みの作業` へは、[`docs/todo/history/`](../todo/history/README.md)・[`docs/todo/notes/`](../todo/notes/README.md)・[`README.md`](../../README.md)・[`docs/specs/99_infra/`](../specs/99_infra/README.md) からアンカーリンクが張られている。節を作り替える場合は参照元も直す

  ```powershell
  rg -n "TODO\.md#" docs README.md
  ```

- Markdown は Prettier の対象外（[`.prettierignore`](../../.prettierignore) の `*.md`）なので、整形コマンドの実行は不要
- 報告は「何を・なぜ変えたか」を差分単位で述べる。**README を更新しなかった場合は、影響なしと判断した理由を 1 行添える**
